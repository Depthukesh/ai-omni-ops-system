# AI全域运营系统 知识库第一阶段数据库落地优先表清单 v1

## 1. 文档目的

本文档用于把知识库方向已经形成的主数据、页面、接口和关系设计，进一步收束成“第一阶段数据库落地优先表清单”，用于：

- 指导知识库域建表顺序
- 指导 Prisma schema 分批实施
- 避免一次性同时改太多知识库相关表导致风险失控

## 2. 排序原则

知识库第一阶段建议按以下原则排优先级：

- 先落主对象表
- 再落高频关系表
- 再落内容扩展表
- 最后落统计与任务表

判断标准主要看三点：

- 是否直接支撑知识空间后台管理
- 是否直接影响知识绑定接口
- 是否属于第一阶段必需能力

## 3. P0 优先表清单

### 3.1 知识空间主表

- `knowledge_spaces`

用途：

- 承担知识空间主对象
- 支撑知识空间列表页和详情页
- 承担品牌、模块、用户层面的知识归属

### 3.2 文档主表

- `knowledge_documents`

用途：

- 承担知识原始文档主对象
- 支撑文档列表和文档状态管理

### 3.3 通用绑定表

- `knowledge_bindings`

用途：

- 支撑知识空间与模块、能力包、Prompt、工作流步骤的通用绑定
- 支撑第一阶段知识绑定接口

## 4. P1 优先表清单

- `knowledge_tags`
- `knowledge_space_tags`
- `knowledge_retrieval_configs`
- `skill_package_knowledge_spaces`

用途：

- 支撑标签管理
- 支撑空间标签关联
- 支撑默认检索配置
- 支撑知识空间与能力包长期关系

## 5. P2 优先表清单

- `knowledge_chunks`
- `knowledge_embeddings`
- `knowledge_retrieval_logs`
- `knowledge_source_sync_tasks`

用途：

- 支撑切片和向量化
- 支撑检索效果分析
- 支撑同步任务和外部知识源接入

## 6. 建表批次建议

### 批次 A：先立底座

- `knowledge_spaces`
- `knowledge_documents`

### 批次 B：先打通绑定

- `knowledge_bindings`

### 批次 C：补配置与标签

- `knowledge_tags`
- `knowledge_space_tags`
- `knowledge_retrieval_configs`

### 批次 D：补能力包长期关系

- `skill_package_knowledge_spaces`

### 批次 E：补检索与同步能力

- `knowledge_chunks`
- `knowledge_embeddings`
- `knowledge_retrieval_logs`
- `knowledge_source_sync_tasks`

## 8. 第一阶段最小可运行数据集

如果目标是先把知识库后台管理和绑定关系跑起来，最小数据集建议为：

- `knowledge_spaces`
- `knowledge_documents`
- `knowledge_bindings`

只要这 3 张表先落地，知识空间列表、详情、文档列表、绑定关系页基本都能对接。

## 9. 与接口开发的对应关系

### 知识空间管理

- `knowledge_documents`

### 知识绑定接口

- `knowledge_bindings`

### 知识空间详情增强

- `knowledge_retrieval_configs`
- `knowledge_tags`
- `knowledge_space_tags`

### 与能力包长期关系

- `skill_package_knowledge_spaces`

## 10. 风险控制建议

为了避免第一阶段数据库改动过大，建议：

- 先按批次落表，不要一次性把知识检索层全做完
- 先保证 P0 表的增删改查可用
- 切片、向量、同步任务允许后置
- 第一阶段先不让现有前台业务强依赖这些表

## 11. 最终结论

知识库第一阶段数据库落地的核心，不是先把检索和向量能力全部做完，而是先让最关键的 3 张表支撑：

- 知识空间管理
- 文档管理
- 通用绑定关系

先把这三块跑通，再继续补标签、检索配置、能力包关系和向量层，会更稳，也更符合“不影响现有网站运行”的原则。
