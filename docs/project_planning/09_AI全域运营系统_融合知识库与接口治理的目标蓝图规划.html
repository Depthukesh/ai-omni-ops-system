AI全域运营系统融合知识库与接口治理的目标蓝图规划

本蓝图把现有系统架构分析报告与 `MaxKB`、`cc-switch` 的借鉴结论融合到一起，形成未来 6 到 12 个月可持续演进的目标架构。

当前基线 结构问题 目标蓝图 知识库蓝图 接口治理蓝图 蓝图总结

1. 当前系统基线

当前系统已经具备多用户、多品牌、品牌上下文隔离、多工作台前台、后台管理台、技能中心与提示词数据库真源、Provider 配置中心、第三方平台配置中心、任务中心和媒体资产中心。

当前主线：`Auth + Brands` 提供上下文，`Collectors` 提供原料，`Reports` 提供策略，`Works` 负责生产，`Publishing` 负责交付，`Tasks + Media` 作为横切面支撑。

2. 当前系统的主要结构问题

核心问题： 目前最大的结构风险是超级服务过重、知识沉淀尚未正式建模、第三方接口治理还停留在配置中心阶段，以及模块虽然页面独立但后端能力边界并未真正独立。
  • WorksService 和 ReportsService 过重
  • 知识沉淀没有正式知识库域
  • 接口治理缺少健康检测、熔断、用量和故障转移产品化能力
  • 工作台页面独立，但后端能力未完全独立
  • 模块注册与接入协议尚未建立

3. 新蓝图总体目标

目标定义： 以品牌为租户边界，以任务为执行边界，以媒体为产物边界，以知识库为长期记忆边界，以 Provider 治理网关为调用边界，把系统升级为“平台底座 + 领域能力 + 业务工作台 + 外挂能力引擎”的统一架构。

第一层：平台底座层

  • auth-core
  • brand-core
  • permission-core
  • task-core
  • media-core
  • provider-core
  • prompt-core
  • knowledge-core
  • workflow-core

第二层：领域能力层

  • collector-domain
  • strategy-domain
  • copy-domain
  • image-domain
  • video-domain
  • html-render-domain
  • publish-domain
  • knowledge-retrieval-domain
  • provider-routing-domain

第三层与第四层

第三层 是用户可见的业务工作台，如品牌增长、小红书、抖音、公众号、设计等。

第四层 是外挂能力引擎，用于放置类似 MaxKB 这样的外挂式知识问答与智能体系统，而不是直接揉进主系统代码层。

4. 融合 MaxKB 后的知识库蓝图

对 MaxKB 的吸收方式不是代码级融合，而是吸收其四个关键思想：知识库可检索、可问答、可进入工作流、可外挂解耦。

知识库在新蓝图中的三种角色

  • 长期记忆层： 承载品牌资料、产品资料、行业报告、历史经验、references、scripts 等。
  • 工作流输入层： 让工作流步骤按品牌或模块显式引用知识空间。
  • 智能问答层： 为未来外挂式问答助手或品牌 AI 助手提供知识能力。

建议新增的知识对象

对象 作用
KnowledgeSpace平台、品牌、模块、技能级知识空间容器
KnowledgeDocument知识原文档与来源
KnowledgeChunk知识切片
KnowledgeEmbedding向量化结果
KnowledgeBinding绑定模块、技能、Prompt、工作流步骤
KnowledgeRetrievalLog知识检索与召回日志

多品牌知识规则

  • 平台公共知识
  • 品牌公共知识
  • 品牌模块知识
  • 用户私有临时知识

建议检索优先级为：用户私有临时知识 → 品牌模块知识 → 品牌公共知识 → 平台公共知识。

MaxKB 在新蓝图中的正确位置：外挂知识问答与智能体引擎，而不是主系统内部的知识主数据层。

5. 融合 cc-switch 后的接口治理蓝图

对 cc-switch 的吸收方式同样不是照搬产品，而是吸收其 Provider 预设、切换、故障转移、健康检测、用量查询、Skills / Prompts 产品化管理思路。

层级 作用
Provider Registry 维护平台级供应商模板、模型、协议、默认超时和默认重试策略
Tenant Routing 维护品牌默认、品牌 fallback、技能绑定和用户覆盖策略
Execution Gateway 统一执行、超时、重试、熔断、fallback、日志和成本统计

建议新增对象

  • ProviderTemplate
  • ProviderModel
  • ProviderHealthSnapshot
  • BrandProviderPolicy
  • BrandModelPolicy
  • SkillProviderBinding
  • ExecutionAttempt
  • ExecutionRoute
  • ProviderFailoverPolicy
  • ModelDiagnosticRecord

未来调用链应统一为：工作流或技能声明需求 → Tenant Routing 计算候选链 → Execution Gateway 执行 → 任务中心记录 → 诊断层收口。

6. 技能与 Prompt 中心的目标状态

技能中心

  • 技能元信息
  • 技能版本
  • 技能状态
  • 依赖 Prompt / references / scripts / knowledge / provider
  • 绑定模块与更新记录

Prompt 中心

  • 平台默认、品牌覆盖、用户覆盖
  • 激活版本
  • 历史版本与回滚
  • 差异对比
  • 绑定知识空间与工作流步骤
未来建议把技能、Prompt、references、scripts、知识空间和 Provider 策略统一看作“能力包”，而不是零散配置项。

7. 蓝图总结

这份目标蓝图的核心不是继续向超级服务里堆功能，而是让主系统内部形成：

  • 多品牌知识主数据层
  • 工作流级知识引用机制
  • 平台级 Provider 治理层
  • 模块注册与能力包机制
最终结论： `MaxKB` 适合做外挂知识问答与智能体引擎，`cc-switch` 适合做 Provider 治理与技能管理产品化的参考对象；真正应该落到主系统内部的，是知识主数据层、治理网关层和模块注册机制。
