# AI全域运营系统统一技能中心设计方案 v1

## 1. 文档目的

本文档用于把第一阶段中“统一技能中心方案”单独展开，明确以下问题：

- 为什么要统一技能中心
- 统一后产品层长什么样
- 数据层如何保持 Skill 与 Prompt 边界
- 统一技能中心与能力包模型的关系是什么
- 旧入口未来如何迁移

## 2. 核心结论

建议采用以下原则：

1. 产品入口统一为“技能中心”  
2. Prompt 不再作为平行中心存在  
3. 数据模型中仍保留 Skill 与 Prompt 边界  
4. 技能中心本质上是“能力包管理中心”  

换句话说：

> 前台和后台都只解释一个“技能中心”，但在领域模型里，Skill、Prompt、references、scripts、knowledge、Provider 仍是不同对象。

## 3. 为什么要统一

如果继续保留“技能中心 + Prompt 中心”双入口，后续会出现以下问题：

- 用户理解成本高
- 配置入口重复
- 技能与 Prompt 的关系不直观
- references、scripts、knowledge、Provider 还会继续挂到不同地方
- 品牌覆盖与用户覆盖的入口会越来越碎

统一之后的收益是：

- 产品入口更清晰
- 能力配置链路更完整
- 后续知识库与 Provider 治理更容易挂接
- 更符合“能力包”平台化思路

## 4. 统一技能中心的定位

统一技能中心不是简单的“技能列表页”，而是一个统一管理以下对象的中心：

- Skill
- Prompt
- references
- scripts
- knowledge 绑定
- Provider 绑定
- 品牌覆盖
- 用户覆盖
- 版本记录

因此它的真实定位应为：

> 能力包管理中心。

## 5. 数据层原则

虽然产品入口统一，但数据层不建议物理合并成一个总表。

建议保留如下边界：

- `SkillPackage`：能力包聚合根
- `Skill`：能力定义对象
- `PromptAsset`：提示词资产对象
- `ReferenceAsset`：参考资料对象
- `ScriptAsset`：脚本资产对象
- `KnowledgeBinding`：知识绑定对象
- `ProviderBinding`：Provider 策略绑定对象

## 6. 统一技能中心的信息架构

## 6.1 列表页

列表页负责做“发现、筛选、状态查看”。

建议字段包括：

- 技能名称
- 所属模块
- 技能状态
- 当前版本
- 是否启用
- 最近更新时间
- 绑定品牌数
- 默认 Provider
- 是否存在品牌覆盖
- 是否存在用户覆盖

建议筛选项：

- 模块
- 状态
- 品牌
- 版本状态
- 是否启用
- 是否有覆盖

## 6.2 详情页

详情页负责做“查看、配置、版本管理、绑定关系管理”。

建议分为以下区域：

- 基本信息区
- Prompt 区
- references 区
- scripts 区
- knowledge 区
- Provider 区
- 版本区
- 品牌覆盖区
- 用户覆盖区

## 6.3 推荐页签结构

- `概览`
- `Prompt`
- `参考资料`
- `脚本`
- `知识`
- `Provider`
- `版本`
- `品牌覆盖`
- `用户覆盖`

## 7. 每个页签应承载什么

## 7.1 概览

展示：

- 技能名称
- 描述
- 所属模块
- 当前状态
- 当前激活版本
- 默认 Provider
- 默认知识空间
- 最近更新时间

## 7.2 Prompt

展示并管理：

- system prompt
- user prompt 模板
- Prompt 版本
- 激活版本
- 差异对比
- 回滚记录

## 7.3 参考资料

展示并管理：

- references 文档
- 文件来源
- 使用说明
- 适用范围

## 7.4 脚本

展示并管理：

- scripts 内容
- 参数说明
- 调用说明
- 适用步骤

## 7.5 知识

展示并管理：

- 绑定知识空间
- 检索范围
- 检索优先级
- 绑定步骤

## 7.6 Provider

展示并管理：

- 默认 Provider 策略
- fallback 策略
- 品牌级覆盖
- 可用模型白名单

## 7.7 版本

展示并管理：

- 能力包版本
- 发布时间
- 变更说明
- 激活状态

## 7.8 品牌覆盖

展示并管理：

- 品牌级 Prompt 覆盖
- 品牌级 Provider 覆盖
- 品牌级知识绑定覆盖

## 7.9 用户覆盖

展示并管理：

- 用户级 Prompt 覆盖
- 用户级 Provider 覆盖
- 用户级偏好覆盖

## 8. 统一技能中心与能力包模型的关系

统一技能中心是“管理界面”，能力包模型是“底层对象关系”。

建议关系如下：

- 技能中心列表项对应 `SkillPackage`
- 技能详情页对应一个能力包的完整视图
- Prompt、references、scripts、knowledge、Provider 都是能力包的组成资产

所以从系统架构上看：

- 技能中心属于产品层
- 能力包属于领域模型层

## 9. 权限与可见性建议

建议统一技能中心支持三类可见性：

- 平台可见
- 品牌可见
- 用户可见

建议支持三类角色：

- 平台管理员
- 品牌管理员
- 普通运营用户

不同角色在统一技能中心中的权限应不同：

- 平台管理员可管理平台默认能力包
- 品牌管理员可配置品牌覆盖
- 普通用户只能使用或查看可见能力

## 10. 迁移路线建议

建议分三步迁移。

### 第一步：命名统一

- 对内对外统一使用“技能中心”
- Prompt 中心不再作为主命名出现

### 第二步：入口统一

- 后台管理台合并入口
- 前台能力配置入口逐步收敛

### 第三步：对象统一映射

- 梳理现有 Skill 与 Prompt 的映射关系
- 梳理现有 references / scripts / Provider 配置的归属
- 把旧入口逐步迁入能力包结构

## 11. 第一阶段要交付到什么程度

第一阶段不要求直接重构完整前后台，只需要做到：

- [ ] 命名口径统一
- [ ] 信息架构清楚
- [ ] 页面结构清楚
- [ ] Skill 与 Prompt 边界清楚
- [ ] 迁移路线清楚

## 12. 最终结论

统一技能中心不是把 Skill 与 Prompt 混成一个对象，而是：

> 在产品层把所有能力相关入口收敛为一个统一中心，在领域模型层继续保留 Skill、Prompt 和其他资产的边界。

这会让系统后续在产品体验上更统一，在架构治理上也更稳。
