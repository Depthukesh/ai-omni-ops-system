# AI全域运营系统融合知识库与接口治理的目标蓝图规划

## 1. 文档目的

本文档用于把以下两部分内容融合成一份统一蓝图：

1. 当前系统架构分析报告  
2. 对 `MaxKB` 与 `cc-switch` 的融合评估结论  

目标不是再做一次零散分析，而是形成一份可指导未来 6 到 12 个月演进的目标蓝图，明确：

- 当前系统应该朝什么形态演进
- 哪些能力需要保留
- 哪些能力需要拆分
- 新增知识库域与接口治理域后，系统整体架构如何变化
- 多品牌、多模块、多工作流在未来应如何统一
- 哪些开源产品适合借鉴，哪些只适合外挂，不应深度融合

## 2. 蓝图结论先行

最终蓝图建议用一句话概括：

> 以品牌为租户边界，以任务为执行边界，以媒体为产物边界，以知识库为长期记忆边界，以 Provider 治理网关为调用边界，把现有多工作台系统升级为“平台底座 + 领域能力 + 业务工作台 + 外挂能力引擎”的统一架构。

这份蓝图的核心不再是“继续加功能”，而是：

- 让系统从功能集合变成平台系统
- 让新增模块可以像 USB 一样插拔接入
- 让知识与模型治理成为平台级能力，而不是每个模块自己维护

## 3. 当前系统基线

结合现有系统架构分析，当前系统已经具备以下基础：

- 多用户
- 多品牌
- 品牌上下文隔离
- 多工作台前台
- 后台管理台
- 技能中心与提示词数据库真源
- Provider 配置中心
- 第三方平台配置中心
- 任务中心
- 媒体资产中心
- 多平台内容生产链路

当前系统的主线已经明确：

1. `Auth + Brands` 提供身份与品牌上下文
2. `Collectors` 提供数据原料
3. `Reports` 提供策略、规划、文案
4. `Works` 负责内容和媒体生产
5. `Publishing` 负责交付
6. `Tasks` 和 `Media` 作为横切面支撑整条链路

这套主线是正确的，说明系统已经具备平台化雏形。

## 4. 当前系统的主要结构问题

虽然主方向正确，但当前系统仍有 5 个关键结构问题。

### 4.1 超级服务过重

目前最典型的是：

- `WorksService`
- `ReportsService`

问题在于：

- 业务跨度过大
- 平台边界不清晰
- 新增能力不断堆叠
- 回归风险高
- 未来很难形成“可插拔模块”

### 4.2 知识沉淀没有正式域模型

虽然系统里已经沉淀了大量资料，但当前还没有正式的知识库域来统一承载：

- 品牌资料
- 产品资料
- 行业报告
- references
- scripts
- 运营文档
- 平台规则说明
- 历史生成经验

这会导致：

- 知识不可复用
- 资料分散
- 工作流无法统一引用
- AI 只能依赖零散 prompt 里的引用

### 4.3 第三方接口治理还不够平台化

当前系统已有 Provider 配置和第三方平台配置，但整体仍偏“配置中心”，还没有演进成完整的调用治理层：

- 模型健康检测不够系统化
- 用量与余额视图不够完善
- 熔断与 failover 策略还不够产品化
- 品牌级 / 技能级 / 用户级路由还可继续标准化

### 4.4 模块虽然页面独立，但后端未完全能力独立

例如：

- 小红书、抖音、公众号、设计工作台虽然前台是独立模块
- 但后端仍大量挂在 `WorksModule` 和 `ReportsModule`

这意味着：

- 看起来模块独立
- 实际上能力边界仍不清晰

### 4.5 模块注册与接入协议尚未建立

当前系统还没有真正的“模块注册中心”与“标准能力合同”，新增模块更多还是通过人工约定接入，而不是通过一套清晰的平台协议接入。

## 5. 新蓝图的总体目标

未来蓝图建议分成四层。

### 5.1 第一层：平台底座层

这一层不面向最终用户页面，而面向所有模块提供统一基础能力。

建议包含：

- `auth-core`
- `brand-core`
- `permission-core`
- `task-core`
- `media-core`
- `storage-core`
- `provider-core`
- `prompt-core`
- `knowledge-core`
- `third-party-platform-core`
- `audit-core`
- `workflow-core`

这一层的目标是：

- 所有模块统一接入
- 任何新模块都不要重复造认证、任务、存储、Provider、知识检索、审计

### 5.2 第二层：领域能力层

这一层是可被多个业务工作台复用的领域服务。

建议包含：

- `collector-domain`
- `strategy-domain`
- `copy-domain`
- `image-domain`
- `video-domain`
- `html-render-domain`
- `publish-domain`
- `knowledge-retrieval-domain`
- `provider-routing-domain`
- `model-diagnostics-domain`

目标是：

- 让小红书、抖音、公众号、设计不直接依赖大而全的超级 service
- 而是组合这些领域能力

### 5.3 第三层：业务工作台层

这一层是用户真正看到的业务模块：

- `brand-growth-workbench`
- `xiaohongshu-workbench`
- `douyin-workbench`
- `wechat-workbench`
- `design-workbench`
- 未来的 `zhihu-workbench`
- 未来的 `video-channel-workbench`

这些工作台应通过声明式方式装配能力，而不是自由生长。

### 5.4 第四层：外挂能力引擎层

这一层用于承接那些不适合直接揉进主系统，但很有价值的外挂能力。

建议包含：

- 外挂知识问答引擎
- 外挂智能体平台
- 外挂数据处理引擎
- 外挂统一代理服务

这里 `MaxKB` 就更适合放在这一层，而不是放到主系统代码层。

## 6. 融合 MaxKB 后的知识库蓝图

## 6.1 我们对 MaxKB 的吸收方式

不是代码级吸收，而是吸收其 4 个核心思想：

1. 知识库不只是文件仓库，而是可检索、可问答、可进入工作流的知识引擎
2. 知识要支持文档摄入、拆分、向量化与检索增强
3. 知识能力可以为工作流和 Agent 服务，而不是只给问答页面服务
4. 外挂式知识引擎与主系统主数据层可以解耦

## 6.2 新蓝图中的知识库定位

知识库在新蓝图中不是独立孤岛，而是以下三种角色的统一体：

### 6.2.1 长期记忆层

承载长期沉淀资料：

- 品牌资料
- 产品资料
- 行业报告
- 历史作品经验
- references
- scripts
- 操作文档

### 6.2.2 工作流输入层

在工作流中可被步骤显式引用，例如：

- 文章生成步骤使用品牌知识空间
- 爆文模仿步骤使用小红书参考知识空间
- HTML 渲染步骤使用品牌视觉规范知识空间

### 6.2.3 智能问答层

为未来外挂式问答助手或运营助手提供知识检索能力。

## 6.3 新知识库域建议建模

建议主系统内新增以下对象：

### 6.3.1 KnowledgeSpace

作为知识空间顶层容器，用于承载：

- 平台公共知识
- 品牌知识
- 模块知识
- 技能知识
- 用户临时知识

### 6.3.2 KnowledgeDocument

记录知识原文档与来源。

### 6.3.3 KnowledgeChunk

记录知识切片，用于检索与召回。

### 6.3.4 KnowledgeEmbedding

记录向量化结果。

### 6.3.5 KnowledgeBinding

把知识空间绑定到：

- 模块
- 子模块
- 技能
- Prompt
- 工作流步骤

### 6.3.6 KnowledgeRetrievalLog

记录谁在什么时候检索了哪些知识，以及命中了哪些内容。

## 6.4 多品牌知识库规则

知识库在多品牌场景下必须采用分层隔离。

建议层级：

1. 平台公共知识
2. 品牌公共知识
3. 品牌模块知识
4. 用户私有临时知识

建议检索优先级：

1. 用户私有临时知识
2. 品牌模块知识
3. 品牌公共知识
4. 平台公共知识

这套设计可以同时满足：

- 多品牌隔离
- 平台知识复用
- 模块知识复用
- 局部定制覆盖

## 6.5 MaxKB 在新蓝图中的位置

建议把 MaxKB 放在“外挂能力引擎层”，承担：

- 统一问答助手
- 培训与客服类问答
- 运营知识问答
- 智能体编排实验场

不建议：

- 作为主系统内部核心代码模块
- 直接承载品牌权限主数据
- 直接取代主系统的知识主数据层

换句话说：

> 主系统负责知识归属、权限、绑定和工作流接入；MaxKB 如需使用，则负责外挂问答与智能体交互。

## 7. 融合 cc-switch 后的接口治理蓝图

## 7.1 我们对 cc-switch 的吸收方式

同样不是照搬产品，而是吸收其 6 个核心思想：

1. Provider 应该有模板、预设、复制、排序和切换能力
2. Provider 管理不应停留在静态配置，而要支持高可用
3. 应该有模型健康检查
4. 应该有用量与配额视图
5. Prompt / Skill 管理应产品化
6. 应该有统一代理与故障转移思路

## 7.2 新蓝图中的 Provider 治理定位

Provider 治理在新蓝图中应从“配置中心”升级为“平台调用治理层”。

建议拆成三层。

### 7.2.1 Provider Registry

负责平台级定义：

- 供应商模板
- 协议类型
- 模型列表
- 默认超时
- 默认重试
- 默认定价
- 默认健康状态规则

### 7.2.2 Tenant Routing

这里的 Tenant 即品牌租户。

负责：

- 品牌默认 Provider
- 品牌 fallback 链
- 品牌禁用模型
- 品牌成本上限
- 用户个性化覆盖
- 模块与技能绑定策略

### 7.2.3 Execution Gateway

负责：

- 统一执行调用
- 统一错误分类
- 统一超时
- 统一重试
- 统一熔断
- 统一 fallback
- 统一日志
- 统一成本记录

## 7.3 新蓝图中的多品牌接口治理规则

建议遵循四级继承链：

1. 平台默认
2. 品牌默认
3. 模块/技能绑定
4. 用户覆盖

执行时再由统一治理层收口。

## 7.4 新增的治理对象

建议后续补充以下对象：

- `ProviderTemplate`
- `ProviderModel`
- `ProviderHealthSnapshot`
- `BrandProviderPolicy`
- `BrandModelPolicy`
- `SkillProviderBinding`
- `ExecutionAttempt`
- `ExecutionRoute`
- `ProviderFailoverPolicy`
- `ModelDiagnosticRecord`

## 7.5 模型调用链的新规则

未来不应再由业务模块自由决定模型调用细节，而应统一走：

1. 工作流或技能声明需求
2. Tenant Routing 计算可选 Provider
3. Execution Gateway 决定真实执行链
4. 任务中心记录执行过程
5. Diagnostics 记录失败与健康状态

这一步完成后，Provider 才真正从“配置项”升级为“平台能力”。

## 8. 新蓝图下的技能与 Prompt 中心

这部分是受到 `MaxKB` 与 `cc-switch` 双重启发后最值得补强的地方。

## 8.1 技能中心未来定位

技能中心不应只是：

- 一条技能记录
- 一段 Prompt

而应演进成真正的“能力包管理中心”。

建议每个技能未来至少包含：

- 技能元信息
- 技能版本
- 技能状态
- 依赖的 Prompt
- 依赖的 references
- 依赖的 scripts
- 依赖的知识空间
- 依赖的 Provider 策略
- 绑定的模块
- 更新记录

## 8.2 Prompt 中心未来定位

Prompt 中心不应只是编辑器，而应支持：

- 平台默认 Prompt
- 品牌覆盖 Prompt
- 用户覆盖 Prompt
- 历史版本
- 激活版本
- 回滚
- 差异对比
- 绑定知识空间
- 绑定技能和工作流步骤

## 8.3 统一能力包思想

未来建议把以下对象统一看作“能力包”：

- 技能
- Prompt
- references
- scripts
- 知识空间
- Provider 策略

当模块需要接入某种能力时，不应手工逐项找配置，而应直接绑定某个能力包。

## 9. 蓝图下的模块目标状态

## 9.1 品牌增长工作台

目标状态：

- 继续作为上游资料与策略层
- 增加知识沉淀能力
- 把品牌资料自动同步进入品牌知识空间

## 9.2 小红书工作台

目标状态：

- 更少直接依赖超级 service
- 通过能力层组合原创、二创、视频、发布能力
- 引入知识空间用于爆文参考、模板参考与内容规则参考

## 9.3 抖音工作台

目标状态：

- 通过能力层组合选题、文案、视频、数字人
- 引入知识空间用于脚本规范、镜头策略、口播规则

## 9.4 公众号工作台

目标状态：

- 继续保留“文章 -> 生图 -> HTML -> 发布”的分阶段工作流
- 接入品牌知识空间与视觉规范知识空间
- 接入品牌 Provider 策略与生图治理策略

## 9.5 设计工作台

目标状态：

- 不再仅依附 `WorksModule`
- 逐步独立为图像生成能力域
- 可接入品牌视觉知识空间

## 10. 蓝图下的技术路线

## 10.1 数据层路线

建议继续以以下组合为主：

- PostgreSQL 主业务库
- Prisma 统一建模
- OSS 统一媒体存储
- Redis 用于缓存、队列和调度
- pgvector 用于知识切片向量检索

## 10.2 工作流路线

建议把工作流层正式提升为平台能力：

- 步骤化定义
- 任务化执行
- 单步诊断
- 步骤级知识引用
- 步骤级 Provider 策略

## 10.3 外挂能力路线

建议采用：

- 主系统承载主数据与权限
- 外挂系统承载问答或特殊执行引擎

适用对象：

- MaxKB
- 未来其他智能体平台
- 未来统一代理服务

## 11. 蓝图的实施原则

未来所有新增模块与新增能力，都必须遵循以下原则。

### 原则一：先建模，后开发

必须先回答：

- 模块边界是什么
- 主实体是什么
- 与 `Brand` 的关系是什么
- 是否需要独立任务类型
- 是否需要独立媒体类型
- 是否需要独立知识空间
- 是否需要独立 Provider 策略

### 原则二：先注册，后接入

必须有统一的：

- 模块注册
- 权限注册
- 路由注册
- 任务类型注册
- 能力包绑定注册

### 原则三：先走底座，后走业务

新增模块不得重复建设：

- 认证
- 任务
- 存储
- Provider 路由
- 知识检索
- 审计

### 原则四：先标准化，后开放扩展

只有统一数据合同和任务合同，才有资格谈“USB 式扩展”。

## 12. 目标蓝图总结

综合当前分析和开源方案借鉴，未来系统蓝图建议定为：

### 核心定位

一个面向多品牌的 AI 全域运营平台，其本质由 5 个中心组成：

1. 品牌上下文中心
2. 内容生产中心
3. 任务与媒体中心
4. 知识与技能中心
5. Provider 与第三方接口治理中心

### 关键变化

从现在的：

- 多工作台 + 超级 service + 配置中心

升级到未来的：

- 平台底座 + 领域能力 + 业务工作台 + 知识长期记忆层 + Provider 治理网关 + 外挂能力引擎

### 最终结论

MaxKB 与 cc-switch 都不应被简单理解成“直接拿来用的模块”。

它们在未来蓝图中的正确角色是：

- `MaxKB`：外挂知识问答与智能体引擎的参考对象
- `cc-switch`：Provider 治理、高可用、技能与 Prompt 管理产品化的参考对象

真正应该落到我们主系统内部的，是：

- 多品牌知识主数据层
- 工作流级知识引用机制
- 平台级 Provider 治理层
- 模块注册与能力包机制

这才是与当前系统主线最一致，也最有长期生命力的融合方式。
