# AI全域运营系统 知识库主数据层设计草案 v1

## 1. 文档目的

本文档用于把知识库方向从“外挂产品评估”进一步推进到“我方系统自己的主数据层设计”，用于：

- 指导知识库域的主对象建模
- 指导知识库与品牌、模块、能力包、工作流的绑定方式
- 指导后续数据库、接口和后台页面设计
- 确保知识库能力逐步接入时不影响现有网站功能运行

## 2. 设计前提

本草案建立在以下前提上：

- 知识库主数据必须掌握在我方系统中
- 外部产品如果要接入，只能作为外挂执行能力或过渡能力
- 知识库域必须服务于多品牌、模块化、能力包化和工作流化
- 第一阶段先建主数据和绑定关系，不直接替换现有业务主流程

## 3. 核心结论

建议把知识库主数据层拆成四层：

1. 容器层：`KnowledgeSpace`
2. 内容层：`KnowledgeDocument`、`KnowledgeChunk`
3. 向量与检索层：`KnowledgeEmbedding`、`KnowledgeRetrievalLog`
4. 绑定与接入层：`KnowledgeBinding`、`KnowledgeSourceSyncTask`

这四层中：

- `KnowledgeSpace` 是聚合入口
- `KnowledgeDocument` 是知识原文档主对象
- `KnowledgeChunk` 是检索颗粒度主对象
- `KnowledgeBinding` 是和模块、能力包、工作流接轨的关键挂点

## 4. 主数据层在系统中的定位

知识库主数据层不直接等于“问答产品”，它在我方系统里承担 3 个角色：

### 4.1 长期记忆层

承载平台、品牌、模块、技能和用户层面的长期资料沉淀。

### 4.2 工作流输入层

允许具体工作流步骤按规则显式引用知识空间，作为生成与检索输入。

### 4.3 挂外部引擎的桥接层

未来无论接 MaxKB、OpenAgent，还是自研检索服务，都通过这层对接，而不是让外挂产品直接掌控品牌和权限主数据。

## 5. 设计原则

### 5.1 主数据归我方系统

品牌归属、权限边界、模块挂载、能力包绑定必须在我方系统可控。

### 5.2 检索与主数据解耦

知识切片、向量化和外挂引擎可以替换，但主数据对象和绑定关系不能漂移到外挂系统。

### 5.3 先旁路，后深入

第一阶段先以知识主数据和绑定能力旁路接入，不替换现有创作链路。

### 5.4 多品牌优先

任何知识对象都必须明确它属于：

- 平台
- 品牌
- 模块
- 用户

## 6. 对象总览

建议引入以下对象：

- `KnowledgeSpace`
- `KnowledgeDocument`
- `KnowledgeChunk`
- `KnowledgeEmbedding`
- `KnowledgeBinding`
- `KnowledgeRetrievalLog`
- `KnowledgeSourceSyncTask`
- `KnowledgeTag`

## 7. 核心对象设计

## 7.1 `KnowledgeSpace`

### 职责

- 作为知识空间顶层容器
- 承担知识权限边界与归属边界
- 作为模块、能力包、工作流引用的主对象

### 建议字段

```ts
export interface KnowledgeSpace {
  id: string;
  spaceKey: string;
  spaceName: string;
  scope: "PLATFORM" | "BRAND" | "MODULE" | "USER";
  ownerBrandId?: string;
  ownerUserId?: string;
  moduleKeys: string[];
  tags: string[];
  description?: string;
  sourceMode: "MANUAL" | "SYNCED" | "HYBRID";
  visibility: "PRIVATE" | "BRAND_SHARED" | "PLATFORM_SHARED";
  status: "DRAFT" | "ACTIVE" | "DISABLED" | "ARCHIVED";
  retrievalConfig?: KnowledgeRetrievalConfig;
  createdAt: string;
  updatedAt: string;
}
```

### 说明

- `scope` 用于明确知识空间归属层级
- `moduleKeys` 用于表达该空间主要服务哪些模块
- `retrievalConfig` 用于放默认检索策略

## 7.2 `KnowledgeDocument`

### 职责

- 记录原始知识文档
- 记录来源、导入方式、解析状态和归属空间

### 建议字段

```ts
export interface KnowledgeDocument {
  id: string;
  spaceId: string;
  documentKey: string;
  title: string;
  sourceType: "FILE" | "URL" | "DOC" | "MARKDOWN" | "FORM" | "API";
  sourceUri?: string;
  mimeType?: string;
  contentText?: string;
  summary?: string;
  language?: string;
  versionTag?: string;
  parseStatus: "PENDING" | "PARSED" | "FAILED";
  syncStatus: "NONE" | "SYNCING" | "SYNCED" | "FAILED";
  tagIds: string[];
  createdBy?: string;
  createdAt: string;
  updatedAt: string;
}
```

## 7.3 `KnowledgeChunk`

### 职责

- 记录检索最小内容块
- 作为向量化和召回的直接对象

### 建议字段

```ts
export interface KnowledgeChunk {
  id: string;
  spaceId: string;
  documentId: string;
  chunkIndex: number;
  content: string;
  tokenCount?: number;
  charCount?: number;
  headingPath?: string[];
  keywords?: string[];
  metadata?: Record<string, unknown>;
  createdAt: string;
  updatedAt: string;
}
```

## 7.4 `KnowledgeEmbedding`

### 职责

- 记录某个 chunk 的向量化结果
- 允许未来切换不同 embedding 模型和向量服务

### 建议字段

```ts
export interface KnowledgeEmbedding {
  id: string;
  chunkId: string;
  embeddingProviderId?: string;
  embeddingModelName?: string;
  vectorDimension?: number;
  vectorStatus: "PENDING" | "READY" | "FAILED";
  checksum?: string;
  createdAt: string;
  updatedAt: string;
}
```

## 7.5 `KnowledgeBinding`

### 职责

- 作为知识空间与业务对象之间的统一绑定关系
- 支撑模块、能力包、Prompt、工作流步骤引用知识

### 建议字段

```ts
export interface KnowledgeBinding {
  id: string;
  knowledgeSpaceId: string;
  bindingType: "MODULE" | "SKILL_PACKAGE" | "PROMPT" | "WORKFLOW_STEP";
  targetId: string;
  targetKey?: string;
  priority: number;
  retrievalMode: "SEMANTIC" | "HYBRID" | "MANUAL";
  isRequired: boolean;
  enabled: boolean;
  createdAt: string;
  updatedAt: string;
}
```

### 说明

- `bindingType + targetId` 构成统一接入协议
- `priority` 用于多个知识空间参与同一步骤时的检索顺序

## 7.6 `KnowledgeRetrievalLog`

### 职责

- 记录一次知识检索请求的输入、命中空间、命中文档与结果
- 为后续效果分析、审计和优化提供依据

### 建议字段

```ts
export interface KnowledgeRetrievalLog {
  id: string;
  taskId?: string;
  workflowStepKey?: string;
  packageId?: string;
  userId?: string;
  brandId?: string;
  queryText: string;
  retrievalMode: "SEMANTIC" | "HYBRID" | "MANUAL";
  hitSpaceIds: string[];
  hitDocumentIds: string[];
  hitChunkIds: string[];
  latencyMs?: number;
  status: "SUCCESS" | "FAILED";
  createdAt: string;
}
```

## 7.7 `KnowledgeSourceSyncTask`

### 职责

- 记录知识来源同步任务
- 为未来接飞书、网页、目录、第三方知识库同步做准备

### 建议字段

```ts
export interface KnowledgeSourceSyncTask {
  id: string;
  spaceId: string;
  sourceType: "FILE_UPLOAD" | "WEB_CRAWL" | "LARK_DOC" | "API_IMPORT" | "EXTERNAL_KB";
  sourceConfig?: Record<string, unknown>;
  syncStatus: "QUEUED" | "RUNNING" | "SUCCESS" | "FAILED";
  lastSyncAt?: string;
  nextSyncAt?: string;
  errorMessage?: string;
  createdAt: string;
  updatedAt: string;
}
```

## 7.8 `KnowledgeTag`

### 职责

- 统一管理文档标签
- 支撑品牌、模块、资料类型等维度筛选

### 建议字段

```ts
export interface KnowledgeTag {
  id: string;
  tagKey: string;
  tagName: string;
  scope: "PLATFORM" | "BRAND";
  ownerBrandId?: string;
  color?: string;
  description?: string;
}
```

## 8. 检索配置模型

建议补充默认检索配置对象：

```ts
export interface KnowledgeRetrievalConfig {
  defaultTopK: number;
  recallMode: "SEMANTIC" | "HYBRID";
  rerankEnabled: boolean;
  rerankModelName?: string;
  chunkSize?: number;
  chunkOverlap?: number;
  retrievalThreshold?: number;
}
```

作用：

- 作为空间级默认检索策略
- 可被工作流步骤或能力包局部覆盖

## 9. 多品牌分层规则

知识库主数据层必须明确支持四级分层：

1. 平台公共知识
2. 品牌公共知识
3. 品牌模块知识
4. 用户私有临时知识

### 9.1 检索优先级建议

默认建议：

1. 用户私有临时知识
2. 品牌模块知识
3. 品牌公共知识
4. 平台公共知识

### 9.2 权限规则建议

- 平台空间只能由平台管理员维护
- 品牌空间只能由品牌管理员和授权用户维护
- 用户私有空间默认不共享
- 模块级空间在品牌边界内共享，不跨品牌复用主数据

## 10. 与现有系统对象的关系

## 10.1 与 `Brand`

- `KnowledgeSpace.ownerBrandId` 绑定品牌归属
- 品牌切换时，默认检索范围跟随品牌上下文变化

## 10.2 与 `ModuleDefinition`

- 模块可挂载一个或多个知识空间
- 模块默认知识空间通过 `KnowledgeBinding(bindingType = MODULE)` 建立

## 10.3 与 `SkillPackage`

- 能力包通过 `KnowledgeBinding(bindingType = SKILL_PACKAGE)` 绑定默认知识空间
- 让能力包成为知识检索的稳定挂点

## 10.4 与工作流步骤

- 工作流步骤通过 `KnowledgeBinding(bindingType = WORKFLOW_STEP)` 指定本步骤可用知识空间
- 便于文章生成、生图说明、HTML 规范等步骤分开引用不同知识

## 10.5 与 Prompt

- Prompt 可选绑定知识空间
- 用于把“提示词模板”和“知识检索范围”解耦

## 11. 与外挂知识引擎的边界

无论后续接 MaxKB、OpenAgent 还是其他产品，都建议遵循：

- 主数据在我方系统
- 外挂引擎只做导入、检索、问答或 Agent 执行
- 外挂引擎不直接承担品牌权限主数据
- 外挂引擎不直接定义模块绑定规则

建议通过桥接层对象表达：

- `externalProviderType`
- `externalSpaceRef`
- `externalDocumentRef`

这样后面替换外挂产品时，不需要重建品牌和模块关系。

## 12. 第一阶段最小落地范围

第一阶段建议只落以下对象：

### P0

- `KnowledgeSpace`
- `KnowledgeDocument`
- `KnowledgeBinding`

### P1

- `KnowledgeChunk`
- `KnowledgeEmbedding`
- `KnowledgeTag`

### P2

- `KnowledgeRetrievalLog`
- `KnowledgeSourceSyncTask`

## 13. 第一阶段数据库落表建议

建议优先表：

- `knowledge_spaces`
- `knowledge_documents`
- `knowledge_bindings`

后续扩展表：

- `knowledge_chunks`
- `knowledge_embeddings`
- `knowledge_tags`
- `knowledge_retrieval_logs`
- `knowledge_source_sync_tasks`

## 14. 第一阶段接口建议

建议先补以下接口：

- `GET /api/admin/knowledge-spaces`
- `POST /api/admin/knowledge-spaces`
- `GET /api/admin/knowledge-spaces/:spaceId`
- `GET /api/admin/knowledge-spaces/:spaceId/documents`
- `POST /api/admin/knowledge-bindings`
- `GET /api/admin/knowledge-bindings`

第一阶段不急着做：

- 对外问答接口
- 复杂检索调优接口
- 多引擎路由接口

## 15. 第一阶段页面建议

建议先做后台管理侧页面，不动现有业务页面：

- 知识空间列表页
- 知识空间详情页
- 文档列表页
- 绑定关系页

这样可以先把底座搭起来，而不破坏现有前台创作流程。

## 16. 对现有功能零影响的接入方式

为了满足“绝对不要影响现有网站功能运行”，建议：

- 第一步只新增知识库后台管理能力
- 第二步只允许能力包和模块挂默认知识空间
- 第三步再在个别新工作流步骤中灰度接入知识检索
- 现有已上线流程默认不强依赖知识库返回结果

这样即使知识库域暂时不完善，也不会阻断当前业务链路。

## 17. 后续最值得继续补的文档

在本草案之后，最值得继续补的是：

- 知识空间数据结构草案
- 知识库后台页面字段清单
- 知识绑定接口草案
- 知识库与 SkillPackage 关系表草案

## 18. 最终结论

知识库主数据层的关键，不是先选哪个外挂产品，而是先把以下东西掌握在我方系统中：

- 空间归属
- 文档归属
- 品牌边界
- 模块绑定
- 能力包绑定
- 工作流步骤绑定

只要这套主数据层先立起来，后续无论接 MaxKB、OpenAgent 还是自研检索引擎，我们都能保持平台化和商业化主动权，同时不影响现有网站运行。
