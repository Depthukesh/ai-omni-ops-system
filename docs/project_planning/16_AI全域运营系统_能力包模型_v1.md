# AI全域运营系统能力包模型 v1

## 1. 文档目的

本文档用于定义统一技能中心背后的底层模型，也就是“能力包模型”。

目标是回答：

- 技能中心到底管理什么
- Skill 与 Prompt 的关系是什么
- references、scripts、knowledge、Provider 如何与技能绑定
- 品牌覆盖与用户覆盖应该落在哪一层

## 2. 核心结论

建议引入统一聚合根：

- `SkillPackage`

这个对象不是简单等于 Skill，而是一个完整能力单元的聚合根。

它至少要承载：

- 能力定义
- 提示词资产
- 参考资料资产
- 脚本资产
- 知识绑定
- Provider 绑定
- 版本状态

## 3. 为什么需要能力包模型

如果没有能力包模型，当前系统会长期处于以下状态：

- Skill 是一块
- Prompt 是一块
- references 是一块
- scripts 是一块
- knowledge 未来又是一块
- Provider 策略还是一块

这会导致：

- 绑定关系分散
- 配置链路断裂
- 版本关系不清楚
- 品牌覆盖和用户覆盖难统一

所以未来必须把它们收敛到一个统一对象关系中。

## 4. 能力包模型的层次

## 4.1 聚合根

- `SkillPackage`

## 4.2 子对象

- `Skill`
- `PromptAsset`
- `ReferenceAsset`
- `ScriptAsset`
- `KnowledgeBinding`
- `ProviderBinding`
- `SkillPackageVersion`

## 4.3 外部关联对象

- `Brand`
- `User`
- `ModuleDefinition`
- `WorkflowStepDefinition`

## 5. 各对象职责

## 5.1 `SkillPackage`

职责：

- 作为能力包聚合根
- 作为模块与工作流绑定的主对象
- 作为版本与状态管理主对象

建议字段：

- `packageKey`
- `packageName`
- `packageStatus`
- `moduleScope`
- `description`
- `defaultVersionId`
- `isBrandOverridable`
- `isUserOverridable`

## 5.2 `Skill`

职责：

- 表示能力定义本身
- 描述这个能力做什么、输出什么、适用于哪里

建议字段：

- `skillKey`
- `skillName`
- `skillType`
- `inputContract`
- `outputContract`
- `runtimeHints`

## 5.3 `PromptAsset`

职责：

- 表示提示词资产
- 支撑多版本、激活、回滚、差异对比

建议字段：

- `promptKey`
- `promptType`
- `content`
- `version`
- `isActive`
- `changeNote`

## 5.4 `ReferenceAsset`

职责：

- 表示 references 资料
- 为技能提供参考背景与操作约束

建议字段：

- `referenceKey`
- `referenceTitle`
- `sourceType`
- `sourcePath`
- `usageNote`

## 5.5 `ScriptAsset`

职责：

- 表示 scripts 资产
- 为技能执行提供脚本与参数约束

建议字段：

- `scriptKey`
- `scriptName`
- `scriptType`
- `scriptContent`
- `parameterSchema`

## 5.6 `KnowledgeBinding`

职责：

- 表示技能与知识空间的绑定关系
- 描述技能检索哪些知识、按什么优先级检索

建议字段：

- `knowledgeSpaceKey`
- `bindingScope`
- `retrievalPriority`
- `retrievalRule`

## 5.7 `ProviderBinding`

职责：

- 表示技能与 Provider 策略的绑定关系
- 决定默认模型、fallback、品牌覆盖能力

建议字段：

- `providerPolicyKey`
- `bindingMode`
- `fallbackPolicy`
- `modelWhitelist`

## 5.8 `SkillPackageVersion`

职责：

- 表示能力包版本
- 串起 Skill、Prompt、references、scripts、knowledge、Provider 的版本快照

建议字段：

- `versionKey`
- `versionNumber`
- `changeSummary`
- `isActive`
- `publishedAt`

## 6. Skill 与 Prompt 的关系模型

建议按以下场景定义关系：

### 一对一

一个 Skill 只有一个 PromptAsset。

适用于：

- 简单单步技能

### 一对多

一个 Skill 对应多个 PromptAsset。

适用于：

- 主生成 Prompt
- 摘要 Prompt
- 标题优化 Prompt
- 格式整理 Prompt

### 多对一

多个 Skill 复用同一个 PromptAsset。

适用于：

- 通用风格 Prompt
- 通用结构化输出 Prompt

因此，Skill 与 Prompt 不应被写死为一一对应关系。

## 7. 品牌覆盖与用户覆盖应落在哪一层

建议分层如下：

### 平台默认层

- 平台默认 SkillPackage
- 平台默认 PromptAsset
- 平台默认 ProviderBinding

### 品牌覆盖层

- 品牌覆盖 Prompt
- 品牌覆盖 Provider
- 品牌覆盖知识绑定

### 用户覆盖层

- 用户级 Prompt 偏好
- 用户级 Provider 偏好
- 用户级使用偏好

原则是：

- 平台定义默认
- 品牌定义业务差异
- 用户定义个人偏好

## 8. 能力包与模块的关系

一个模块可以绑定多个能力包。

例如公众号工作台可以绑定：

- `wechat-article-generator`
- `wechat-image-designer`
- `wechat-html-renderer`
- `wechat-api-publisher`

因此关系是：

- 一个模块 -> 多个能力包
- 一个能力包 -> 可被多个模块复用

## 9. 能力包与工作流步骤的关系

一个能力包可以绑定到一个或多个工作流步骤。

例如：

- 文章生成步骤绑定 `wechat-article-generator`
- 生图步骤绑定 `wechat-image-designer`
- HTML 步骤绑定 `wechat-html-renderer`

这意味着能力包不仅是“配置对象”，还是工作流装配对象。

## 11. 最终结论

能力包模型的价值在于：

- 让统一技能中心有底层模型支撑
- 让知识库和 Provider 治理有稳定挂点
- 让品牌覆盖、用户覆盖和版本管理都能落到统一对象关系中

如果没有能力包模型，后续系统还是会回到“对象很多、入口很多、关系分散”的老路。
