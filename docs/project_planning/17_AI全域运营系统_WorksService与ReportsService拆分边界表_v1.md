# AI全域运营系统 WorksService 与 ReportsService 拆分边界表 v1

## 1. 文档目的

本文档用于把第一阶段中的“超级 service 拆分路线”进一步具体化，回答以下问题：

- `WorksService` 和 `ReportsService` 现在为什么过重
- 哪些职责适合拆成领域能力
- 哪些职责应暂时留在编排层
- 建议按什么顺序拆

## 2. 核心拆分原则

建议遵循以下原则：

1. 先拆边界清晰的能力  
2. 先拆复用性高的能力  
3. 先拆对业务流程影响最小的能力  
4. 保留“工作流编排”在上层，不要一开始把所有事情拆碎  

## 3. `WorksService` 现状判断

`WorksService` 当前通常会混合以下几类职责：

- 文案生成
- 图片生成
- 视频生成
- HTML 渲染
- 发布动作
- 工作流步骤推进
- 任务创建与状态更新
- 媒体落库与关联

问题在于：

- 既有领域能力
- 又有编排逻辑
- 又有任务与媒体横切处理

因此它更像“总控中心”，而不是单一服务。

## 4. `WorksService` 拆分边界表

| 当前职责 | 推荐归属 | 是否第一阶段确认拆分 | 说明 |
|---|---|---:|---|
| 文案生成 | `copy-domain` | 否 | 重要但通常与业务编排耦合较深，建议第二批 |
| 图片生成 | `image-domain` | 是 | 边界较清晰，且可被多个模块复用 |
| 视频生成 | `video-domain` | 否 | 链路复杂、依赖多，建议第三批 |
| HTML 渲染 | `html-render-domain` | 是 | 输入输出边界最清晰，优先拆分 |
| 发布动作 | `publish-domain` | 是 | 发布目标和调用链可独立治理 |
| 工作流步骤推进 | `workflow-orchestration` | 否 | 应保留在上层编排，先不急拆到过细 |
| 任务创建与状态更新 | `task-core` | 否 | 属于平台底座，应继续统一收口 |
| 媒体落库与关联 | `media-core` | 否 | 属于平台横切能力，不应分散到各域 |

## 5. `WorksService` 建议拆分顺序

### 第一批

- `html-render-domain`
- `publish-domain`
- `image-domain`

原因：

- 这三块输入输出合同更清晰
- 对业务编排侵入较小
- 多工作台复用价值较高

### 第二批

- `copy-domain`
- `workflow-orchestration`

原因：

- 文案生成往往与上下文编排深度耦合
- 工作流推进本身属于更上层的编排逻辑，需要谨慎抽离

### 第三批

- `video-domain`

原因：

- 视频能力链路最长
- 依赖第三方平台与媒体处理更多
- 风险最高，建议最后拆

## 6. `ReportsService` 现状判断

`ReportsService` 当前通常会混合以下几类职责：

- 数据归集后的洞察抽取
- 报告生成
- 营销规划
- 策略推导
- 品牌建议输出

问题在于：

- 报告生成和策略规划被放在同一个超级 service 中
- 模块边界与复用边界不清晰

## 7. `ReportsService` 拆分边界表

| 当前职责 | 推荐归属 | 是否第一阶段确认拆分 | 说明 |
|---|---|---:|---|
| 洞察抽取 | `insight-domain` | 是 | 适合作为通用分析能力沉淀 |
| 报告生成 | `report-generation-domain` | 是 | 输出形态清晰，易先抽离 |
| 品牌策略推导 | `strategy-domain` | 否 | 与业务语境耦合较深，建议第二批 |
| 营销规划 | `campaign-domain` | 否 | 与品牌上下文和业务目标耦合更深 |
| 原始数据组装 | `collector-domain` / 编排层 | 否 | 更像前置输入准备，不宜盲拆 |

## 8. `ReportsService` 建议拆分顺序

### 第一批

- `report-generation-domain`
- `insight-domain`

### 第二批

- `strategy-domain`
- `campaign-domain`

原因：

- 先把更像“通用输出能力”的部分拆出来
- 再处理高度依赖业务语境的规划与策略能力

## 9. 哪些职责不要误拆

以下能力不建议直接挂到 `WorksService` 或 `ReportsService` 的拆分子域中：

- 任务状态治理
- 媒体主数据治理
- 权限控制
- 品牌上下文解析
- Provider 调用治理

这些能力更适合继续留在平台底座层：

- `task-core`
- `media-core`
- `permission-core`
- `brand-core`
- `provider-core`

## 10. 第一阶段要交付到什么程度

第一阶段不要求直接重构代码，但至少应形成：

- [ ] 两大 service 的职责清单
- [ ] 每项职责的推荐归属
- [ ] 哪些属于领域能力、哪些属于编排层、哪些属于平台底座
- [ ] 分批拆分顺序
- [ ] 风险提示

## 11. 第一阶段之后如何进入代码拆分

建议进入第二轮时，按以下方式推进：

1. 先抽清晰域的接口合同  
2. 再把调用入口改为通过领域能力层  
3. 再逐步缩小超级 service 的职责范围  

不要直接大规模删改超级 service。

## 12. 最终结论

`WorksService` 和 `ReportsService` 的拆分，核心不是“拆得越多越好”，而是：

> 把真正可复用、边界清晰的能力抽出来，把仍需掌握全局上下文的编排逻辑先留在上层。

只有这样拆，才能既降低耦合，又不把系统拆散。
