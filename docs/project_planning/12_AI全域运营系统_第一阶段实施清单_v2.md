# AI全域运营系统第一阶段实施清单 v2

## 1. 文档定位

本文档是在 `v1` 基础上的进一步深化版本，目标不是重复第一阶段方向，而是把第一阶段继续下钻成：

- 更接近真实目录与真实系统现状
- 更接近项目可执行任务
- 更适合后续拆成真正的开发任务单

与 `v1` 相比，`v2` 重点补强 4 件事：

1. 把当前目录现状与主仓收束问题写实  
2. 把模块注册机制从概念细化为可落字段  
3. 把统一技能中心从理念细化为页面结构与数据关系  
4. 把 `WorksService` / `ReportsService` 的拆分从方向细化为拆分顺序  

## 2. 第一阶段的真实现状基线

结合目前 `规划文档` 目录与已形成文档，第一阶段启动前，至少要承认以下现实：

- `ai-omni-ops-system` 是目标主仓
- `规划文档` 目录已经承载了阶段性规划文档
- `规划文档` 中存在 `备份` 目录
- `规划文档` 中也放入了 `2026-06-06-system-architecture-analysis-report.md/html` 的副本
- 当前蓝图文档已经形成 `08 / 09 / 10 / 11`

这意味着第一阶段不是从零开始，而是从“已有规划成果已堆起来，但入口和边界还未完全收束”的状态继续推进。

## 3. 第一阶段的目标重述

第一阶段的本质目标不是开发某个新业务模块，而是完成以下 5 个平台前置条件：

1. 主仓边界清晰  
2. 文档入口清晰  
3. 模块注册标准清晰  
4. 能力包结构清晰  
5. 统一技能中心方案清晰  

只有这 5 件事清晰之后，第二阶段的知识库主数据、第三阶段的 Provider 治理才不会返工。

## 4. 第一阶段的 5 条工作线

## 4.2 工作线 B：模块注册机制 v1

### 4.2.1 目标

建立统一模块接入协议，让未来新增模块不再靠临时口头约定接入。

### 4.2.2 推荐对象

建议定义统一对象：`ModuleDefinition`

### 4.2.3 推荐字段

基础字段：

- `moduleKey`
- `moduleName`
- `moduleType`
- `moduleStatus`
- `entryRoute`
- `icon`
- `sortOrder`

权限与开关字段：

- `requiredPermissions`
- `featureFlags`
- `isPlatformVisible`
- `isBrandVisible`
- `isAdminVisible`

依赖字段：

- `requiredCapabilities`
- `requiredProviders`
- `requiredTables`
- `requiredStorages`

执行字段：

- `taskTypes`
- `mediaTypes`
- `workflowTypes`
- `publishTargets`

装配字段：

- `defaultSkillPackages`
- `defaultKnowledgeSpaces`
- `defaultProviderPolicies`

### 4.2.4 首批落图对象

第一批必须先统一描述以下 5 个工作台：

- 品牌增长工作台
- 小红书工作台
- 抖音工作台
- 公众号工作台
- 设计工作台

### 4.2.5 第一阶段要交付到什么程度

本阶段不要求马上做完整模块注册后台，只需要做到：

- [ ] 形成统一字段字典

- [ ] 形成新模块接入模板
- [ ] 明确“哪些字段是必填，哪些字段是扩展项”

### 4.2.6 建议输出件

## 4.3 工作线 C：能力包机制 v1

### 4.3.1 目标

把当前分散的 Skill、Prompt、references、scripts、知识绑定、Provider 策略统一到能力包视角下。

- 一个能力单元
- 一组依赖资产
- 一套执行策略
- 一个模块可绑定的能力包

### 4.3.3 推荐结构

聚合根：

- `SkillPackage`

子对象：

- `PromptAsset`
- `ReferenceAsset`
- `ScriptAsset`
- `KnowledgeBinding`
- `ProviderBinding`
- `SkillPackageVersion`

- 技能
- Prompt
- references
- scripts
- 品牌覆盖
- 用户覆盖

- [ ] 明确品牌覆盖和用户覆盖落在哪一层

### 4.3.6 建议输出件

## 4.5 工作线 E：超级 service 拆分路线 v1

### 4.5.1 目标

避免在没有清晰边界的情况下盲目拆服务，先把职责和顺序定清楚。

### 4.5.2 `WorksService` 的建议拆分顺序

建议按“最容易独立、最能降低耦合”的顺序拆：

第一批：

- `html-render-domain`
- `publish-domain`
- `image-domain`

第二批：

- `copy-domain`
- `workflow-orchestration`

第三批：

- `video-domain`

原因：

- HTML 渲染和发布边界天然更清晰
- 图像生成也更容易从内容编排中拆出来
- 文案和工作流编排通常耦合更深，应稍后拆
- 视频链路复杂度最高，建议放后

### 4.5.3 `ReportsService` 的建议拆分顺序

第一批：

- `report-generation-domain`
- `insight-domain`

第二批：

- `strategy-domain`
- `campaign-domain`

原因：

- 报告生成与洞察抽取更容易先抽成独立能力
- 战略与营销规划通常与更多业务上下文耦合，建议后拆

### 4.5.4 第一阶段要交付到什么程度

- [ ] 列出两大 service 的职责清单
- [ ] 标注哪些职责属于横切能力
- [ ] 标注哪些职责仍留在编排层
- [ ] 给出分三批拆分顺序
- [ ] 给出拆分风险说明

### 4.5.5 建议输出件

- `WorksService_职责拆分图_v1.md`
- `ReportsService_职责拆分图_v1.md`
- `超级Service拆分顺序建议_v1.md`

## 8. 第一阶段最终结论

如果说 `v1` 解决的是“第一阶段做什么”，那么 `v2` 解决的是“第一阶段先把哪些规则钉死，以及每项规则要产出到什么程度”。

第一阶段的最佳推进方式不是立即写代码，而是先把以下 4 个产物做扎实：

1. 模块注册规范  
2. 能力包模型  
3. 统一技能中心方案  
4. 超级 service 拆分路线  

这 4 个产物一旦稳定，后面的知识库主数据、Provider 治理和外挂能力路线就会顺很多，也更不容易返工。
