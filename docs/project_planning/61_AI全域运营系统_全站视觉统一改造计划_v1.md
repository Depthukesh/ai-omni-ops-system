# AI全域运营系统 全站视觉统一改造计划 v1

## 1. 文档目的

本文档用于明确下一阶段“全站页面视觉统一”的执行方案，目标不是把首页的营销排版机械复制到每个页面，而是把首页已经建立起来的品牌气质、设计语言和交互标准，系统性扩展到整个网站。

本文档主要回答 5 个问题：

- 全站视觉统一的目标到底是什么
- 哪些页面应该先改，哪些页面后改
- 哪些地方要抽成公共设计系统，而不是逐页硬改
- 如何在不破坏现有业务功能的前提下推进
- 每个阶段完成后用什么标准判断是否达标

## 2. 设计判断

结合当前首页、现有业务页面结构和 `design-taste-frontend` 的规则，我对本次任务的设计判断是：

- 这是一次“已有项目的系统性视觉升级”，不是从零重写网站
- 首页属于营销型页面，应该保持更强的品牌表达、叙事感和视觉张力
- 工作台、个人中心、后台管理属于产品型页面，应该继承首页的品牌调性，但不能照搬首页的大段动效和营销式排版
- 本次统一的重点应该是“设计系统一致”，不是“所有页面长得一样”

因此，本次统一的正确方向是：

- 统一品牌色、字体、圆角、边框、阴影、按钮、表单、导航和空态语言
- 统一页面壳层、区块标题、内容容器、卡片层级和交互反馈
- 区分营销页、认证页、工作台页、管理页四类页面的视觉密度

## 3. 当前现状判断

根据当前代码结构，前端已经有一定的样式基座，但还没有形成真正可复用的统一设计系统。

### 3.1 当前已经具备

- 主站已经有全局样式入口：`apps/web/src/styles/globals.css`
- 根布局和 dashboard 布局已经是统一入口：
  - `apps/web/src/app/layout.tsx`
  - `apps/web/src/app/(dashboard)/layout.tsx`
- 个人中心已有二级统一布局：
  - `apps/web/src/app/(dashboard)/personal-center/layout.tsx`
- 多个页面已经在复用一批通用语义类，例如：
  - `page-shell`
  - `dashboard-shell`
  - `panel`
  - `metric-card`
  - `primary-button`
  - `secondary-button`
  - `field`

### 3.2 当前存在的问题

- 官网首页目前仍是特殊接入方式，和主站其他页面不是同一套实现逻辑
- `globals.css` 承载内容过多，设计 token、布局规则、组件样式和业务样式混在一起
- 登录页、注册页、帮助页、手机接力页等存在较多独立样式或内联样式
- 品牌增长、小红书、抖音、公众号、更多功能等工作台壳层风格不够统一
- 个人中心和交易页的层级、标题、容器、操作区还没有形成稳定的视觉协议
- 后台管理页信息密度高，但当前品牌感和首页割裂较强

### 3.3 当前最重要的现实约束

- 当前项目主站并不是标准 Tailwind 工程，不能直接按首页的 Tailwind CDN 方式扩散到全站
- 当前网站已有大量业务页面，不能一次性大改所有页面，否则风险过高
- 本次改造必须优先通过公共层改造解决问题，而不是逐页写大量特例样式

## 4. 本次统一的总目标

本次改造的最终目标不是“页面全部重做”，而是建立一套可以长期持续扩展的站内视觉系统。

具体目标如下：

- 建立全站统一的设计 token
- 建立全站统一的页面壳层规范
- 建立全站统一的常用 UI 基元
- 统一首页、认证页、工作台、个人中心、后台的品牌语言
- 清理明显割裂的孤岛样式和高风险内联样式
- 为后续新页面开发提供默认样式基线

## 5. 统一原则

### 5.1 统一的是“语言”，不是“模板”

- 首页保留更强的叙事感、动态感和视觉冲击
- 工作台页面采用更克制的同品牌语言，不使用过量营销动效
- 后台管理保持高可读、高密度，但在色彩、边框、状态和按钮上与前台统一

### 5.2 优先抽公共层，不先做散点修补

- 先统一 token、容器、导航、按钮、表单、卡片、状态组件
- 再把这些公共能力落到各类页面
- 避免某个页面单独做得很好看，但其他页面无法复用

### 5.3 先改壳层，再改页面内容区

- 先统一根布局、导航、页面头部、区块标题、卡片层级
- 再进入各业务工作区内部的区块内容升级
- 这样能用最小代价先提升整站一致性

### 5.4 视觉升级不能影响现有链路

- 登录、注册、支付、任务、后台管理等核心路径优先保证稳定
- 样式改造过程中不随意改接口、不随意改页面路由、不随意改核心交互逻辑

## 6. 页面分组与改造优先级

我建议按下面 6 组页面推进。

### 第一组：首页与外部入口

目标：先把品牌外观基线彻底稳定。

包含页面：

- `/`
- `/help/publisher`
- `/help/xhs-draft-publisher`
- `/help/douyin-publisher`
- `/help/wechat-channel-publisher`
- `/publish/mobile/[token]`

优先级说明：

- 首页是全站品牌基线，必须先稳定
- 帮助页和手机接力页属于高曝光外部入口，不能继续风格割裂

### 第二组：认证入口

目标：让用户从首页进入登录、注册、后台登录时，品牌感觉不跳变。

包含页面：

- `/login`
- `/register`
- `/admin/login`

优先级说明：

- 认证页是首页之后的第一触点
- 这组页面结构相对集中，适合优先抽出统一 AuthShell

### 第三组：全局工作台壳层

目标：统一进入产品后的主导航、页头、容器、信息层级和操作区。

包含公共壳层：

- `apps/web/src/app/(dashboard)/layout.tsx`
- `apps/web/src/app/(dashboard)/personal-center/layout.tsx`
- 各业务 workspace shell

优先级说明：

- 只要壳层统一，整站一致性感知会立刻提升一大截
- 这是最值得先做的“杠杆层”

### 第四组：核心业务工作台

目标：统一四大主工作台的区块样式、导航模式、空态、卡片和表单。

包含页面：

- `/brand-growth`
- `/xiaohongshu`
- `/douyin`
- `/wechat`
- `/more-features/design`

优先级说明：

- 这是系统的核心生产页面
- 页面数量多，但结构高度相似，适合做共用 Workspace 模式

### 第五组：个人中心与交易页

目标：让“账户、订单、作品、任务、技能、团队、第三方配置”形成一致的二级产品体验。

包含页面：

- `/personal-center`
- `/personal-center/tasks`
- `/personal-center/orders`
- `/personal-center/works`
- `/personal-center/skills`
- `/personal-center/security`
- `/personal-center/team`
- `/personal-center/invites`
- `/personal-center/third-party-platforms`
- `/membership-purchase`
- `/points-purchase`
- `/orders/[id]`

优先级说明：

- 这组页面更偏产品管理面板
- 需要在信息密度和品牌感之间找到平衡

### 第六组：后台管理页

目标：在不牺牲效率的前提下，让后台风格与前台品牌体系接轨。

包含页面：

- `/admin`

优先级说明：

- 后台是信息密度最高、复杂度最高的一组
- 适合最后在已有统一组件和布局能力基础上做收口

## 7. 技术实施策略

### 7.1 不建议继续放大全局大文件

当前 `globals.css` 已经承担过多职责。下一步建议把样式体系拆成可维护结构，例如：

- `tokens.css`
- `base.css`
- `layout.css`
- `components.css`
- `workspace.css`
- `utilities.css`

如果为了控制改动风险，也可以先维持单入口引入，但内部按模块分段整理。

### 7.2 先建立站内设计 token

建议先正式定义一套全站可复用 token，包括：

- 品牌背景层级
- 文字层级
- 主强调色与弱强调色
- 边框与分割线颜色
- 卡片背景和浮层背景
- 阴影与发光规则
- 圆角等级
- 按钮高度与尺寸
- 表单高度与状态色
- 页面最大宽度与区块间距

### 7.3 抽统一 UI 基元

建议先沉淀一批高频 UI 基元，避免每个页面重复手写：

- `PageHeader`
- `SectionHeader`
- `Panel`
- `MetricCard`
- `StatusPill`
- `PrimaryButton`
- `SecondaryButton`
- `FormField`
- `ActionBar`
- `EmptyState`
- `WorkspaceNav`
- `WorkspaceSection`

### 7.4 抽统一壳层

建议新增或收口以下壳层能力：

- `MarketingShell`
- `AuthShell`
- `DashboardShell`
- `WorkspaceShell`
- `AdminShell`

这样首页、认证页、工作台、后台就不是靠“页面各自长样子”，而是靠统一壳层约束产出。

### 7.5 清理孤岛样式

优先清理以下高风险孤岛：

- 首页临时注入式样式
- 手机接力页内联样式
- 认证页零散样式
- 帮助页与主站风格割裂的部分

## 8. 分阶段执行计划

## 第一阶段：建立视觉基线

目标：

- 把首页视觉语言沉淀成全站设计规则
- 产出 token、组件、壳层的第一版基线

输出物：

- 全站视觉规范
- CSS token 第一版
- 基础组件第一版
- 首页正式站内化方案

完成标准：

- 不再依赖临时注入方案来维持首页效果
- 认证页可以直接使用同一套基线能力

## 第二阶段：统一壳层与认证体验

目标：

- 统一顶层导航、页面头部、内容容器和认证体验

范围：

- `/`
- `/login`
- `/register`
- `/admin/login`
- dashboard 顶层 layout

完成标准：

- 用户从首页进入登录再进入系统，品牌语气不跳变
- 导航、按钮、表单、标题、卡片层级统一

## 第三阶段：统一工作台骨架

目标：

- 建立统一的 WorkspaceShell
- 收口品牌增长、小红书、抖音、公众号、更多功能的公共结构

范围：

- `/brand-growth`
- `/xiaohongshu`
- `/douyin`
- `/wechat`
- `/more-features/design`

完成标准：

- 不同工作台虽然内容不同，但页头、分区、状态条、空态、操作区保持统一
- 新工作台后续可以复用同一套骨架

## 第四阶段：统一个人中心与交易页

目标：

- 让个人中心子页形成统一的二级产品区体验

范围：

- 个人中心及全部子页
- 会员购买、积分购买、订单详情

完成标准：

- 二级导航、页面头、详情区、操作区、表格/卡片风格统一

## 第五阶段：统一后台管理页

目标：

- 让后台管理页接入同一品牌系统，但保持高信息密度和高可用性

范围：

- `/admin`

完成标准：

- 后台与前台在色彩、组件、状态和交互反馈上是一家系统
- 不牺牲后台效率，不把后台做成营销页

## 第六阶段：收尾与验收

目标：

- 统一处理边角页、帮助页、异常页、空态、加载态、错误态

范围：

- 所有剩余外部页、帮助页、异常场景

完成标准：

- 全站视觉统一不再只覆盖主链路，而是覆盖完整产品闭环

## 9. 我准备怎么做

如果按这份计划正式开工，我会按下面的工作方式推进。

### 9.1 先做审计，不直接开改

我会先把 `apps/web/src/app` 的页面和壳层做一次完整盘点，输出：

- 页面清单
- 页面分组
- 公共壳层清单
- 孤岛样式清单
- 高复用组件清单

### 9.2 先做设计系统层

我不会先随机挑某个页面美化，而是先做：

- token
- 基础组件
- 壳层组件
- 页面结构规范

### 9.3 再按页面组推进

推进顺序建议固定为：

1. 首页与认证
2. dashboard 壳层
3. 四大工作台
4. 个人中心与交易
5. 后台
6. 帮助页与边角页

### 9.4 每阶段都做验收与文档回写

每完成一个阶段，都同步做：

- 代码提交
- `docs/changes/*.md` 记录
- 必要的 `docs/site-map.md` 更新
- 阶段验收说明

## 10. 风险与控制方案

### 风险 1：首页风格强，后台页面信息密度高，容易硬套失败

控制方式：

- 只统一设计语言，不强行统一排版结构
- 将页面按“营销 / 认证 / 产品 / 管理”四类处理

### 风险 2：页面很多，逐页手改成本高

控制方式：

- 先改 token、壳层、组件
- 再让页面迁移到公共层

### 风险 3：样式升级影响现有业务交互

控制方式：

- 只在样式层、结构层做改造
- 关键流程逐阶段验证

### 风险 4：首页目前仍有特殊实现，继续叠补丁会越来越乱

控制方式：

- 首页后续要正式站内化
- 不继续扩大临时注入方案的使用范围

## 11. 验收标准

当整套改造完成后，我认为至少要达到以下标准：

- 用户从首页进入登录，再进入系统，品牌语言连续
- 前台工作台、个人中心、后台管理不再像三个产品
- 按钮、表单、卡片、标题、状态、空态有统一规则
- 新页面开发时，不需要再临时发明一套风格
- 样式不再大量依赖内联写法和页面级特例

## 12. 当前建议的下一步

如果按这份计划继续，我建议下一步正式进入“第一阶段：建立视觉基线”，先做下面 4 件事：

1. 盘点 `apps/web/src/app` 全部页面与样式孤岛
2. 定义全站视觉 token 与页面分层规则
3. 抽出第一批公共 UI 基元与壳层
4. 先把首页、登录、注册、dashboard 顶层 layout 统一为同一语言

这 4 件事完成后，后面的页面改造就会从“逐页修饰”，变成“按系统迁移”。
