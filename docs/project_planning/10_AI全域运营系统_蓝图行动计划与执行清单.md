# AI全域运营系统蓝图行动计划与执行清单

## 1. 文档目的

本文档是《融合知识库与接口治理的目标蓝图规划》的配套行动文档，用于回答三个问题：

1. 从现在到目标蓝图，中间应该怎么走  
2. 每个阶段应该做哪些事  
3. 每项工作在开工前与交付前要检查什么  

这份文档暂时放在 `规划文档` 中，用于方案评审、排优先级和控制节奏；待方向确认后，再同步沉淀到项目 `docs` 中。

## 2. 行动计划总原则

整个行动计划遵循以下原则：

### 2.1 不推倒重来

以现有系统为基础渐进演进，而不是重构式重写。

### 2.2 先底座，后扩展

优先建设平台底座能力，再扩展新模块。

### 2.3 先治理超级模块，再做大规模新增功能

如果不先治理 `WorksService` 和 `ReportsService`，后面加知识库与接口治理会进一步放大复杂度。

### 2.4 先内部统一，再外挂集成

先把主系统的数据、权限、品牌、任务和能力包机制做稳，再决定是否接外挂系统，例如 MaxKB。

### 2.5 每个阶段都必须可交付、可暂停、可回退

每个阶段都应形成独立可验收成果，而不是只有“大而全”的最终目标。

## 3. 建议分期

建议把蓝图拆成 5 个阶段。

### Phase 0：基线收束期

目标：

- 收束主仓与文档基线
- 继续清理过渡态
- 为后面知识库和接口治理做准备

### Phase 1：平台底座治理期

目标：

- 梳理模块注册规则
- 梳理能力包机制
- 治理超级 service

### Phase 2：知识库主数据落地期

目标：

- 在主系统内建设正式知识库域
- 先把知识作为“主数据”和“工作流输入”接进系统

### Phase 3：Provider 治理升级期

目标：

- 把 Provider 配置中心升级为治理层
- 建立健康检测、诊断、用量、熔断、fallback 体系

### Phase 4：外挂能力引擎接入验证期

目标：

- 按需验证 MaxKB 或其他外挂引擎
- 用外挂能力补强问答、Agent、复杂流程能力

## 4. 分阶段行动计划

## 4.1 Phase 0：基线收束期

### 目标

- 明确唯一主仓
- 明确哪些目录属于备份
- 明确哪些文档是正式蓝图来源
- 继续清理 mock fallback
- 继续收敛技能与 Prompt 的数据库真源

### 产出

- 主仓确认说明
- 备份仓说明
- 文档索引更新
- 过渡态清单

### 本阶段任务

1. 明确 `ai-omni-ops-system` 为唯一主仓  
2. 对平行仓与备份仓加只读说明  
3. 盘点剩余 mock fallback 与本地 fallback  
4. 盘点尚未完全数据库化的模块  
5. 把当前蓝图文档和行动文档列入规划文档总索引  

### 验收标准

- 团队内部不再对主仓产生歧义
- 文档有统一入口
- 过渡态问题有明确清单

## 4.2 Phase 1：平台底座治理期

### 目标

- 为未来可插拔模块建立统一底座
- 拆分超级 service 的外沿边界

### 本阶段重点

#### 4.2.1 模块注册机制

建立统一模块注册元数据，至少包括：

- `moduleKey`
- `moduleName`
- `moduleType`
- `entryRoute`
- `requiredPermissions`
- `requiredCapabilities`
- `requiredTables`
- `taskTypes`
- `featureFlags`

#### 4.2.2 能力包机制

定义统一能力包对象：

- 技能
- Prompt
- references
- scripts
- 知识空间
- Provider 策略

#### 4.2.3 服务拆分路线

优先拆分：

- `WorksService`
- `ReportsService`

拆分目标：

- 图像生成能力
- 视频生成能力
- HTML 渲染能力
- 发布能力
- 报告能力
- 营销规划能力
- 文案能力

### 产出

- 模块注册规范
- 能力包定义文档
- 服务拆分边界图

### 验收标准

- 新模块接入已有统一模板
- 超级 service 拆分路线被确认

## 4.3 Phase 2：知识库主数据落地期

### 目标

- 在主系统正式引入知识库域

### 本阶段重点

#### 4.3.1 数据模型

新增：

- `KnowledgeSpace`
- `KnowledgeDocument`
- `KnowledgeChunk`
- `KnowledgeEmbedding`
- `KnowledgeBinding`
- `KnowledgeRetrievalLog`

#### 4.3.2 多品牌规则

定义：

- 平台公共知识
- 品牌公共知识
- 品牌模块知识
- 用户临时知识

#### 4.3.3 工作流接入

让工作流支持：

- 步骤级知识绑定
- 步骤级检索范围
- 技能级知识绑定

#### 4.3.4 首批接入对象

建议先接：

- 技能 references
- 技能 scripts 说明
- 品牌资料
- 公众号资料
- 小红书模板参考

### 产出

- 知识库数据库设计初稿
- 知识库接口设计初稿
- 知识绑定机制说明
- 知识接入首批范围清单

### 验收标准

- 至少一个工作流可引用知识空间
- 至少一个技能可绑定知识空间
- 品牌知识与平台知识可区分

## 4.4 Phase 3：Provider 治理升级期

### 目标

- 把 Provider 管理从“配置中心”升级为“治理中心”

### 本阶段重点

#### 4.4.1 Registry

建立：

- Provider 模板
- 模型清单
- 协议类型
- 默认策略

#### 4.4.2 Routing

建立：

- 平台默认策略
- 品牌默认策略
- 技能绑定策略
- 用户覆盖策略

#### 4.4.3 Execution Gateway

建立：

- 统一超时
- 统一重试
- 统一错误分类
- 统一 fallback
- 统一熔断
- 统一日志

#### 4.4.4 诊断与运维能力

建立：

- 模型健康检测
- 延迟测试
- 用量面板
- 失败热力图
- 品牌配额视图

### 产出

- Provider Registry 设计稿
- Tenant Routing 设计稿
- Execution Gateway 设计稿
- 健康检测与用量面板设计稿

### 验收标准

- 至少一个模块完整走治理层调用链
- 至少能在后台查看模型健康状态
- 至少能查看品牌级调用用量

## 4.5 Phase 4：外挂能力引擎接入验证期

### 目标

- 在主系统内知识与接口治理已经稳定后，再验证外挂式能力系统

### 推荐验证对象

- MaxKB

### 验证方向

1. 单点登录或品牌映射  
2. 知识空间同步  
3. 嵌入式问答助手  
4. 运营知识问答  
5. 品牌知识问答  

### 不做的事

- 不把 MaxKB 直接融合进主系统代码仓
- 不把品牌权限主数据交给外挂系统

### 验收标准

- 外挂系统可以不影响主系统主流程
- 即使外挂不可用，主系统主业务仍正常

## 5. 跨阶段工作流

为了保证每个阶段不偏离目标，建议所有工作都按 6 个工作流推进。

### 5.1 架构工作流

负责：

- 架构设计
- 模块边界
- 服务拆分
- 蓝图更新

### 5.2 数据工作流

负责：

- 表设计
- Prisma 设计
- 迁移计划
- 数据隔离策略

### 5.3 前端工作流

负责：

- 页面壳层标准化
- 管理台交互设计
- 新模块接入规范

### 5.4 后端工作流

负责：

- 模块拆分
- 网关治理
- 工作流接入

### 5.5 运维工作流

负责：

- Redis
- pgvector
- 监控
- 熔断与告警
- 外挂系统部署策略

### 5.6 文档工作流

负责：

- 蓝图同步
- 变更记录
- 数据字典
- 模块接入模板

- [ ] 是否需要独立媒体类型

- [ ] 依赖哪些领域能力

- [ ] 是否更新数据库说明
- [ ] 是否新增变更文档

## 7. 建议优先级

推荐优先级如下。

### P0

- 主仓收束
- 模块注册与能力包规则
- `WorksService` / `ReportsService` 拆分路线

### P1

- 知识库主数据层
- 知识绑定机制
- Provider Registry + Routing 设计

### P2

- Execution Gateway
- 模型健康检测
- 用量与诊断面板

### P3

- MaxKB 外挂验证
- 更强的 Agent / 问答整合

## 8. 最终执行建议

建议不要直接同时启动所有工作，而是采用：

1. 先完成蓝图确认  
2. 再确认 Phase 0 与 Phase 1  
3. 再分别启动知识库与 Provider 治理两条并行线  
4. 等主系统内知识与治理层稳定后，再评估外挂能力  

这样做的原因是：

- 可以控制范围
- 可以降低风险
- 不会因为外挂系统而打乱主系统演进主线

## 9. 最终结论

如果用一句话概括这份行动计划：

> 先把主系统自己的平台底座、知识主数据层与 Provider 治理层做好，再把外挂能力系统作为增强层引入，而不是反过来让外挂产品决定主系统架构。

这条顺序一旦明确，后面的开发、拆分、扩展和文档治理都会顺得多。
