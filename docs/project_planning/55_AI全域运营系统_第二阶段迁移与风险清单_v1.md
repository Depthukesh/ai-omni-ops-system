# AI全域运营系统 第二阶段迁移与风险清单 v1

## 1. 文档目的

本文档用于说明第二阶段本轮开发的迁移顺序、回退边界和主要风险，核心目标是：

- 不影响现有网站功能运行
- 每完成一块，该块功能要可用
- 出现问题时可以快速定位和回退

## 3. 推荐迁移顺序

### 3.1 数据层先行

顺序：

1. 更新 `prisma/schema.prisma`
2. 补迁移 SQL
3. 执行 `npx prisma generate`

目标：

- 先确保关系表模型和 Prisma Client 可用

### 3.2 后端接口层

顺序：

1. 新增 service
2. 新增 controller
3. 新增 module
4. 注册到 `AppModule`

目标：

- 让接口先具备最小闭环

### 3.3 前端治理层

顺序：

1. 补 `admin.ts`
2. 新增独立关系页
3. 挂到后台模块中心子菜单

目标：

- 保证页面和接口同步可联调

### 3.4 文档与归档

顺序：

1. 更新 `docs/project_planning`
2. 更新 `docs/database-archive.md`
3. 新增 `docs/changes` 记录

## 4. 主要风险

### 4.1 Prisma 关系声明不完整

风险：

- 新增关系表后，如果 `KnowledgeBase` 反向关系字段未补齐，`prisma generate` 可能失败

控制方式：

- 同步补齐 Prisma 双向关系定义

### 4.2 迁移 SQL 与 Prisma schema 不一致

风险：

- Prisma schema 写了关联，但 SQL 没有补外键或索引，后续可能出现行为不一致

控制方式：

- 迁移中补齐：
  - 唯一索引
  - 查询索引
  - `knowledgeBaseId` 外键

### 4.3 前后端数据结构不一致

风险：

- 前端若只传 `packageId`，后端又要求 `packageKey / packageName`，会造成保存失败

控制方式：

- 前端服务层和页面统一按能力包元数据自动补齐 payload

### 4.4 与第一阶段 `KnowledgeBinding` 概念混淆

风险：

- 用户或开发者可能误以为第二阶段关系页等同于第一阶段详情页中的 `Knowledge` 区块

控制方式：

- 页面命名明确使用：
  - `知识关系`
- 文档明确说明：
  - 第一阶段是桥接层
  - 第二阶段是能力包知识治理专用关系层

### 4.5 菜单扩展影响现有后台认知

风险：

- 后台模块中心新增子菜单后，可能让用户短期内不清楚第一阶段页与第二阶段页差异

控制方式：

- 子页文案突出“第二阶段 / 独立关系层 / 治理页”语义
- 保留现有四个子页不动，只新增一个新入口

### 4.6 数据库未迁移时接口不可用

风险：

- 如果直接切数据库接口，没有 mock 兜底，则开发和演示期可能中断

控制方式：

- 继续保持：
  - 数据库优先
  - `mock-data` 兜底

---

## 5. 回退策略

如果本轮出现问题，按以下粒度回退：

### 5.1 页面层回退

- 临时隐藏 `知识关系` 子页入口
- 不影响现有第一阶段后台详情页知识区块

### 5.2 接口层回退

- 保留 module 代码但不在前端调用
- 第一阶段 `KnowledgeBinding` 相关接口继续可用

### 5.3 数据层回退

- 即使新表暂时不可用，后端也可回退到 `mock-data.skillPackageKnowledgeSpaces`

## 7. 本轮结论

第二阶段本轮迁移风险总体可控，原因是：

- 变更集中在后台治理域
- 保持数据库优先 / mock 兜底双通路
- 不直接改现有业务模块运行链路
- 第一阶段知识桥接层不被替换

因此适合把本轮作为第二阶段启动批次正式落地。
