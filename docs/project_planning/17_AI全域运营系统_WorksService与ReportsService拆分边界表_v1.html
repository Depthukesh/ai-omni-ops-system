AI全域运营系统 WorksService 与 ReportsService 拆分边界表 v1

本表用于把超级 service 的拆分从“方向建议”推进到“职责归属、拆分顺序和保留边界”的层面，便于后续进入真正的代码拆分阶段。

WorksService Works 拆分顺序 ReportsService Reports 拆分顺序 不要误拆的职责 最终结论

1. WorksService 拆分边界表

现状： WorksService 同时混合了领域能力、工作流编排和任务/媒体横切处理，因此更像总控中心，而不是单一服务。
当前职责 推荐归属 第一阶段是否确认拆分 说明
文案生成copy-domain否重要但与业务编排耦合较深，建议第二批
图片生成image-domain是边界清晰，可被多个模块复用
视频生成video-domain否链路复杂，建议第三批
HTML 渲染html-render-domain是输入输出边界最清晰
发布动作publish-domain是发布目标和调用链容易独立治理
工作流步骤推进workflow-orchestration否应保留在上层编排
任务创建与状态更新task-core否属于平台底座，应统一收口
媒体落库与关联media-core否属于平台横切能力，不应分散

2. WorksService 建议拆分顺序

  1. 第一批： html-render-domain、publish-domain、image-domain
  2. 第二批： copy-domain、workflow-orchestration
  3. 第三批： video-domain

优先拆边界清晰、复用高、对主流程侵入更小的能力；视频链路最复杂，建议最后拆。

3. ReportsService 拆分边界表

现状： ReportsService 同时混合洞察抽取、报告生成、营销规划和策略推导，模块边界与复用边界不清晰。
当前职责 推荐归属 第一阶段是否确认拆分 说明
洞察抽取insight-domain是适合作为通用分析能力沉淀
报告生成report-generation-domain是输出形态清晰，易先抽离
品牌策略推导strategy-domain否与业务语境耦合较深，建议第二批
营销规划campaign-domain否与品牌上下文耦合更深
原始数据组装collector-domain / 编排层否更像前置输入准备，不宜盲拆

4. ReportsService 建议拆分顺序

  1. 第一批： report-generation-domain、insight-domain
  2. 第二批： strategy-domain、campaign-domain

先把更像通用输出能力的部分抽出来，再处理高度依赖业务语境的规划与策略能力。

5. 哪些职责不要误拆

  • 任务状态治理
  • 媒体主数据治理
  • 权限控制
  • 品牌上下文解析
  • Provider 调用治理

这些能力更适合继续留在平台底座层：task-core、media-core、permission-core、brand-core、provider-core。

6. 最终结论

拆分原则： 不是拆得越多越好，而是把真正可复用、边界清晰的能力抽出来，把仍需掌握全局上下文的编排逻辑先留在上层。

第一阶段只需要形成职责清单、归属建议、分批顺序和风险说明，不必直接大规模删改超级 service。
