AI全域运营系统蓝图行动计划与执行清单

本文件是《融合知识库与接口治理的目标蓝图规划》的配套执行文档，用于把目标蓝图拆成阶段、任务、验收标准和开工前检查项，便于后续评审和推进。

总原则 分期计划 阶段动作 执行清单 优先级 执行建议

1. 行动计划总原则

原则重点： 不推倒重来，先治理底座，再扩展能力；先统一主系统内部规则，再决定外挂系统的接入方式。
  • 以现有系统为基础渐进演进，而不是重构式重写
  • 优先建设平台底座能力，再扩展新模块
  • 先治理 WorksService 和 ReportsService，再做大规模新增功能
  • 先把主系统的数据、权限、任务和能力包机制做稳，再决定外挂集成
  • 每个阶段都必须可交付、可暂停、可回退

2. 建议分期

Phase 0：基线收束期

收束主仓与文档基线，继续清理过渡态，为知识库和接口治理做准备。

Phase 1：平台底座治理期

建立模块注册规则、能力包机制和超级 service 拆分路线。

Phase 2：知识库主数据落地期

在主系统内建设正式知识库域，让知识进入工作流与技能。

Phase 3：Provider 治理升级期

把 Provider 配置中心升级为治理层，建设健康检测、诊断、用量、熔断和 fallback 能力。

Phase 4：外挂能力引擎接入验证期

在主系统稳定后，再按需验证 MaxKB 或其他外挂能力系统。

3. 分阶段行动计划

Phase 0：基线收束期

目标： 明确唯一主仓、备份仓用途、正式文档入口，继续清理 mock fallback 和未完全数据库化的模块。

产出： 主仓确认说明、备份仓说明、文档索引更新、过渡态清单。

  • 明确 ai-omni-ops-system 为唯一主仓
  • 对平行仓与备份仓加只读说明
  • 盘点剩余 mock fallback 与本地 fallback
  • 盘点尚未完全数据库化的模块
  • 把蓝图文档和行动文档列入规划文档总索引

Phase 1：平台底座治理期

目标： 为未来可插拔模块建立统一底座，拆分超级 service 的外沿边界。

主题 重点动作
模块注册机制 建立 moduleKey、moduleName、moduleType、entryRoute、requiredPermissions、requiredCapabilities、requiredTables、taskTypes、featureFlags 等统一元数据
能力包机制 把技能、Prompt、references、scripts、知识空间、Provider 策略统一收敛为能力包
服务拆分路线 优先拆分 WorksService 与 ReportsService，明确图像、视频、HTML、发布、报告、营销规划、文案等子域

Phase 2：知识库主数据落地期

目标： 在主系统正式引入知识库域，并先把知识作为主数据和工作流输入接进系统。

  • 新增 KnowledgeSpace、KnowledgeDocument、KnowledgeChunk、KnowledgeEmbedding、KnowledgeBinding、KnowledgeRetrievalLog
  • 定义平台公共知识、品牌公共知识、品牌模块知识、用户临时知识四层结构
  • 让工作流支持步骤级知识绑定、步骤级检索范围、技能级知识绑定
  • 首批先接技能 references、技能 scripts 说明、品牌资料、公众号资料、小红书模板参考

Phase 3：Provider 治理升级期

目标： 把 Provider 管理从配置中心升级为治理中心。

  • 建立 Provider Registry：Provider 模板、模型清单、协议类型、默认策略
  • 建立 Routing：平台默认、品牌默认、技能绑定、用户覆盖策略
  • 建立 Execution Gateway：统一超时、重试、错误分类、fallback、熔断和日志
  • 建立诊断能力：模型健康检测、延迟测试、用量面板、失败热力图、品牌配额视图

Phase 4：外挂能力引擎接入验证期

目标： 在主系统内知识与接口治理稳定后，再验证外挂式能力系统。

推荐验证对象优先是 MaxKB，但前提是主系统主数据、权限与工作流接入能力已经稳定。
  • 验证单点登录或品牌映射
  • 验证知识空间同步
  • 验证嵌入式问答助手
  • 验证品牌知识问答
  • 坚持不把 MaxKB 直接融合进主系统代码仓

4. 跨阶段工作流

架构工作流

负责架构设计、模块边界、服务拆分和蓝图更新。

数据工作流

负责表设计、Prisma 设计、迁移计划和数据隔离策略。

前端工作流

负责页面壳层标准化、管理台交互设计和新模块接入规范。

后端工作流

负责模块拆分、网关治理和工作流接入。

运维工作流

负责 Redis、pgvector、监控、熔断告警和外挂系统部署策略。

文档工作流

负责蓝图同步、变更记录、数据字典和模块接入模板。

5. 执行清单

总清单

类别 开工项
基线与治理 确认唯一主仓；标记平行仓与备份仓用途；盘点 mock fallback、本地 fallback；确认规划文档索引
模块底座 设计模块注册元数据、能力包模型、统一任务合同、统一媒体合同、统一发布合同
服务拆分 拆分 WorksService 和 ReportsService 边界，明确图像、视频、HTML、发布、策略、文案等子域
知识库 设计知识库数据库模型、API、知识空间分层、知识绑定机制、检索日志，并选定首批接入模块
Provider 治理 设计 Provider 模板层、品牌路由层、执行网关层、健康检测、用量与配额面板、failover 与熔断规则
技能与 Prompt 为技能增加版本与状态、依赖对象定义；为 Prompt 增加版本、回滚、知识空间绑定能力
外挂能力验证 验证 MaxKB 独立部署、品牌知识空间映射、嵌入式问答入口以及主系统与外挂解耦边界

新增模块前检查清单

  • 模块目标、主实体、模块类型是否定义清楚
  • 是否需要独立数据表、任务类型、媒体类型、知识空间、发布记录
  • 依赖哪些底座能力、领域能力、Provider 策略、技能或 Prompt
  • 是否更新站点地图、数据库说明、变更文档、模块接入说明

知识库开工前清单

  • 确认知识空间层级
  • 确认品牌隔离规则
  • 确认知识上传入口
  • 确认知识切片与向量策略
  • 确认工作流引用方式
  • 确认权限与审计策略
  • 确认首批接入模块

Provider 治理开工前清单

  • 确认 Provider 模板结构
  • 确认品牌级策略结构
  • 确认技能级绑定结构
  • 确认错误分类标准
  • 确认健康检测策略
  • 确认用量统计来源
  • 确认 failover 执行规则

6. 建议优先级

P0

  • 主仓收束
  • 模块注册与能力包规则
  • WorksService / ReportsService 拆分路线

P1

  • 知识库主数据层
  • 知识绑定机制
  • Provider Registry + Routing 设计

P2

  • Execution Gateway
  • 模型健康检测
  • 用量与诊断面板

P3

  • MaxKB 外挂验证
  • 更强的 Agent / 问答整合

7. 最终执行建议

建议不要同时启动所有工作，而是先完成蓝图确认，再确认 Phase 0 与 Phase 1，再分别启动知识库与 Provider 治理两条并行线，等主系统内知识与治理层稳定后，再评估外挂能力。

最终结论： 先把主系统自己的平台底座、知识主数据层与 Provider 治理层做好，再把外挂能力系统作为增强层引入，而不是反过来让外挂产品决定主系统架构。
