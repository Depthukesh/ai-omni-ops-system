# AI全域运营系统开发交付检查清单

## 1. 目的

本文件定义两件事：

- 每次开始开发前，必须明确和携带哪些信息
- 每次开发完成后，必须更新和交付哪些记录

目标不是增加文档负担，而是提前把项目变大后最容易失控的点固定下来，确保：

- 项目结构可追踪
- 代码修改可回溯
- 提交边界清晰
- 风险与待办不丢失
- 新人和后续自己都能快速接手

## 1.1 执行范围

- 本清单不是在用户说“继续”时才触发
- 本清单适用于每一次实际开发动作，包括排查、设计、改代码、改文档、联调、验证、提交和交接
- 也就是说，只要进入开发流程中的任一步，就默认要遵循本清单，而不是按指令关键词选择性执行
- 如果某一步信息不足，也必须先补齐最小必要上下文，再继续往下做

## 2. 开发前必须带上的信息

每次开始一个开发任务时，至少要确认下面 10 类信息。

### 2.1 任务基本信息

- 任务标题：一句话说明这次要做什么
- 任务类型：`feat` / `fix` / `refactor` / `docs` / `chore`
- 任务范围：前端、后端、文档、扩展、脚本中的哪些部分会被影响
- 目标板块：例如 `brand-growth`、`xiaohongshu`、`personal-center`、`admin`

### 2.2 业务背景信息

- 为什么要改
- 用户当前遇到的问题是什么
- 这次改完希望达到什么结果
- 是否属于主链路、过渡方案还是补充能力

### 2.3 入口与影响范围

- 入口页面或入口 API 是什么
- 可能影响哪些页面、模块、表、脚本
- 是否跨板块
- 是否会影响已有数据或历史兼容

### 2.4 代码落点信息

- 页面入口文件
- 关联工作区/组件/hook
- 前端 service
- 后端 controller/service
- 数据模型或资源目录
- 如果任务涉及技能、Prompt、能力包或技能中心，还必须额外确认：
  - 对应 `SkillConfig` 是否已存在
  - 对应 `PromptTemplate` 是否已存在
  - 对应 `SkillPromptBinding` 是否已存在
  - 前端真实调用入口在哪个页面、哪个工作区、哪个提交动作
  - 本次是改数据库现有记录、补自动同步，还是同时新增种子与绑定

如果在开始开发前说不清“改动将落在哪几个文件层级”，说明任务还没被拆清楚。

### 2.5 现有规范基线

开始前必须先对齐这些基线文档：

- `docs/engineering-standards.md`
- `docs/site-map.md`
- `docs/site-map-mermaid.md`
- `docs/development-delivery-checklist.md`
- 与当前任务最近的一条 `docs/changes/*.md`

如果本次会修改已有功能或已有结构，还必须额外确认：

- `docs/site-map.md` 与 `docs/site-map-mermaid.md` 中对应板块的具体条目，而不是只泛读整份文档
- 最近相关的 `docs/changes/*.md` 中，之前是按什么思路和什么边界落地的
- 本次拟采用的实现方式是否与既有结构、交互逻辑、数据链路保持一致

如果发现本次方案与既有开发思路或开发逻辑不一致，必须先向用户说明冲突点并获得确认，不能直接开始改。

如果改的是资源生成、作品存储、发布链路，还要额外看：

- `docs/generated-content-storage-standards.md`

如果改的是数据库、迁移、正式入库边界，还要额外看：

- `docs/database-archive.md`

如果改的是 Git 边界、提交拆分、备份策略，还要额外看：

- `docs/git-workflow.md`

如果改的是个人中心、多用户、品牌协作，还要额外看：

- `docs/personal-center-multi-user-system-plan.md`

### 2.6 Git 基线信息

- 当前分支或当前提交点
- 工作区是否已有未提交改动
- 这些未提交改动是否属于本次任务
- 本次准备做几个提交，每个提交分别解决什么问题

如果工作区里已经有无关改动，必须先划清边界，不能直接混着做。

### 2.7 验证方式

开发前就要先定好如何验证，不允许改完才想。

- 开发前就要先定好如何验证，不允许改完才想。
- 看接口
- `GetDiagnostics`
- `npm run build:web`
- `npm run build:server`
- 本地联调
- 手工走主链路
- 如果改动涉及部署链、Nginx、PM2、端口或运行用户，还必须提前约定服务器侧验证：工作区干净检查、监听端口检查、健康检查，以及运行时 Secrets 是否真实传进目标进程；若应用由 `ecosystem.config.*` 托管，还要验证关键 Secret 是否已进入对应 `pm2` 进程的实际 `env`
- 如果改动涉及部署链、Nginx、PM2、端口或运行用户，还必须提前约定服务器侧验证：工作区检查、是否生成远端现场备份、监听端口检查、健康检查，以及运行时 Secrets 是否真实传进目标进程；若应用由 `ecosystem.config.*` 托管，还要验证关键 Secret 是否已进入对应 `pm2` 进程的实际 `env`

### 2.8 风险信息

- 最可能出错的点是什么
- 是否涉及第三方模型、飞书、扩展、发布桥接、定时器
- 是否涉及资源副本、历史数据兼容、任务状态同步

### 2.9 文档更新范围

开始前就要知道本次结束后要更新哪些文档：

- 是否更新 `docs/changes/*.md`
- 是否更新 `docs/site-map.md`
- 是否更新 `docs/site-map-mermaid.md`
- 是否更新 `docs/engineering-standards.md`
- 是否需要新增专题文档

### 2.10 待解决事项基线

- 当前任务开始前，是否已有明确未解决问题
- 这些问题是否属于本次一起处理
- 哪些问题明确不在本次范围内

## 3. 开发中必须持续记录的信息

长任务不允许只做代码，不留过程痕迹。开发中至少要持续记录这些内容：

- 当前做到哪一步
- 已确认的真实原因或真实结构
- 哪些是假设，哪些已经验证
- 哪个问题修掉了，哪个问题还没修掉
- 当前是否出现新的风险、边界变化或无关改动

如果执行时间较长，必须持续同步阶段性进展，避免任务中断后无人知道停在什么位置。

## 4. 开发完成后必须更新的信息

每次开发完成后，至少要补齐下面 8 类信息。

### 4.1 代码结果

- 实际改了哪些文件
- 各文件分别承担什么职责变化
- 是否新增了组件、hook、service、controller、脚本或文档
- 如果本次是技能相关任务，还必须说明：
  - 新增或调整了哪些 `SkillConfig`
  - 新增或调整了哪些 `PromptTemplate`
  - 新增或调整了哪些 `SkillPromptBinding`
  - 哪个前端业务入口已经接上真实调用

### 4.2 验证结果

- 做了哪些验证
- 哪些已通过
- 哪些未做
- 是否还有残余风险
- 如果本次改动涉及部署或运行环境，还要写清服务器侧验证是否覆盖：`git status`/自动备份路径、公网/本机监听端口、进程运行用户、健康检查、关键环境变量/Secrets 是否已注入运行进程；若使用 `PM2 + ecosystem.config.*`，还要说明是否已验证目标进程实际读取到对应 Secret
- 如果本次改动涉及技能或 Prompt，还必须写清：
  - 是否已验证数据库真实存在对应记录
  - 如果当前环境数据库不可达，是否已补自动落库机制，以及阻塞点是什么
  - 是否已验证后台技能中心、个人中心和业务工作台三处口径一致

不能只写“已完成”，必须写明验证方式。

### 4.3 文档更新

默认至少更新：

- `docs/changes/*.md`

满足下面任一条件时，必须额外更新：

- 结构变化：更新 `docs/site-map.md`
- 结构关系变化：更新 `docs/site-map-mermaid.md`
- 通用规则变化：更新 `docs/engineering-standards.md`
- 新增长期专题：新增专题文档并在 `docs/README.md` 纳入说明

如果开发流程、交付要求、开发前必读 / 开发后必更规则发生变化，还必须同步更新：

- `docs/development-delivery-checklist.md`
- `docs/engineering-standards.md`

如果 Git 备份流程、快照策略、暂存边界发生变化，还必须同步更新：

- `docs/git-workflow.md`

### 4.4 Git 备份信息

- 本次提交范围
- 提交信息
- 是否存在未纳入本次提交的剩余改动
- 剩余改动为什么不纳入

### 4.5 网站地图更新

如果这次改动改变了下列任一内容，必须更新网站地图：

- 页面入口
- 板块结构
- 页面内部工作区结构
- 前端 `service -> API` 关系
- 后端模块承接关系
- 数据主链路

更新 `docs/site-map.md` 时，还必须把本次对应的 `docs/changes/*.md` 作为参考资料挂到相关板块，便于后续追溯“为什么会变成现在这样”。

### 4.6 代码规范更新

如果本次开发暴露出新的共性问题，必须把它升级为规则，而不是只在这次修掉：

- 命名规范
- 目录规范
- 页面拆分阈值
- 资源落盘规范
- 第三方接入规范
- 技能落库与前端接入规范
- 日志/异常规范
- 文档同步规则

### 4.7 待解决事项

每次开发结束后，必须明确：

- 已解决事项
- 未解决事项
- 明确后置事项
- 当前风险点
- 下一步最合适做什么

### 4.8 交接信息

如果下一轮不是立即继续做，至少要能让别人看懂：

- 当前代码已经到什么状态
- 下一步从哪个文件开始
- 是否依赖某个本地环境、配置或已启动服务

## 5. 必做文档矩阵

下面这张表定义了“什么情况必须更新什么文档”。

| 场景 | 必须更新 |
| --- | --- |
| 任意实际代码改动 | `docs/changes/*.md` |
| 页面、模块、主链路变化 | `docs/site-map.md` |
| 页面/模块/数据关系变化 | `docs/site-map-mermaid.md` |
| 新的通用约束或流程 | `docs/engineering-standards.md` |
| 开发流程、交付清单、必读规则变化 | `docs/development-delivery-checklist.md` |
| Git 备份、快照、暂存策略变化 | `docs/git-workflow.md` |
| 资源、发布、存储等专题规则变化 | 对应专题文档 |
| 新增文档类型 | `docs/README.md` |

## 6. 必做 Git 矩阵

每次提交前必须确认：

- 本次提交只解决一类问题
- 已完成最低限度验证
- 不混入无关改动
- 提交信息能反映真实意图
- 提交后还能说清楚“这次提交解决了什么”

推荐提交信息：

- `feat:` 新功能
- `fix:` 修问题
- `refactor:` 重构/收敛
- `docs:` 文档沉淀
- `chore:` 杂项维护

## 8. 强制执行规则

从现在开始，后续开发默认执行以下强制规则：

- 没有任务范围说明，不开始改代码
- 没有验证方式，不开始改代码
- 没有文档更新，不视为任务完成
- 没有 Git 备份或边界说明，不视为任务闭环
- 没有待解决事项记录，不能直接进入下一轮复杂开发
- 以上规则适用于开发过程中的每一步，不是只在用户发送“继续”时才执行
- 只要发生新的排查、修改、验证、提交或交接动作，都要重新套用本清单检查当前步骤是否完整

## 9. 最终目标

项目越大，越不能靠记忆驱动，而要靠结构化记录驱动。

这套清单的目标不是“多写文档”，而是把以下能力提前建设出来：

- 任何板块都能快速定位入口
- 任何改动都能快速追溯原因
- 任何提交都能快速判断边界
- 任何未解决事项都不会凭空消失
- 任何接手者都能在最短时间内恢复上下文
