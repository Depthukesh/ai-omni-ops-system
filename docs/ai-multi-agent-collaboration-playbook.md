# AI Agent 协作开发手册

## 1. 目标

- 让两个或更多 AI Agent 能同时推进同一个网站，而不互相覆盖、重复劳动或把规范做散。
- 把“如何分工、如何对齐、如何交接、如何验收、如何提交”固化成统一流程。
- 保证新增 Agent 进入项目时，先接入现有规范，再开始开发，而不是各写各的。

## 2. 适用范围

- `apps/web`
- `apps/server`
- `packages/shared`
- `docs`
- 本仓库所有通过对话或自动化方式接入的 AI Agent

## 3. 角色模型

### 3.1 主 Agent

- 负责和用户直接对齐需求。
- 负责划分任务边界、指定本轮目标和验收标准。
- 负责维护任务总进度、统一口径、最终交付说明。
- 负责最终提交边界检查和决定是否推送远端。

### 3.2 并行 Agent

- 只处理被明确分配的子任务。
- 不自行扩大范围，不跨边界顺手改动其他模块。
- 必须遵守主 Agent 指定的代码落点、验证方式和 Git 边界。
- 完成后输出结构化回执，供主 Agent 合并结果。

### 3.3 文档 Agent

- 当任务涉及路线图、规范、方案、阶段总结、交接文档时，可由单独 Agent 负责文档沉淀。
- 文档 Agent 不能脱离真实代码状态凭空写文档，必须基于实际改动、实际验证、实际提交状态产出。

## 4. 协作原则

### 4.1 单轮只允许一个总目标

- 一轮协作必须先定义一个总目标，例如：
  - “给后台仪表盘增加退出登录按钮”
  - “继续减薄小红书 workspace-shell”
  - “把视频生成可靠性补丁推上远端并补交接文档”
- 如果一个 Agent 做 UI 修复，另一个 Agent 做完全无关的后端改造，就会失去统一验收口径。

### 4.2 一个 Agent 只负责一块明确边界

- 边界按以下维度划分：
  - 文件边界
  - 模块边界
  - 页面边界
  - 文档边界
  - 提交边界
- 同一时刻不要让两个 Agent 同时改同一个核心文件，除非其中一个只读不写。

### 4.3 所有 Agent 必须遵守同一套基线

- 开始前必须统一读取：
  - `AGENTS.md`
  - `docs/ai-agent-access-and-secrets-policy.md`
  - `docs/engineering-standards.md`
  - `docs/README.md`
  - `docs/site-map.md`
  - `docs/site-map-mermaid.md`
  - `docs/development-delivery-checklist.md`
- 如果本轮任务有最近相关的 `docs/changes/*.md`，也必须先读。

### 4.4 用户只看主 Agent

- 用户对接窗口只能有一个。
- 并行 Agent 不直接向用户承诺范围、时间、结论。
- 最终对外口径由主 Agent 统一输出。

## 5. 推荐协作模式

### 5.1 模式 A：主 Agent 编排，子 Agent 并行探索

- 适合：
  - 先摸清代码结构
  - 查找多个影响点
  - 对比几个实现方案
- 做法：
  - 主 Agent 定义查询范围
  - 子 Agent 分头检索
  - 主 Agent 汇总结果，决定最终改法
- 这个模式适合“先看清楚再动手”，不适合直接让多个 Agent 同时写代码。

### 5.2 模式 B：主 Agent 设计，子 Agent 分块落地

- 适合：
  - 页面拆分
  - 文档补齐
  - 前后端边界清晰的任务
- 做法：
  - 主 Agent 先固定方案、接口、命名和边界
  - 子 Agent 各自完成独立子块
  - 主 Agent 统一检查风格、验证和提交

### 5.3 模式 C：主 Agent 写代码，子 Agent 做审阅/验证

- 适合：
  - 风险高的主链路修复
  - 认证、发布、支付、任务状态、持久化链路
- 做法：
  - 主 Agent 独占修改代码
  - 子 Agent 负责 review、测试建议、文档同步建议
- 这是最稳的模式，适合高风险链路。

## 6. 任务拆分规范

### 6.1 拆分前必须先明确 6 件事

1. 任务标题
2. 总目标
3. 影响范围
4. 不可触碰边界
5. 验证方式
6. 提交策略

### 6.2 推荐拆分粒度

- 正确示例：
  - Agent A：抽离 `workspace-shell.tsx` 的 props builder
  - Agent B：补对应 `docs/changes/*.md` 和索引
- 正确示例：
  - Agent A：后台页增加退出按钮
  - Agent B：只做浏览器联调或 review
- 错误示例：
  - Agent A 改 `workspace-shell.tsx`
  - Agent B 同时也改 `workspace-shell.tsx`
- 错误示例：
  - Agent A 改页面
  - Agent B 顺手改同链路 service 的协议字段
  - 但双方没有先对齐接口

### 6.3 高风险任务禁止并行写

- 以下任务默认不允许两个 Agent 同时改代码：
  - 认证与登录态
  - 数据库 schema 和 migration
  - 发布链路
  - 支付链路
  - 第三方任务状态回收
  - `packages/shared` 里的共享协议

## 7. 统一规范对齐方式

### 7.1 统一命名

- 主 Agent 先定：
  - 文件命名
  - hook 命名
  - props 类型命名
  - service 命名
  - docs 文档标题
- 未对齐命名之前，并行 Agent 不要自行发明新命名体系。

### 7.2 统一架构边界

- 页面/`page.tsx` 只做挂载和一级编排。
- 复杂逻辑下沉到 hook、service、gateway、repository。
- 共享协议优先进 `packages/shared`。
- 外部集成不散落在页面组件中。
- 这是所有 Agent 的共同约束，不因任务大小而例外。

### 7.3 统一验证标准

- 每个子任务完成时至少说明：
  - 改了哪些文件
  - 跑了什么验证
  - 哪些通过
  - 哪些没做
  - 还剩什么风险
- 最低常见验证：
  - `GetDiagnostics`
  - 前端构建
  - 后端构建
  - 页面联调
  - 真实链路验证

### 7.4 统一文档标准

- 任何实际代码改动，默认至少补一条 `docs/changes/*.md`。
- 涉及入口、结构或关系变化时，同步更新：
  - `docs/README.md`
  - `docs/site-map.md`
  - `docs/site-map-mermaid.md`
- 如果只是某个并行 Agent 提交了代码，但没补文档，该子任务不算完整闭环。

## 8. 进度对齐机制

### 8.1 统一任务板

- 推荐由主 Agent 维护一份轻量任务板，最少包含：
  - `pending`
  - `in_progress`
  - `blocked`
  - `completed`
- 每个子任务要有唯一标题，不要用“顺手改一下”这类模糊表述。

### 8.2 统一阶段回报格式

- 每个并行 Agent 回报时使用固定结构：

```md
## 子任务回报

- 任务：`...`
- 范围：`...`
- 改动文件：
  - `...`
- 验证：
  - `GetDiagnostics`
  - `npm run build:web`
- 结果：`通过 / 部分通过 / 未做`
- 风险：`...`
- 建议主 Agent 下一步：`...`
```

### 8.3 统一阶段快照

- 一个阶段结束后，主 Agent 必须把当前状态写入至少一处：
  - `docs/changes/*.md`
  - 专题 handoff 文档
  - `AGENTS.md`
- 如果多人协作了一整轮但没有阶段快照，后续恢复成本会很高。

## 9. Git 协作标准

### 9.1 提交权归主 Agent

- 推荐默认策略：
  - 并行 Agent 负责给出修改结果
  - 主 Agent 负责最终边界检查、`git add`、`git commit`、`git push`
- 这样最容易避免混入工作区其它无关改动。

### 9.2 一个提交只覆盖一个子目标

- 示例：
  - `feat: add admin dashboard logout button`
  - `refactor: split xiaohongshu video detail props`
  - `docs: hand off xiaohongshu structure governance`
- 不允许把两个 Agent 的无关成果混进同一个提交。

### 9.3 混合工作区必须精确暂存

- 如果工作区已有无关改动，提交时必须：
  - `git status --short`
  - 只暂存本次任务相关文件
  - 提交后再次说明未纳入的剩余改动

### 9.4 推送规则

- 默认先本地验证，再由用户决定是否推送。
- 如果用户明确要求“直接提交推送”，由主 Agent 统一执行。
- 并行 Agent 不单独推送远端，避免打乱提交顺序和口径。

## 10. 冲突处理

### 10.1 文件冲突

- 两个 Agent 同时需要改同一文件时，只能保留一个写入者。
- 另一个 Agent 改为：
  - 只读分析
  - 先出建议
  - 或改其它辅助文件

### 10.2 方案冲突

- 如果两个 Agent 提出不同方案，主 Agent 统一裁决。
- 裁决依据优先级：
  1. 用户当前明确要求
  2. `AGENTS.md`
  3. `docs/engineering-standards.md`
  4. 最近相关变更记录
  5. 风险更低的实现方式

### 10.3 进度冲突

- 如果 Agent A 还在改，Agent B 想基于旧代码继续改，先暂停。
- 先等 Agent A 交回结构化结果，再决定 B 是否继续。

## 11. 推荐执行流程

### 11.1 任务开始

1. 主 Agent 读基线文档
2. 明确总目标和边界
3. 判断是否需要第二个 Agent
4. 如果需要，拆出子任务

### 11.2 执行中

1. 子 Agent 只处理指定边界
2. 主 Agent 持续汇总进度
3. 发现边界变化及时中止并重新分配

### 11.3 子任务完成

1. 子 Agent 提交结构化回报
2. 主 Agent 审阅差异
3. 主 Agent 统一验证
4. 主 Agent 统一补文档

### 11.4 任务结束

1. 主 Agent 做 Git 边界检查
2. 独立提交
3. 根据用户要求决定是否推送
4. 写变更记录和阶段快照

## 12. 本项目推荐分工模板

### 12.1 场景一：低风险前端结构治理

- Agent A：
  - 负责代码拆分
  - 抽 props builder、section container、modal shell
- Agent B：
  - 负责文档同步
  - 补 `docs/changes/*.md`、`docs/README.md`、`docs/site-map*.md`
- 主 Agent：
  - 审查结构是否符合“薄入口 + 下沉逻辑”
  - 统一构建验证和提交

### 12.2 场景二：UI 补位 / 小功能

- Agent A：
  - 负责页面改动
- Agent B：
  - 负责查找复用链路、做浏览器验证或 review
- 主 Agent：
  - 统一决定是否提交推送

### 12.3 场景三：高风险主链路

- Agent A：
  - 负责主代码修改
- Agent B：
  - 只做 review、测试建议、回归点检查
- 主 Agent：
  - 统一合并结论和交付

## 13. 给第二个 Agent 的接入提示词模板

```md
你现在作为本仓库的并行开发 Agent，只负责用户当前任务中的指定子范围。

开始前必须先读：
- `AGENTS.md`
- `docs/engineering-standards.md`
- `docs/README.md`
- `docs/site-map.md`
- `docs/site-map-mermaid.md`
- 当前任务最近相关的 `docs/changes/*.md`

你本轮只允许处理以下范围：
- [在这里写清文件/模块/页面边界]

你本轮禁止触碰：
- [在这里写清禁止范围]

你完成后必须输出：
- 改动文件清单
- 核心改动摘要
- 验证结果
- 风险和未做项
- 建议主 Agent 下一步

不要自行扩大范围，不要擅自提交，不要直接推送。
```

## 14. 给主 Agent 的调度清单

- 这轮总目标是否唯一且清楚
- 子任务边界是否互不重叠
- 是否已经指定验证方式
- 是否已经指定提交策略
- 是否已经指定权限边界和 Secrets 注入方式
- 是否已经指定文档落点
- 是否已经说明不允许触碰的区域
- 是否已经约定统一命名和结构
- 是否已经准备阶段快照文档

## 15. 最低落地要求

- 如果只是临时引入第二个 Agent，最低也要做到：
  - 所有 Agent 先读 `AGENTS.md`
  - 主 Agent 明确任务边界
  - 并行 Agent 不直接提交推送
  - 主 Agent 统一验证和交付
  - 本轮结束后留下 `docs/changes/*.md` 或 handoff 文档

## 16. 本项目当前建议

- 当前仓库最适合采用：
  - 主 Agent 负责需求对齐、边界控制、最终提交
  - 第二个 Agent 负责“并行检索 / 文档同步 / 低耦合子块落地 / review”
- 在当前工作区仍存在用户未收口改动的情况下，不建议两个 Agent 同时直接写同一片核心代码。
- 如果确实要双写并行，必须先拆到不同文件层级，再由主 Agent 最终收口。
