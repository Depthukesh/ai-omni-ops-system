# AI全域运营系统开发规范

## 1. 目标

- 让后续开发在同一套架构边界、命名习惯和交付流程下推进
- 降低“功能能跑但不可维护”“局部修好后其他链路再次出错”的概率
- 把当前代码中已经暴露出的热点问题，提前固化为明确约束

## 2. 适用范围

- `apps/web`
- `apps/server`
- `apps/web/public/extensions/xhs-draft-publisher`
- `packages/shared`
- `docs`

## 3. 当前重点问题

### 3.1 已暴露热点

- `xiaohongshu/page.tsx` 职责过多，集成了工作区、作品管理、发布、轮询和弹窗状态
- `works.service.ts`、`collectors.service.ts`、`reports.service.ts` 文件过大，配置读取、第三方调用、业务编排、数据映射耦合在一起
- Web 页面、扩展脚本、后端发布会话之间存在协议字符串和工具函数重复实现
- 业务代码中分散直接读取 `process.env`，默认值与行为不统一
- 历史作品依赖第三方外链资源，导致图片失效后页面预览和一键发布一起失败

### 3.2 当前收敛方向

- 页面做薄，业务编排下沉到 hooks、service、gateway
- 协议和类型共享，避免“前端一份、后端一份、扩展一份”
- 外部依赖统一封装，避免直接在业务流程里散写 `fetch`
- 资源优先落本站可控副本，不依赖临时外链长期存活

## 4. 架构总原则

### 4.1 页面与控制器只做入口编排

- 前端页面负责展示、用户交互、调用服务，不直接承载复杂业务规则
- 后端 controller 负责参数接收和返回，不直接承载复杂业务逻辑
- 复杂逻辑必须下沉到独立 service、gateway、repository、mapper

### 4.2 共享能力必须集中

- 跨前端页面、扩展、后端都会使用的协议、类型、工具函数，优先放入 `packages/shared`
- 不允许同一套协议名称、session 字段、消息类型在三处以上重复硬编码

### 4.3 外部集成必须隔离

- 第三方模型、飞书、浏览器扩展、小红书创作者页都视为外部集成
- 外部集成调用统一放入 gateway 或 adapter，不直接散落在页面或主业务 service 中
- 外部依赖失败必须返回明确中文错误，不允许只透出 `fetch failed`、`Request failed`

### 4.4 文件与资源必须可控

- 所有生成资产优先保存为本站可访问副本或持久化存储
- `works` 这类生成作品资源，生产态优先落 OSS 等对象存储，不再把 `.runtime/generated-works` 作为长期正式持久化目录
- 用户头像、品牌产品图、品牌资料附件、报告 HTML 这类需要长期访问的上传/生成资源，也必须直接落 OSS 等对象存储，不把本地运行目录当正式真源
- 本地开发若未配置 OSS，允许仅在非生产环境回退到 `.runtime` 下的受控本地目录做联调；但 `storageKey`、站内读取接口和资源结构必须保持与 OSS 正式链路一致，不能为本地调试另起一套 URL
- 本地开发环境若发现 Next `/api` 重写代理对长响应 POST / 流式或大报文接口出现 `socket hang up`、`ECONNRESET` 等不稳定问题，浏览器端允许在 `localhost/127.0.0.1` 下直接指向 `127.0.0.1:3011/api`；生产环境则应优先使用受控的同域 API Route / 网关代理，不再依赖脆弱的 rewrite 转发长请求
- 对大模型长耗时报告链路，不允许继续依赖单次同步 HTTP 等待完整产物；若线上存在网关超时风险，必须改为 `创建任务 -> 后台执行 -> 前端轮询 latestTask` 的异步模式
- 不允许仅保存第三方临时 URL 作为长期作品资源
- 发布前必须校验图片、视频等关键资源可访问

## 5. 前端规范

### 5.1 页面拆分规范

- 单个页面超过以下任一条件时，必须拆分：
- 超过 800 行
- 超过 10 个 `useState`
- 超过 5 个轮询/副作用逻辑
- 同时承载“工作区 + 弹窗 + 发布 + 任务轮询 + 作品管理”
- 后台复杂栏目页如果同时包含“筛选区 + 列表区 + 单项详情编辑”，优先拆成独立面板组件，不继续把状态、保存逻辑和弹窗细节堆进单个 `page.tsx`

### 5.2 推荐目录结构

- 页面主入口：`app/.../page.tsx`
- 页面专属子组件：`components/`
- 页面逻辑 hooks：`hooks/`
- 调接口 service：`services/`
- 纯工具：`utils/`

### 5.3 Service 规范

- `services/*.ts` 只负责 HTTP 请求、请求参数整理、响应类型定义
- 不在 service 里写 DOM、弹窗、`window.postMessage`、页面状态逻辑
- 所有接口类型命名保持统一：
- `Get*Response`
- `Create*Payload`
- `Update*Payload`
- `*Record`
- 用户态工作区的 service 不允许把品牌请求默认硬编码到 `DEMO_BRAND_ID`；若接口属于品牌域，默认优先解析当前登录品牌上下文
- 品牌域工作区初始化时，不允许只信任浏览器本地缓存的 `currentBrandId`；首次加载前应优先通过 `/auth/me` 或等价真实接口校正当前登录用户的品牌上下文，避免残留 demo brand 或旧品牌污染后续工作区请求
- 品牌域页面中的媒体代理、附件下载、灯箱预览等二级资源请求，也必须显式透传当前真实 `brandId`；不能因为“主数据已切到真实品牌”就默认允许图片/视频代理继续回退到 `DEMO_BRAND_ID`
- 媒体代理 helper 不允许对任意字符串无脑拼接代理 URL；只有命中受支持的飞书/Lark 附件域名时才走站内代理，普通 `http(s)` 资源保持直出，非法字符串直接过滤为空
- 需要给前端工作区暴露“可选模型 / 可选 Provider”时，不允许继续在页面或组件里写死枚举；必须由后端按后台 `ApiProviderConfig` 的当前激活配置动态下发
- 为排障临时加入的“同步诊断 / 原始字段 / 调试 JSON”类展示，不允许长期默认暴露在正式用户界面；联调结束后必须删除，或至少收口到显式开发开关后再保留

### 5.4 状态与轮询规范

- 轮询逻辑优先抽成通用 hook，如 `useTaskPolling`
- 同类任务状态刷新不允许在多个页面重复复制 `setTimeout + filter + sort`
- 页面状态提示必须区分：
- 本地提交中
- 后端排队中
- 执行中
- 成功
- 失败
- 对单条记录的详情编辑，如果不需要与列表长期并排对照，优先使用弹窗承载详情，而不是在主页面长期保留右侧常驻编辑板块

### 5.5 认证入口规范

- 前台工作台默认视为受保护页面；除明确的公共页外，新增前台页面应统一挂到现有登录门卫下，未登录跳回根页 `/?next=...`
- 根页 `/` 是前台统一认证入口，默认优先展示注册，再允许切换普通登录；不要再新增平行的前台门户页绕开登录
- 后台管理入口与前台账号入口分离；`/admin` 只允许管理员账号进入，普通用户认证入口不要直接复用后台页面
- 注册准入规则以服务端为准；当前基线是“邀请码一次性消费”，不能只在前端做可绕过的展示态限制

### 5.6 列表交互规范

- 同一张数据列表中的主操作按钮应保持统一视觉语言，避免只因按钮文案不同而出现样式不一致
- 列表如果需要给操作区腾空间，优先移除低价值重复列，而不是压缩按钮宽度导致换行或排列错位
- 危险操作不要求在列表中直接使用高风险视觉样式，但进入确认态后必须明确升级为危险操作提示
- 配置中心类列表如果字段包含密钥、Headers、扩展参数或长 URL，默认必须提供搜索/筛选，并对敏感字段做遮挡显示；长 JSON 优先折叠为摘要，避免页面退化为长表单墙

### 5.7 发布与扩展规范

- Web 页与扩展之间只通过统一协议通信
- `window.postMessage` 必须校验 `source`，后续补充 `origin` 白名单
- 扩展连接状态不能只校验 content script，必须同时确认 background/service worker 可响应
- 电脑端一键发布必须有兜底路径，不能完全依赖单一桥接链路
- 发布弹窗如果依赖浏览器扩展，必须同时提供可访问的下载入口、安装说明和权限排查提示，不允许只留源码目录路径给用户自行猜测

## 6. 浏览器扩展规范

### 6.1 权限规范

- `manifest.json` 中的 `host_permissions` 和 `content_scripts.matches` 必须尽量收紧
- 只给真实工作台域名和 `creator.xiaohongshu.com` 必要权限
- 非必要场景不允许对全站 `http://*/*`、`https://*/*` 长期开启注入

### 6.2 协议规范

- 扩展消息类型集中定义到共享协议文件
- 所有消息 payload 必须有稳定字段，不允许临时拼接无类型对象
- content script 与 background 的职责分离：
- content script 只负责页面桥接和 DOM 执行
- background 只负责开页、任务分发、会话解析、结果回写

### 6.3 调试规范

- 创作者页自动化必须保留可见调试状态，如角标或阶段消息
- 扩展失败必须把错误回传到站内页面，不允许只停留在浏览器控制台

## 7. 后端规范

### 7.1 DTO 与校验

- 所有 controller 输入都必须逐步迁移到 DTO
- 开启统一 `ValidationPipe`
- 不允许只写 TypeScript type 就默认视为“已校验”

### 7.2 配置规范

- 环境变量统一收口到配置模块，不允许在业务 service 中散读 `process.env`
- `.env.example` 必须同步维护
- 所有 baseUrl、端口、OAuth、第三方接口配置都应有统一 resolver
- 生产后端监听地址必须可配置，默认优先绑定 `127.0.0.1` 等本机回环地址，不把 Node 业务端口直接暴露到公网
- 同域 `/api` 访问后端时，优先使用受控的 API Route / 网关代理；若必须使用 rewrite，只能用于短平快请求，不能把长响应 POST、流式或大报文接口长期挂在 rewrite 上
- 同域代理即使已经改为 API Route，只要接口本身会等待大模型完整生成结果，也不能把“长耗时问题”只归因于代理层；必须同时检查业务接口是否应该任务化

### 7.3 Service 拆分规范

- 业务主 service 负责编排，不直接承担所有细节
- 推荐拆分：
- `FacadeService`：业务主入口
- `Gateway`：第三方接口调用
- `Repository`：数据库/Mock 适配
- `Mapper`：入参/出参/元数据转换
- `AssetService`：文件落盘、资源缓存、URL 解析

### 7.4 异常与日志规范

- 参数问题使用 `BadRequestException`
- 业务不存在使用 `NotFoundException`
- 外部集成失败使用统一集成异常或清晰的 `ServiceUnavailableException`
- 日志逐步收敛到统一 logger，不再散写 `console.log/error`
- 错误信息必须包含：
- 失败阶段
- 外部 provider 或接口
- 实际尝试顺序（若存在多模型/多 provider fallback）
- 是否可重试
- 删除、解绑、覆盖、重置密码、转移归属这类危险写操作，必须在前端提供确认弹窗或等价二次确认，不允许静默直接执行
- 生产 Web/API 进程不允许长期以 `root` 身份运行；部署可保留 `root` SSH 入口，但实际 `pm2`/Node 运行用户必须切到独立普通账号

### 7.5 数据访问规范

- `Prisma` 与 `mock-data` 双轨逻辑不应继续横向扩散到所有 service
- 新功能优先通过 repository 层收口数据库与 mock 差异
- 业务层不直接处理“数据库可用/不可用”分支细节
- 任何按 `brandId` 读取或写入品牌数据的 controller，都必须先校验当前登录用户是否属于该品牌，不能只依赖前端传入的 `x-brand-id` 或路由参数
- 对第三方模型、图像、视频等运行时配置，业务 service 不允许再直接读取散落的 `.txt`、硬编码模型名或旧 demo provider；统一通过后台 `ApiProviderConfig` + `runtimeKey` 解析
- 报告类与内容生成类链路在读取技能配置中的 `provider` 时，必须校验该 provider 的 `runtimeKey` 是否与当前生成链路兼容；若技能配置填入了图像/视频等不兼容 provider，不允许直接照用，必须自动回退到正确的文本 runtime
- 当后台技能中心已明确指定某条内容生成链路的首选模型时，运行时必须先严格尝试该模型，再继续 fallback；不允许在报错文案里把“最后一次失败模型”误显示成“第一跳模型”
- 对飞书/多维表格这类第三方附件字段，不允许直接把整列 flatten 成 `imageList`；必须先按图片、视频、文档类型分流，再决定前端以图片缩略图、视频播放器还是下载链接呈现
- 对需要 Bearer 鉴权的站内媒体代理地址，不允许直接赋给 `<img>`、`<video>`、灯箱预览或下载链接；这类资源必须先通过前端鉴权请求拉取 blob，再转成 object URL 使用，避免浏览器媒体请求不带登录态导致 401 空白

### 7.6 Mock 模式规范

- 数据库不可用时，mock fallback 仍应尽量保持与正式运行时一致的权限与配置行为
- mock 模式下的登录返回、鉴权上下文、回退用户资料必须沿用 `mock-data` 中的真实 `systemRole`，不能额外硬编码降级，否则后台与前台联调结果会失真

## 8. 资源与作品规范

### 8.1 生成资源

- 新生成的图片、视频、HTML 结果必须优先落本站副本
- 若已接入对象存储，`storageKey` 必须作为正式持久化真源，站内 `/api/.../assets/...` URL 只作为读取入口，不作为“本地文件存在”的证明
- 新增上传型资源时，必须同时定义：
- 明确的 `storageKey` 前缀
- 稳定的站内读取接口
- 删除/覆盖时的 OSS 同步规则
- 作品记录里如果引用第三方 URL，必须同时具备本站可控兜底副本
- 小红书原创/二创成品图不能只在 prompt 文本里口头约束尺寸；凡是对交付比例有明确要求的图片链路，都必须在保存前提供服务端规范化兜底
- 当前小红书图文成品图统一以竖版 `1242x1660` 作为默认基线；如果第三方模型返回横图、方图或接近方图的比例，必须在落盘前先裁切收口，不能直接进入作品库
- 参考图型图片生成链路不能只在前置分析阶段把参考图拆成文字；最终文生图阶段也必须继续把参考图原图透传给模型，避免“拆解过但最终没参考”
- 小红书原创/二创图片链路中，“配图提示词生成”和“最终图片生成”默认视为两个独立技能，不能再把最终图像模型选择混进提示词技能里
- 作品创建弹窗里的发布主体、账号角色等后续仍要参与展示、发布或权限判断的结构化字段，不允许只停留在前端临时状态；必须同步写入作品主记录 `MediaAsset.metadataJson`
- 所有作品创作默认都必须显式设置“账号角色”；不能只在原创链路补字段而让二创、视频或后续新增作品类型缺失同类结构化发布主体信息

### 8.2 发布资源

- 发布会话生成前先校验配图、视频是否可访问
- 如果历史资源失效，必须在站内直接返回明确错误
- 不允许把无效资源继续发给扩展或移动接力页后再失败

## 9. 文档与 Git 规范

### 9.1 文档更新要求

- 每次开始实际开发前，默认先读取 `docs/engineering-standards.md`、`docs/site-map.md`、`docs/site-map-mermaid.md`、`docs/development-delivery-checklist.md` 和当前任务最近的 `docs/changes/*.md`
- 如果本次要修改已有页面、已有工作区或已有业务链路，开始动手前必须额外回看 `docs/site-map.md`、`docs/site-map-mermaid.md` 中对应板块的具体条目，而不只是泛读整份文档
- 若回看基线后发现本次准备采用的实现方式与既有开发思路、页面结构或业务逻辑不一致，必须先向用户确认，再继续开发；不能直接按新的理解覆盖旧实现
- 涉及 Git 边界、提交拆分或快照备份时，额外读取 `docs/git-workflow.md`
- 涉及数据库 schema、迁移或正式入库边界时，额外读取 `docs/database-archive.md`
- 涉及资源生成、作品副本、发布素材时，额外读取 `docs/generated-content-storage-standards.md`
- 涉及个人中心、多用户、品牌协作时，额外读取 `docs/personal-center-multi-user-system-plan.md`
- 任何实际代码改动都要同步更新 `docs/changes/*.md`
- 涉及结构、入口、主链路变化时同步更新 `docs/site-map.md`
- 涉及结构关系和全局关联变化时同步更新 `docs/site-map-mermaid.md`
- 涉及数据库 schema、迁移、正式持久化边界或业务板块入库路径变化时同步更新 `docs/database-archive.md`
- 涉及通用约束变化时同步更新本规范文档
- 前台品牌可见范围默认只认真实 `BrandMember` 关系；不要因为 `SUPER_ADMIN` 或其他后台系统角色，直接把全品牌切换能力透传到前台个人中心或品牌工作区
- 品牌增长策略板块默认视为 `Owner` 专属工作区；凡是品牌档案写入、飞书绑定、品牌增长报告、可视化报告、半年营销规划等策略型入口，新增或调整时都要同时校验前端路由闸门与后端 `Owner` 鉴权
- 团队协作默认采用“邀请确认后加入”模型；不要再引入“直接写入成员立即入组”或“手动输入邀请码加入”的平行链路
- 涉及 Git 边界、暂存策略或备份流程变化时同步更新 `docs/git-workflow.md`
- 涉及开发流程、交付闭环、记录清单变化时同步更新 `docs/development-delivery-checklist.md`
- 涉及文档索引、新增文档类型或“开发前必读 / 开发后必更”入口说明变化时同步更新 `docs/README.md`
- 更新 `docs/site-map.md` 时，相关板块要把本次对应的 `docs/changes/*.md` 作为“参考变更”挂到相应位置，避免后续只知道结构结果，不知道是哪次变更带来的
- 用户只说“更新一下”时，默认按完整交付闭环执行：同步更新开发规范、Git 备份、文字网站地图、Mermaid 网站地图、变更记录，并在交付时说明验证结果与未纳入提交的剩余改动

### 9.2 提交规范

- GitHub Actions 或其他自动部署脚本在执行 `git pull` 前，必须先校验服务器工作区 `git status --porcelain -uall` 为空；一旦发现未收口改动或额外文件，部署必须直接失败并要求人工排查
- 自动部署完成后，必须补本机健康检查与端口检查，确认 `3001/3011` 仅对 `127.0.0.1` 监听，不允许再次直接暴露到公网
- 自动部署中的健康检查如果依赖刚重启的 Web/API 进程，必须带有限等待窗口与重试，不允许只做一次立即 `curl` 就把“启动中”误判成部署失败
- 如果服务器仓库目录已经收口到普通运行用户，部署脚本中的 `git fetch`、`git checkout`、`git status`、`git pull` 也必须切到同一普通用户执行，不允许再由 `root` 直接操作该仓库触发 `dubious ownership`
- 如果部署中的 Git 拉取依赖 SSH 私钥，切到普通运行用户后还必须同步准备该用户自己的 `~/.ssh`、`known_hosts` 与对应 Deploy Key/SSH config；不能默认复用 `root` 的 SSH 上下文
- 如果业务依赖 seed 数据才能正常工作，部署脚本不能只执行 `prisma db push`；必须显式补对应的目标化 seed 步骤，并避免在生产环境默认运行会覆盖 demo 用户、品牌或演示任务的整套 seed
- 如果业务依赖第三方运行时密钥，部署脚本必须把对应 GitHub Secrets 显式传给远端运行用户和 `pm2 startOrReload --update-env`；不能假设远端 shell、旧 PM2 进程或历史登录态会自动保留这些环境变量
- 如果 `PM2` 通过 `ecosystem.config.*` 启动应用，关键运行时密钥还必须在 `ecosystem` 的 `env` 中显式映射自 `process.env`，不能只把 Secret 放在触发 `pm2` 的临时 shell 里
- 关键运行时密钥完成 `pm2 startOrReload --update-env` 后，部署脚本必须再做一次“进程内是否真实存在该环境变量”的校验；缺失时直接让部署失败，不接受“工作流成功、运行态缺 Secret”的假成功

- 一个提交只解决一类问题
- 提交前至少完成相关构建或诊断验证
- 不把无关改动混入同一提交
- 如果工作区已经存在无关改动，必须显式缩小 `git add` 范围，只提交本次任务涉及的文件，并在交付记录里注明剩余改动为什么未纳入
- 提交信息建议使用：
- `feat:`
- `fix:`
- `refactor:`
- `docs:`
- `chore:`

### 9.3 开发交付规范

- 每次开始开发前，必须先明确任务标题、任务类型、目标板块、影响范围、代码落点、验证方式和 Git 边界
- 如果任务会修改已有内容，必须把“对应网站地图条目 + 最近相关变更记录 + 与现有实现是否一致”一并核对清楚
- 若实现过程中确认需要偏离既有结构、交互或数据链路，先暂停并询问用户，不得自行改道
- 每次结束开发后，必须补齐验证结果、文档更新、Git 备份信息和待解决事项
- 上述清单统一以 `docs/development-delivery-checklist.md` 作为默认执行模板
- 没有范围说明、没有验证方式、没有文档更新或没有 Git 边界说明的任务，不视为完整闭环
- 本规则适用于开发过程中的每一步，而不是只在收到“继续”这类指令时才启用
- 任何新的排查、修改、验证、提交、交接动作，都默认重新经过这套交付检查
- 若用户未逐项展开而只说“更新一下”，也视为要求执行这套闭环，不再等待额外提醒
