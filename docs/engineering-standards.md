# AI全域运营系统开发规范

## 1. 目标

- 让后续开发在同一套架构边界、命名习惯和交付流程下推进
- 降低“功能能跑但不可维护”“局部修好后其他链路再次出错”的概率
- 把当前代码中已经暴露出的热点问题，提前固化为明确约束

## 2. 适用范围

- `apps/web`
- `apps/server`
- `apps/web/public/extensions/xhs-draft-publisher`
- `packages/shared`
- `docs`

## 3. 当前重点问题

### 3.1 已暴露热点

- `xiaohongshu/page.tsx` 职责过多，集成了工作区、作品管理、发布、轮询和弹窗状态
- `works.service.ts`、`collectors.service.ts`、`reports.service.ts` 文件过大，配置读取、第三方调用、业务编排、数据映射耦合在一起
- Web 页面、扩展脚本、后端发布会话之间存在协议字符串和工具函数重复实现
- 业务代码中分散直接读取 `process.env`，默认值与行为不统一
- 历史作品依赖第三方外链资源，导致图片失效后页面预览和一键发布一起失败

### 3.2 当前收敛方向

- 页面做薄，业务编排下沉到 hooks、service、gateway
- 协议和类型共享，避免“前端一份、后端一份、扩展一份”
- 外部依赖统一封装，避免直接在业务流程里散写 `fetch`
- 资源优先落本站可控副本，不依赖临时外链长期存活

## 4. 架构总原则

### 4.1 页面与控制器只做入口编排

- 前端页面负责展示、用户交互、调用服务，不直接承载复杂业务规则
- 后端 controller 负责参数接收和返回，不直接承载复杂业务逻辑
- 复杂逻辑必须下沉到独立 service、gateway、repository、mapper

### 4.2 共享能力必须集中

- 跨前端页面、扩展、后端都会使用的协议、类型、工具函数，优先放入 `packages/shared`
- 不允许同一套协议名称、session 字段、消息类型在三处以上重复硬编码

### 4.3 外部集成必须隔离

- 第三方模型、飞书、浏览器扩展、小红书创作者页都视为外部集成
- 外部集成调用统一放入 gateway 或 adapter，不直接散落在页面或主业务 service 中
- 外部依赖失败必须返回明确中文错误，不允许只透出 `fetch failed`、`Request failed`

### 4.4 文件与资源必须可控

- 所有生成资产优先保存为本站可访问副本或持久化存储
- `works` 这类生成作品资源，生产态优先落 OSS 等对象存储，不再把 `.runtime/generated-works` 作为长期正式持久化目录
- 用户头像、品牌产品图、品牌资料附件、报告 HTML 这类需要长期访问的上传/生成资源，也必须直接落 OSS 等对象存储，不把本地运行目录当正式真源
- 不允许仅保存第三方临时 URL 作为长期作品资源
- 发布前必须校验图片、视频等关键资源可访问

## 5. 前端规范

### 5.1 页面拆分规范

- 单个页面超过以下任一条件时，必须拆分：
- 超过 800 行
- 超过 10 个 `useState`
- 超过 5 个轮询/副作用逻辑
- 同时承载“工作区 + 弹窗 + 发布 + 任务轮询 + 作品管理”
- 后台复杂栏目页如果同时包含“筛选区 + 列表区 + 单项详情编辑”，优先拆成独立面板组件，不继续把状态、保存逻辑和弹窗细节堆进单个 `page.tsx`

### 5.2 推荐目录结构

- 页面主入口：`app/.../page.tsx`
- 页面专属子组件：`components/`
- 页面逻辑 hooks：`hooks/`
- 调接口 service：`services/`
- 纯工具：`utils/`

### 5.3 Service 规范

- `services/*.ts` 只负责 HTTP 请求、请求参数整理、响应类型定义
- 不在 service 里写 DOM、弹窗、`window.postMessage`、页面状态逻辑
- 所有接口类型命名保持统一：
- `Get*Response`
- `Create*Payload`
- `Update*Payload`
- `*Record`
- 用户态工作区的 service 不允许把品牌请求默认硬编码到 `DEMO_BRAND_ID`；若接口属于品牌域，默认优先解析当前登录品牌上下文

### 5.4 状态与轮询规范

- 轮询逻辑优先抽成通用 hook，如 `useTaskPolling`
- 同类任务状态刷新不允许在多个页面重复复制 `setTimeout + filter + sort`
- 页面状态提示必须区分：
- 本地提交中
- 后端排队中
- 执行中
- 成功
- 失败
- 对单条记录的详情编辑，如果不需要与列表长期并排对照，优先使用弹窗承载详情，而不是在主页面长期保留右侧常驻编辑板块

### 5.5 列表交互规范

- 同一张数据列表中的主操作按钮应保持统一视觉语言，避免只因按钮文案不同而出现样式不一致
- 列表如果需要给操作区腾空间，优先移除低价值重复列，而不是压缩按钮宽度导致换行或排列错位
- 危险操作不要求在列表中直接使用高风险视觉样式，但进入确认态后必须明确升级为危险操作提示

### 5.6 发布与扩展规范

- Web 页与扩展之间只通过统一协议通信
- `window.postMessage` 必须校验 `source`，后续补充 `origin` 白名单
- 扩展连接状态不能只校验 content script，必须同时确认 background/service worker 可响应
- 电脑端一键发布必须有兜底路径，不能完全依赖单一桥接链路

## 6. 浏览器扩展规范

### 6.1 权限规范

- `manifest.json` 中的 `host_permissions` 和 `content_scripts.matches` 必须尽量收紧
- 只给真实工作台域名和 `creator.xiaohongshu.com` 必要权限
- 非必要场景不允许对全站 `http://*/*`、`https://*/*` 长期开启注入

### 6.2 协议规范

- 扩展消息类型集中定义到共享协议文件
- 所有消息 payload 必须有稳定字段，不允许临时拼接无类型对象
- content script 与 background 的职责分离：
- content script 只负责页面桥接和 DOM 执行
- background 只负责开页、任务分发、会话解析、结果回写

### 6.3 调试规范

- 创作者页自动化必须保留可见调试状态，如角标或阶段消息
- 扩展失败必须把错误回传到站内页面，不允许只停留在浏览器控制台

## 7. 后端规范

### 7.1 DTO 与校验

- 所有 controller 输入都必须逐步迁移到 DTO
- 开启统一 `ValidationPipe`
- 不允许只写 TypeScript type 就默认视为“已校验”

### 7.2 配置规范

- 环境变量统一收口到配置模块，不允许在业务 service 中散读 `process.env`
- `.env.example` 必须同步维护
- 所有 baseUrl、端口、OAuth、第三方接口配置都应有统一 resolver
- 生产后端监听地址必须可配置，默认优先绑定 `127.0.0.1` 等本机回环地址，不把 Node 业务端口直接暴露到公网

### 7.3 Service 拆分规范

- 业务主 service 负责编排，不直接承担所有细节
- 推荐拆分：
- `FacadeService`：业务主入口
- `Gateway`：第三方接口调用
- `Repository`：数据库/Mock 适配
- `Mapper`：入参/出参/元数据转换
- `AssetService`：文件落盘、资源缓存、URL 解析

### 7.4 异常与日志规范

- 参数问题使用 `BadRequestException`
- 业务不存在使用 `NotFoundException`
- 外部集成失败使用统一集成异常或清晰的 `ServiceUnavailableException`
- 日志逐步收敛到统一 logger，不再散写 `console.log/error`
- 错误信息必须包含：
- 失败阶段
- 外部 provider 或接口
- 是否可重试
- 删除、解绑、覆盖、重置密码、转移归属这类危险写操作，必须在前端提供确认弹窗或等价二次确认，不允许静默直接执行
- 生产 Web/API 进程不允许长期以 `root` 身份运行；部署可保留 `root` SSH 入口，但实际 `pm2`/Node 运行用户必须切到独立普通账号

### 7.5 数据访问规范

- `Prisma` 与 `mock-data` 双轨逻辑不应继续横向扩散到所有 service
- 新功能优先通过 repository 层收口数据库与 mock 差异
- 业务层不直接处理“数据库可用/不可用”分支细节
- 任何按 `brandId` 读取或写入品牌数据的 controller，都必须先校验当前登录用户是否属于该品牌，不能只依赖前端传入的 `x-brand-id` 或路由参数

## 8. 资源与作品规范

### 8.1 生成资源

- 新生成的图片、视频、HTML 结果必须优先落本站副本
- 若已接入对象存储，`storageKey` 必须作为正式持久化真源，站内 `/api/.../assets/...` URL 只作为读取入口，不作为“本地文件存在”的证明
- 新增上传型资源时，必须同时定义：
- 明确的 `storageKey` 前缀
- 稳定的站内读取接口
- 删除/覆盖时的 OSS 同步规则
- 作品记录里如果引用第三方 URL，必须同时具备本站可控兜底副本
- 小红书原创/二创成品图不能只在 prompt 文本里口头约束尺寸；凡是对交付比例有明确要求的图片链路，都必须在保存前提供服务端规范化兜底
- 当前小红书图文成品图统一以竖版 `1242x1660` 作为默认基线；如果第三方模型返回横图、方图或接近方图的比例，必须在落盘前先裁切收口，不能直接进入作品库

### 8.2 发布资源

- 发布会话生成前先校验配图、视频是否可访问
- 如果历史资源失效，必须在站内直接返回明确错误
- 不允许把无效资源继续发给扩展或移动接力页后再失败

## 9. 文档与 Git 规范

### 9.1 文档更新要求

- 每次开始实际开发前，默认先读取 `docs/engineering-standards.md`、`docs/site-map.md`、`docs/site-map-mermaid.md`、`docs/development-delivery-checklist.md` 和当前任务最近的 `docs/changes/*.md`
- 涉及 Git 边界、提交拆分或快照备份时，额外读取 `docs/git-workflow.md`
- 涉及数据库 schema、迁移或正式入库边界时，额外读取 `docs/database-archive.md`
- 涉及资源生成、作品副本、发布素材时，额外读取 `docs/generated-content-storage-standards.md`
- 涉及个人中心、多用户、品牌协作时，额外读取 `docs/personal-center-multi-user-system-plan.md`
- 任何实际代码改动都要同步更新 `docs/changes/*.md`
- 涉及结构、入口、主链路变化时同步更新 `docs/site-map.md`
- 涉及结构关系和全局关联变化时同步更新 `docs/site-map-mermaid.md`
- 涉及数据库 schema、迁移、正式持久化边界或业务板块入库路径变化时同步更新 `docs/database-archive.md`
- 涉及通用约束变化时同步更新本规范文档
- 涉及 Git 边界、暂存策略或备份流程变化时同步更新 `docs/git-workflow.md`
- 涉及开发流程、交付闭环、记录清单变化时同步更新 `docs/development-delivery-checklist.md`
- 涉及文档索引、新增文档类型或“开发前必读 / 开发后必更”入口说明变化时同步更新 `docs/README.md`
- 用户只说“更新一下”时，默认按完整交付闭环执行：同步更新开发规范、Git 备份、文字网站地图、Mermaid 网站地图、变更记录，并在交付时说明验证结果与未纳入提交的剩余改动

### 9.2 提交规范

- GitHub Actions 或其他自动部署脚本在执行 `git pull` 前，必须先校验服务器工作区 `git status --porcelain -uall` 为空；一旦发现未收口改动或额外文件，部署必须直接失败并要求人工排查
- 自动部署完成后，必须补本机健康检查与端口检查，确认 `3001/3011` 仅对 `127.0.0.1` 监听，不允许再次直接暴露到公网

- 一个提交只解决一类问题
- 提交前至少完成相关构建或诊断验证
- 不把无关改动混入同一提交
- 如果工作区已经存在无关改动，必须显式缩小 `git add` 范围，只提交本次任务涉及的文件，并在交付记录里注明剩余改动为什么未纳入
- 提交信息建议使用：
- `feat:`
- `fix:`
- `refactor:`
- `docs:`
- `chore:`

### 9.3 开发交付规范

- 每次开始开发前，必须先明确任务标题、任务类型、目标板块、影响范围、代码落点、验证方式和 Git 边界
- 每次结束开发后，必须补齐验证结果、文档更新、Git 备份信息和待解决事项
- 上述清单统一以 `docs/development-delivery-checklist.md` 作为默认执行模板
- 没有范围说明、没有验证方式、没有文档更新或没有 Git 边界说明的任务，不视为完整闭环
- 本规则适用于开发过程中的每一步，而不是只在收到“继续”这类指令时才启用
- 任何新的排查、修改、验证、提交、交接动作，都默认重新经过这套交付检查
- 若用户未逐项展开而只说“更新一下”，也视为要求执行这套闭环，不再等待额外提醒

## 10. 当前整改优先级

### P0

- 建立统一配置模块，收口环境变量读取
- 引入 DTO + ValidationPipe
- 建立共享扩展协议与共享 session 类型
- 新生成作品资源统一缓存到本站副本

### P1

- 拆分 `xiaohongshu/page.tsx`
- 抽离统一任务轮询 hook
- 收敛扩展权限与注入范围
- 引入统一日志与异常过滤

### P2

- 拆分 `works.service.ts`、`collectors.service.ts`、`reports.service.ts`
- 收敛 Prisma 与 mock 双轨分支到 repository 层
- 清理重复工具函数并迁移到 `packages/shared`

## 11. 未来开发默认执行规则

- 新功能先判断是否已有相同能力可复用，再决定新增代码位置
- 新协议先放共享层，再接页面、后端、扩展
- 新资源先考虑长期可访问性，再决定存储方案
- 新页面优先做小组件组合，不再持续扩大单文件页面
- 新异常先想清“用户能否看懂”，再决定错误文案
- 新提交默认同时补文档，不再事后回补
- 用户口头提到“更新一下”时，默认联动开发规范、Git 备份、网站地图、变更记录四类文档，不把它理解为单一文件更新
