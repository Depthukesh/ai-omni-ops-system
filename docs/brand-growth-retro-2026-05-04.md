## 2. 产品目标回顾

从原始需求看，这套产品不是单点内容生成器，而是一套“品牌建档 -> 数据收集 -> 报告生成 -> 内容生产 -> 个人沉淀 -> 后台运营”的多用户 AI 全域运营系统。

当前项目已经明确收口到 MVP 阶段，核心目标不是继续横向扩模块，而是先跑通以下闭环：

1. 品牌资料库
2. 小红书收集数据
3. 品牌增长报告
4. 品牌增长可视化报告
5. 个人中心可见内容
6. 后台基础运营能力

这一步非常关键，因为它决定了项目从“概念很多、范围很大”切换到了“先让主链路稳定可演示”的正确方向。

## 3. 阶段进展回顾

### 3.1 阶段一：产品骨架和品牌增长工作台成型

当前前端已经形成完整的品牌增长工作台，主页面集中在 `apps/web/src/app/(dashboard)/brand-growth/workspace.tsx`。

已落地的页面骨架包括：

- 品牌背景资料
- 产品资料库
- 品牌运营情况调研
- 第三方数据
- 企业经营数据
- 收集数据
- 品牌增长报告
- 品牌增长可视化报告
- 全年营销规划占位

这说明前端不再是静态原型，而是已经形成“工作台式产品容器”，可以承载真实数据和真实操作。

### 3.2 阶段二：飞书集成从“平台代管”转向“用户自有应用”

这是整个项目里最重要的一次架构纠偏之一。

当前实现已经具备：

- 用户填写自己的 `App ID / App Secret`
- 系统发起用户级 Feishu OAuth
- OAuth 状态查询
- Token 持久化到 `UserFeishuIntegration`
- 品牌绑定飞书副本链接
- 通过用户自己的授权读取飞书表

这一步的价值非常大：

- 避免平台统一应用模式带来的多租户安全与权限边界问题
- 符合正式产品中“最终用户自己授权”的产品要求
- 为后续多用户扩展打下正确基础

### 3.3 阶段三：飞书副本同步链路跑通

当前飞书同步已经不只是“能授权”，而是进入到真实数据同步阶段。

现状包括：

- 能根据品牌绑定读取飞书副本
- 能匹配并同步品牌账号、竞品账号、品牌作品、对标作品等表
- 同步前会清理旧的小红书结果资产，改为全量覆盖
- 同步后可回写同步状态
- 图片和视频附件已通过本站后端代理访问
- Token 失效时支持刷新并重试

这一阶段说明产品已经从“配置和连接”走到“数据进站”的关键节点。

### 3.4 阶段四：品牌增长报告链路跑通

当前品牌增长报告已经形成完整链路：

- 读取品牌档案
- 读取小红书收集工作台
- 调用模型生成结构化增长报告
- 写入任务、媒体资产、业务资产
- 前端支持读取与编辑保存

从产品视角看，这意味着“品牌资料不是只存着”，而是已经能转化成第一份 AI 产出物，即《品牌增长报告》。

### 3.5 阶段五：品牌增长可视化报告经历多轮修正后稳定

这是近期最复杂、也最有代表性的研发过程。

可视化报告链路经历了几个阶段：

1. 先尝试模型直接输出完整 HTML
2. 遇到模型超时、JSON 解析失败、HTML 截断、任务长期 RUNNING 等问题
3. 增加异步任务、失败原因展示、超时回收、返回内容校验
4. 恢复你提供的 `article-visual-report-designer` 技能后，再次遇到内容过长导致 `finish_reason = length`
5. 最终改成“两步生成”：
   - 第一步：模型输出结构化大纲 JSON
   - 第二步：后端模板渲染成 HTML

这一轮调整的意义非常大：

- 保住了你提供的技能内容和审美方向
- 避开了国内模型在单次长 HTML 输出上的长度瓶颈
- 让可视化报告从“不稳定偶发成功”变成“可重复成功”

### 3.6 阶段六：后台管理台具备基础运营能力

当前后台不是空壳，已经有一套可用的管理台基础能力。

前后端都已存在的模块包括：

- 订单管理
- 会员/积分规则
- 用户管理
- API/模型消耗
- 技能/提示词
- 知识库管理
- API Providers

这说明系统已经开始具备“系统运营层”，而不是只有用户前台。

## 5. 做得好的地方

### 5.1 最重要的好：范围收口正确

这个项目最值得肯定的地方，不是“做了很多页面”，而是及时把范围收口到 MVP 主链路，避免了继续无限扩功能。

如果没有这一步，项目很容易变成：

- 页面越做越多
- 每条链路都半通不通
- 最终没有任何一条链路可演示

而现在已经至少形成了一条可解释的主线：

品牌建档 -> 飞书同步 -> 小红书数据展示 -> 品牌增长报告 -> 品牌增长可视化报告

### 5.2 第二个好：飞书授权架构改对了

从“统一平台应用 / 本机 CLI 授权”切到“用户自有应用 + 用户自有 OAuth”，这是一次非常关键的正确决策。

这意味着：

- 产品架构和正式上线模式一致
- 权限边界更清晰
- 多用户可扩展性更强
- 合规性更好

### 5.3 第三个好：前后端闭环不是假数据闭环

很多项目会停留在前端演示或 seed 数据阶段，但本项目已经推进到：

- 有真实 API
- 有真实数据库模型
- 有真实任务记录
- 有真实飞书同步
- 有真实模型调用

这说明它不是“PPT 产品”，而是已经进入真正系统开发状态。

### 5.4 第四个好：对失败的处理逐步成熟

最近这轮可视化报告联调，虽然过程很曲折，但体现出一个优点：

- 没有把失败掩盖掉
- 而是不断把失败显式化、结构化、可定位化

例如：

- 任务异步化
- `QUEUED / RUNNING / FAILED / SUCCESS`
- 超时回收
- 错误原因回写
- `finish_reason = length` 拦截
- 半截 HTML 不再伪装成成功

这类能力是产品后期稳定性的基础。

### 5.5 第五个好：可视化报告最终找到正确工程解法

直接让模型吐完整 HTML，在理想状态下看起来最自由，但在工程上最不稳定。

最终切到“两步生成”，说明当前研发思路开始从“追求一次成功的效果”转向“追求长期可运行的架构”。

这是一种明显的工程成熟度提升。

## 6. 当前存在的问题

下面按优先级划分。

### 6.1 P0 问题：直接影响 MVP 完整演示

#### P0-1 全年营销规划尚未实现

问题：

- 页面已有入口，但只有静态占位
- 后端未见对应生成链路

影响：

- 品牌增长策略板块的第三份核心产物缺失
- 后续小红书营销策划方案和营销日历缺少上游输入

建议方案：

- 先按最小闭环补一版 `GET / POST / PATCH`
- 输入先使用“品牌建档 + 品牌增长报告”
- 输出先固定为 HTML 表格版本
- 不要一开始做复杂交互，先把生成链路跑通

#### P0-2 品牌增长报告输入不完整

问题：

- 当前报告模型输入主要来自品牌背景、产品、调研和小红书数据
- 行业报告与企业经营资料虽然已存储，但未真正进入模型输入

影响：

- 报告深度和商业判断可能明显偏弱
- 难以达到原始需求中“经营诊断 + 增长策略 + ROI 逻辑”的目标

建议方案：

- 在 `buildGrowthAnalysisInput()` 中显式加入：
  - `industryFeeds`
  - `businessAssets`
- 先做摘要抽取而不是全量直塞
- 为不同资料类型设定长度预算，避免 prompt 爆炸

#### P0-3 多品牌能力尚未真正打开

问题：

- 前端工作台仍固定使用 `DEMO_BRAND_ID`

影响：

- 虽然数据库是多品牌结构，但前台体验仍像单品牌演示站

建议方案：

- 将品牌增长页改为路由参数模式，例如 `/brand-growth/[brandId]`
- 增加品牌切换入口
- 所有 services 去掉默认 demo id 的隐式依赖

### 6.2 P1 问题：影响系统稳定性和后续扩展

#### P1-1 任务执行还不是正式队列

问题：

- 报告异步任务当前通过应用进程内 `setTimeout(..., 0)` 启动

影响：

- 进程重启后任务状态一致性风险较高
- 后续并发增大时不可控

建议方案：

- 接入真正的任务队列
- 建议优先选择：
  - `BullMQ + Redis`
- 任务表负责记录状态
- 队列负责执行、重试、超时、并发控制

#### P1-2 Controller 临时直接 new Service

问题：

- 多个 Controller 中存在为绕过 `start:dev` 注入问题而直接 new Service 的代码

影响：

- 依赖注入关系不规范
- 测试和维护成本高
- 后续模块化扩展容易出问题

建议方案：

- 统一恢复为标准 Nest DI
- 优先排查 PrismaService 和模块 import/export 关系
- 清掉 Controller 中的临时构造代码

#### P1-3 报告产物存储还没闭环

问题：

- 当前报告媒体与业务资产里记录的 `fileUrl/sourceUrl` 仍是示例占位地址

影响：

- 系统层面缺少真正的文件资产闭环
- 后续分享、下载、归档会受影响

建议方案：

- 短期：接入本地磁盘或项目内静态存储
- 中期：接入 OSS / S3
- 长期：把报告产物、附件代理、图片沉淀统一抽象到媒体服务层

#### P1-4 自动化测试不足

问题：

- 当前这几条关键链路几乎没有看到对应自动化测试

影响：

- 每次修 bug 容易带出新回归
- 对“页面又坏了”“又变回演示数据”这类问题缺少保护

建议方案：

- 先补最小但高价值测试：
  - 报告生成结果解析测试
  - 可视化任务状态流转测试
  - 飞书 OAuth 状态解析测试
  - 飞书同步字段映射测试

### 6.3 P2 问题：影响产品完整度和精细体验

#### P2-1 全年营销规划、小红书后续模块未真正接上

问题：

- 小红书营销策划方案、营销日历、原创/二创/视频笔记等链路尚未形成完整实现

建议方案：

- 先围绕已完成的品牌增长主链路，按“营销策划方案 -> 营销日历 -> 作品生成”顺序继续推进

#### P2-2 后台部分页面仍保留 seed fallback

问题：

- 后台管理页在 API 失败时会退回 seed 数据

影响：

- 管理者可能误把演示数据当真实数据

建议方案：

- 后台改为“接口异常提示 + 空态”
- 保留 seed 仅限开发专用开关，不要作为默认回退

#### P2-3 可视化报告稳定性提升了，但风格自由度被模板收束

问题：

- 两步生成方案更稳，但目前模板审美仍偏统一

影响：

- 与技能自由直出相比，视觉差异性和创意弹性偏弱

建议方案：

- 把模板继续分层：
  - 商业分析模板
  - 品牌诊断模板
  - 年度规划模板
- 模型输出不仅给内容，还输出风格变量
- 由后端模板系统读取主题色、区块密度、图表风格

## 7. 从前端到后端的完整判断

### 7.1 前端判断

当前前端已经具备“工作台级别”的组织能力，尤其在品牌增长策略板块上，已经不再是简单页面堆叠，而是：

- 有步骤感
- 有状态流
- 有结果展示
- 有错误提示
- 有报告预览

这说明前端主工作台方向是正确的。

当前最需要的不是“大改版”，而是继续补齐：

- 多品牌能力
- 全年营销规划
- API 失败时不回退 seed
- 后续模块联动

### 7.2 后端判断

当前后端已经具备“系统骨架 + 业务骨架 + 生成链路”的三层结构：

- 系统层：Prisma、Task、Media、Admin、Auth
- 业务层：Brands、Collectors、Reports
- 生成层：模型调用、提示词读取、报告落库

这说明后端已经不只是接口拼装，而是有比较明确的业务边界。

当前最需要的不是继续扩新模块，而是继续做“稳定化工程”：

- 标准 DI
- 队列化
- 真实媒体存储
- 更完整输入
- 自动化测试
