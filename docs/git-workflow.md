# Git 版本记录规则

## 1. 目标

Git 在本项目中的作用不是“备份一下代码”，而是：

1. 能回看每次修改到底改了什么
2. 能定位某个问题是从哪次改动开始出现的
3. 能知道每次提交背后的业务目标和设计意图

## 2. 基本规则

- 每次重要改动都要提交，不长期堆积大量未提交修改
- 提交前先确认代码可运行、关键链路已验证
- 提交前默认先完成本项目“开发前必读”基线：`docs/engineering-standards.md`、`docs/site-map.md`、`docs/site-map-mermaid.md`、`docs/development-delivery-checklist.md` 和当前任务最近的 `docs/changes/*.md`
- 提交时同步补充 `docs/changes/*.md`
- 涉及结构变化时同步更新 `docs/site-map.md`
- 涉及结构关系变化时同步更新 `docs/site-map-mermaid.md`
- 如果工作区里已有无关改动，必须按文件边界缩小暂存范围，不能把其他任务的修改混进本次备份
- 用户只说“更新一下”时，默认包含本次 Git 备份；不能只更新文档而不做版本留痕

## 3. 推荐提交流程

### 3.1 功能型改动

1. 改代码
2. 自测或接口验证
3. 写变更记录
4. `git add`
5. `git commit`

### 3.3 混合工作区改动

1. 先用 `git status --short` 确认当前有哪些已修改文件
2. 划清哪些文件属于本次任务，哪些属于其他任务或用户未完成修改
3. 只对本次任务相关文件执行 `git add <paths...>`
4. 提交说明里写清这次备份覆盖的范围
5. 交付说明里补充剩余未纳入提交的文件和原因
6. 若本次是按“更新一下”执行默认闭环，需同时确认规范文档、网站地图、Mermaid 地图、变更记录是否已一并纳入备份范围

### 3.4 快照备份建议

1. 在大批量暂存、拆分提交或首次推送远端前，优先先做一次时间戳快照
2. 快照优先打包 Git 视角下的源码文件，避免把 `.runtime` 等运行中日志一起打入导致压缩失败
3. 快照命名建议带日期和用途，例如 `ai-omni-ops-system-YYYY-MM-DD-git-snapshot.zip`
4. 快照不能替代 Git 提交，但可以作为提交前的回滚保险

### 3.5 自动部署工作区检查

1. GitHub Actions 或其他服务器自动部署，在执行 `git pull` 之前必须先检查服务器工作区是否干净
2. 最低要求是执行 `git status --porcelain -uall`
3. 一旦发现 tracked 文件被改动、或仓库内出现未跟踪额外文件，部署必须直接失败
4. 不能用自动部署去“顺手覆盖”服务器现场，更不能假设 GitHub 仓库干净就代表服务器运行目录也干净
5. 如果服务器存在异常文件，必须先人工排查、隔离和记录，再决定是否继续部署

### 3.2 修 Bug 改动

1. 先记录问题现象
2. 修复代码
3. 验证问题已消失
4. 在变更记录里写清根因和验证方式
5. 再提交

## 4. 推荐提交粒度

- 一个提交只解决一类问题
- 不把“文档整理、前端样式、后端修复、配置调整”全部混进同一个提交
- 如果是同一条链路的连续小修，可以合并成一个阶段性提交
- 如果同一条链路同时涉及代码、样式和文档，可以作为同一阶段性提交；但无关板块仍不能一起混入

## 5. 推荐提交信息格式

建议使用：

- `docs: 建立全站地图与变更记录体系`
- `fix: 修复每日热点定时任务启动与补跑`
- `feat: 接入小红书营销日历继续生成`
- `refactor: 抽离统一 scheduler 模块`
- `chore: 收敛 gitignore 与本地运行文件`

## 6. 首次基线提交建议

首次提交建议作为“当前项目基线”，用于标记系统已进入可追踪状态。

推荐信息：

- `chore: 初始化仓库并建立文档与版本记录规范`

## 7. 当前需要用户配合的信息

首次正式提交前，需要确认两项 Git 身份信息：

1. `user.name`
2. `user.email`

这两个值可以是你常用的 Git 身份，也可以只用于本项目的本地身份。
