# Git 版本记录规则

## 1. 目标

Git 在本项目中的作用不是“备份一下代码”，而是：

1. 能回看每次修改到底改了什么
2. 能定位某个问题是从哪次改动开始出现的
3. 能知道每次提交背后的业务目标和设计意图

## 2. 基本规则

- 每次重要改动都要提交，不长期堆积大量未提交修改
- 提交前先确认代码可运行、关键链路已验证
- 提交时同步补充 `docs/changes/*.md`
- 涉及结构变化时同步更新 `docs/site-map.md`

## 3. 推荐提交流程

### 3.1 功能型改动

1. 改代码
2. 自测或接口验证
3. 写变更记录
4. `git add`
5. `git commit`

### 3.2 修 Bug 改动

1. 先记录问题现象
2. 修复代码
3. 验证问题已消失
4. 在变更记录里写清根因和验证方式
5. 再提交

## 4. 推荐提交粒度

- 一个提交只解决一类问题
- 不把“文档整理、前端样式、后端修复、配置调整”全部混进同一个提交
- 如果是同一条链路的连续小修，可以合并成一个阶段性提交

## 5. 推荐提交信息格式

建议使用：

- `docs: 建立全站地图与变更记录体系`
- `fix: 修复每日热点定时任务启动与补跑`
- `feat: 接入小红书营销日历继续生成`
- `refactor: 抽离统一 scheduler 模块`
- `chore: 收敛 gitignore 与本地运行文件`

## 6. 首次基线提交建议

首次提交建议作为“当前项目基线”，用于标记系统已进入可追踪状态。

推荐信息：

- `chore: 初始化仓库并建立文档与版本记录规范`

## 7. 当前需要用户配合的信息

首次正式提交前，需要确认两项 Git 身份信息：

1. `user.name`
2. `user.email`

这两个值可以是你常用的 Git 身份，也可以只用于本项目的本地身份。
