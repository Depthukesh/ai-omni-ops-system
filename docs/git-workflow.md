# Git 版本记录规则

## 1. 目标

Git 在本项目中的作用不是“做一次备份”，而是：

1. 让每次改动都能回看背景和范围
2. 让问题能追到具体提交
3. 让代码、文档和验证结果一起留痕

## 2. 当前默认规则

- 一个提交只解决一类问题
- 提交前先确认关键链路已验证
- 提交前默认先读：
  - `docs/README.md`
  - `docs/engineering-standards.md`
  - `docs/site-map.md`
  - `docs/site-map-mermaid.md`
  - `docs/development-delivery-checklist.md`
  - 最近相关的 `docs/changes/*.md`
- 提交前同步补 `docs/changes/*.md`
- 涉及结构变化时同步更新 `docs/site-map.md`
- 涉及结构关系变化时同步更新 `docs/site-map-mermaid.md`
- 涉及数据边界变化时同步更新 `docs/database-archive.md`
- 工作区已有无关改动时，必须缩小 `git add` 范围，不能把其他任务混进来

## 3. 推荐提交流程

### 3.1 功能或修复

1. 明确范围
2. 改代码
3. 做验证
4. 补文档
5. `git add` 仅本次相关文件
6. `git commit`

### 3.2 混合工作区

1. 先看 `git status --short`
2. 划清哪些文件属于本次任务
3. 只暂存本次任务文件
4. 提交说明里写清范围
5. 交付说明里写清未纳入提交的剩余改动和原因

### 3.3 快照备份

1. 在大批量整理、删除、拆分提交前，优先先做快照
2. 快照优先打包 Git 视角下的源码与文档
3. 快照命名建议带日期和用途
4. 快照不能替代 Git 提交

## 4. 自动部署工作区规则

- 自动部署前必须先检查服务器工作区是否干净
- 最低要求：`git status --porcelain -uall`
- 发现脏工作区时，先备份现场，再决定是否自动收口
- 不允许在未备份现场的前提下直接覆盖服务器工作区
- 生产部署完成后还要补健康检查和端口检查

## 5. 推荐提交粒度

- `feat:` 新功能
- `fix:` 缺陷修复
- `refactor:` 结构收口
- `docs:` 文档整理
- `chore:` 基础设施、脚本、配置清理

不要把下面这些无关内容混进同一个提交：

- 文档重构
- 页面样式改造
- 后端逻辑修复
- 部署脚本调整
- 数据边界迁移

## 6. 交付时必须说明

- 做了哪些验证
- 哪些文件纳入提交
- 提交信息是什么
- 是否还有未纳入提交的剩余改动

## 7. 当前特别提醒

- 当前文档体系已经按“核心基线 / 专题方案 / 变更记录 / 历史规划”重新整理
- 提交前不要再把已放弃路线、重复 HTML 镜像或无关历史草案一起带进新的提交
- `local-single-user` 交付链推进后，像 `.release/`、`*.tsbuildinfo`、`.dbg/trae-debug-log-*.ndjson` 这类发布产物、构建缓存和调试日志，不应继续进入新提交；如果它们已被 `.gitignore` 覆盖却仍在 Git 跟踪内，应优先移出索引，再保留本地文件
