# local-single-user 稳定性交付重构方案与开发计划

## 1. 目标

本方案只围绕两个约束展开：

1. 方案必须稳定可交付
2. 开发周期不能特别长，必须按小步闭环推进

因此，这次不走“大推翻重写”，而走：

- 先统一主链约束
- 再逐步替换历史分散脚本
- 每一阶段都能独立发版验证

## 2. 第一性原理

本地单机版对用户真正承诺的只有四件事：

1. 安装一定成功
2. 安装后一定能启动
3. 重启后一定能恢复
4. 升级后数据不丢、版本切换可验证

只要这四件事里任何一件要靠“环境刚好正常”或“多个脚本互相兜底”才能成立，系统就不是稳定交付系统。

因此，重构必须满足三条根约束：

### 2.1 单一入口

- 安装只认一个入口
- 启动只认一个入口
- 升级只认一个入口

其他脚本只能是内部实现，不再各自决定最终状态。

### 2.2 单一状态

安装、启动、升级、自愈、失败、回滚，必须统一写入同一份生命周期状态，而不是各自写日志、各自超时、各自推断。

### 2.3 单一环境解析

系统不能依赖：

- PATH 里刚好有 `powershell`
- 历史 Startup 工件刚好没残留
- 本地旧目录刚好干净
- metadata 刚好在某个时点已经落盘

所有关键宿主依赖必须由系统自己解析、自己校验、自己兜底。

## 3. 当前系统性问题

根据最近连续故障，当前问题主要集中在：

### 3.1 环境解析分散

`PowerShell/cmd/taskkill/浏览器打开` 的解析散在多个脚本里：

- `build-local-single-user-release.cjs`
- `local-single-user-runtime.cjs`
- `local-single-user-launcher.cjs`
- `local-single-user-autostart.cjs`
- `package-local-single-user-release.cjs`

导致同一类环境问题要在多处重复修。

### 3.2 生命周期没有统一状态文件

当前更多依赖：

- `launcher.log`
- `runtime metadata`
- `install log`
- `update status`

但没有一个统一的“当前到底处于什么状态”的生命周期文件。

### 3.3 安装 / 启动 / 自启 / 升级仍然是并列脚本思维

虽然已经做了很多修复，但核心调度仍主要分散在：

- `.cmd`
- `.ps1`
- `.cjs`

之间传递，尚未形成统一 runtime manager。

## 4. 目标架构

本次重构目标不是一次性做成大而全，而是逐步收敛到下面这个结构：

### 4.1 Local Runtime Manager

唯一负责：

- 启动
- 停止
- 自愈
- 自启恢复
- 生命周期状态写入
- 运行时 metadata 写入

### 4.2 Installer Orchestrator

唯一负责：

- 安装
- 覆盖安装
- 首启
- 首启验活

### 4.3 Updater Orchestrator

唯一负责：

- 升级准备
- 版本切换
- 回滚
- 升级状态写入

### 4.4 Lifecycle State

统一状态文件至少覆盖：

- `INSTALLING`
- `STARTING`
- `READY`
- `UPDATING`
- `FAILED`
- `ROLLING_BACK`

并统一附带：

- 当前入口
- 当前版本
- 关键路径
- 最近错误
- 最近更新时间

## 5. 分阶段开发计划

本计划故意压缩周期，不走长期大重构。

### 阶段 1：基础收口

目标：

- 统一宿主环境解析
- 落第一版生命周期状态文件
- 不改主业务协议，不改数据库

交付物：

- 统一平台 helper
- launcher 生命周期状态写入
- 关键入口脚本改为共享环境解析

周期：

- 1 到 2 天

风险：

- 低

验收标准：

- 启动链不再在多个 Node 脚本里各自拼 `powershell/cmd`
- 启动成功或失败时可在统一 lifecycle 文件里看到结果

### 阶段 2：安装 / 自启主链收口

目标：

- 安装、自启、首启 ready 判定统一收敛
- 清理历史 fallback 分叉

交付物：

- 安装入口与自启入口统一环境解析
- 安装阶段直接读 lifecycle 状态，而不是只靠日志和超时猜测
- Startup / Task / fallback 工件治理进一步统一

周期：

- 2 到 4 天

风险：

- 中低

验收标准：

- 安装失败能明确落到统一状态
- 自启恢复不再依赖历史残留工件是否碰巧正确

### 阶段 3：升级链收口

目标：

- 升级、回滚、重启统一由状态机驱动

交付物：

- updater 与 launcher 状态口径统一
- 升级成功 / 失败 / 回滚在同一状态模型里可追踪

周期：

- 3 到 5 天

风险：

- 中

验收标准：

- “点击升级无反应 / 超时 / 成功但页面没切 / 回滚不清楚”这类问题能直接定位到具体状态

### 阶段 4：交付验证矩阵

目标：

- 把“可运行”变成“可稳定交付”

交付物：

- 全新安装验证
- 覆盖安装验证
- 重启自启验证
- 应用内升级验证
- 数据保留验证
- 弱环境验证

周期：

- 2 到 3 天

风险：

- 低

验收标准：

- 发版前有固定验证矩阵，而不是出问题后再补

## 6. 周期控制结论

如果按上述小步推进：

- 阶段 1 + 阶段 2：可以在短周期内完成主收益收口
- 阶段 3：控制在中等工作量
- 阶段 4：作为交付兜底补上

也就是说，整套方案不是长周期推翻重做，而是：

- 先用约 3 到 6 天收住安装 / 启动 / 自启主链
- 再用约 3 到 5 天收口升级链
- 最后补验证矩阵

这是当前“稳定可交付”和“周期不能太长”之间最稳的平衡点。

## 7. 当前执行策略

本轮开始，默认按本计划推进：

1. 先做阶段 1
2. 每完成一阶段就落文档和变更记录
3. 每一阶段都要求独立可发版验证
4. 不再继续无计划地按单点故障打补丁

## 8. 阶段 1 当前已推进内容

本轮已开始推进阶段 1，已落地方向：

- 新增统一平台 helper，收口 PowerShell / cmd / taskkill 解析
- launcher 开始写统一 lifecycle 状态
- runtime / autostart / package 等主链脚本开始切到共享环境解析

后续下一步将继续围绕阶段 2 推进安装与自启主链收口。

## 9. 阶段 2 当前已推进内容

本轮已继续推进阶段 2 中“安装主链收口”的第一刀，已落地方向：

- 安装脚本开始直接读取 `local-single-user-lifecycle.json`
- 安装器在首启前先写 `INSTALLING`
- 安装等待逻辑在发现 lifecycle 已进入 `FAILED` 时可提前失败
- 安装超时信息开始直接附带 lifecycle 上下文，而不再只给出笼统超时

当前仍未完成的阶段 2 内容：

- 安装 / 自启 / 启动之间进一步减少 fallback 分叉
- 自启链上的历史恢复逻辑仍需继续简化
- 安装 / 自启 / 启动之间进一步减少 fallback 分叉
本轮继续推进后，阶段 2 已新增：

- 自启 helper 开始先解析真实 `localAppRoot`
- 自启恢复链开始写入并消费统一 lifecycle 状态
- 自启失败日志开始直接带出 `lifecyclePhase / lifecycleError`

也就是说，阶段 2 的主收益项已经基本落地：

- 安装链接入 lifecycle
- 自启链接入 lifecycle

当前阶段 2 剩余工作已经从“主链是否收口”变成“边角 fallback 是否继续精简”。这时已经可以进入一轮真实版本升级验证，再决定是否直接切入阶段 3。
