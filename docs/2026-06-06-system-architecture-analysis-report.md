# AI 全域智能体系统架构分析报告

## 1. 报告目的

本报告用于系统性梳理当前网站的真实架构、模块边界、模块协作方式、数据存储设计、数据库结构，以及未来如何把模块能力改造成类似 USB 插拔一样可扩展、可复用、可维护的体系。

这份报告的用途有两个：

1. 作为当前系统蓝图，帮助判断现有架构是否健壮、模块划分是否合理、哪些地方仍处于过渡态。
2. 作为未来开发前的架构参照，避免遗漏已有能力、影响其他板块、重复造轮子，保证新增模块可以沿统一规范接入。

## 3. 系统总体架构

### 3.1 总体判断

当前系统不是一个单一页面应用，而是一个以品牌为上下文、以多平台内容生产为核心的复合型业务系统。它同时具备：

- SaaS 化账号与团队体系
- 多品牌工作区
- 内容采集、策略生成、作品生产、发布交付
- 模型与提示词配置中心
- 第三方接口配置中心
- 任务中心与媒体资产中心

从架构分层上看，当前系统可以概括为 6 层：

1. 表现层：`apps/web/src/app`
2. 前端服务层：`apps/web/src/services`
3. API 代理层：`apps/web/src/app/api/[...path]/route.ts`
4. 后端业务模块层：`apps/server/src/modules/*`
5. 基础设施层：`prisma`、`storage`、`common`、`config`
6. 数据层：PostgreSQL、OSS、本地 fallback 资源

### 3.2 典型请求链路

一个典型业务请求的调用链如下：

1. 用户进入前端某个工作台页面。
2. 页面壳层组件调用 `src/services/*` 中的前端服务。
3. 前端服务统一走浏览器同域 `/api/*`。
4. Next API 代理把请求转发给 NestJS 后端。
5. 后端控制器接收请求，并交由对应模块 service 处理。
6. service 再调用数据库、OSS、第三方模型接口、第三方平台接口。
7. 结果回到前端，前端再以工作区、详情卡片、任务记录、历史记录等形式呈现。

### 3.3 当前最关键的系统主轴

如果用一句话总结当前系统主轴，可以表述为：

> 以品牌为统一上下文，以采集数据和品牌资料为原料，通过报告与作品模块驱动多平台内容生产，再通过发布模块输出到平台，整个过程由任务、媒体、技能、供应商和提示词系统共同支撑。

## 4. 代码仓与目录结构

### 4.1 Monorepo 结构

主仓采用 workspace monorepo 结构：

- `apps/web`：前端站点
- `apps/server`：后端服务
- `packages/shared`：共享枚举、类型、权限模型
- `packages/prompt-runtime`：提示词运行时基础能力
- `packages/ui`：共享 UI 组件预留区
- `docs`：规范、站点地图、变更记录、路线图
- `prisma`：数据库 schema 与迁移

### 4.2 当前主仓外的其他代码资产

根目录同时存在：

- 平行仓：`ai-omni-ops-xhs-agent`
- 备份仓：`ai-omni-ops-system-code-backup-20260525-205255`
- 大量解决方案文档、截图、素材、运维资料

这意味着当前“代码资产治理”还没有完全收束到单一主仓，后续应明确：

- 哪个仓是生产主仓
- 哪些目录是只读备份
- 哪些目录属于方案文档与素材

否则将影响未来架构治理和开发协作的一致性。

## 7. 非独立模块与共享基础设施

这里的“非独立模块”不是指它们不重要，而是它们当前并不适合单独当作完整业务域来看，而是作为共享层、承接层、支撑层存在。

### 7.1 Works 模块

系统地位：

- 当前后端最大的生产执行中心

作用：

- 承接小红书内容生成
- 承接抖音视频与数字人
- 承接公众号工作流
- 承接设计工作台
- 承接多种媒体资产生成与中间流程

问题：

- 能力很多，跨度很大
- 容易演化成“超级模块”
- 未来新增业务如果继续堆进去，会导致维护成本持续上升

结论：

- 它现在是系统最关键的生产引擎
- 但不是理想状态下的最终结构
- 后续应按平台域或能力域继续拆分

### 7.2 Reports 模块

系统地位：

- 策略与文案生成中心

作用：

- 负责增长报告、营销规划、营销日历、热点选题、文案输出

问题：

- 同时承担报告、策划、日历、文案多个方向
- 逻辑边界已经偏宽

结论：

- 它是“策略生成中枢”
- 长期看应拆成报告域、策略域、文案域三类子域

### 7.3 Publishing 模块

系统地位：

- 交付出口层

作用：

- 把作品从内部状态推向平台外部状态

特点：

- 自己不是内容生产中心
- 它依赖 `WorksModule` 提供可发布内容

结论：

- 它是清晰的交付层模块
- 但它的输入输出模型应继续标准化

### 7.4 Collectors 模块

系统地位：

- 数据采集与素材原料层

作用：

- 负责抓取热点、账号、素材、趋势等内容

特点：

- 它不是最终业务呈现模块
- 但它是报告和作品模块的重要原料来源

结论：

- 应视为“数据输入层”

### 7.5 Prompt / Skill / Provider 体系

系统地位：

- AI 编排配置层

作用：

- 管理技能
- 管理提示词
- 管理模型供应商
- 决定同一业务链路最终如何选择模型与 fallback

特点：

- 横跨所有业务模块
- 是系统“标准化、模块化、可替换”的关键枢纽

结论：

- 它不是某个业务模块，而是系统 AI 基础底座

## 8. 模块之间如何协作

### 8.1 统一协作模式

当前系统大致遵循如下协作关系：

1. `Auth + Brands` 提供身份与品牌上下文。
2. `Collectors` 提供原始素材与数据输入。
3. `Reports` 提供策略、规划、日历、文案。
4. `Works` 把上游输入转成具体作品与媒体。
5. `Media + Storage` 保存结果资产。
6. `Tasks` 记录长耗时执行过程。
7. `Publishing` 完成平台交付。
8. `Admin + Skills + Providers + ThirdPartyPlatforms` 统一治理模型与配置。

### 8.2 模块协作矩阵

#### 品牌增长

- 依赖：`Auth`、`Brands`、`Collectors`、`Reports`
- 输出给：小红书、抖音、公众号

#### 小红书

- 依赖：`Brands`、`Collectors`、`Reports`、`Works`、`Publishing`、`Tasks`、`Media`
- 输出给：发布链路、作品中心、任务中心

#### 抖音

- 依赖：`Brands`、`Collectors`、`Reports`、`Works`、`Tasks`、`Media`
- 输出给：作品中心、任务中心

#### 公众号

- 依赖：`Brands`、`Reports`、`Works`、`Publishing`、`Tasks`、`Media`
- 输出给：发布历史、任务中心、作品资产

#### 设计工作台

- 依赖：`Brands`、`Works`、`Media`、`Tasks`、`Providers`
- 输出给：设计结果展示与后续资产复用

## 9. 数据存储总览

### 9.1 当前正式主链路

当前正式持久化主链路是：

- PostgreSQL：结构化业务数据
- OSS：长期媒体资源与文件资产
- 本地 fallback：开发态或数据库不可用时的过渡兜底

### 9.2 数据类型划分

#### 结构化数据

存储于 PostgreSQL：

- 用户
- 品牌
- 角色与权限
- 订单
- 积分
- 任务
- 媒体资产元数据
- 技能
- 提示词
- API Provider
- 第三方平台配置
- 公众号配置与工作流会话

#### 大文件与媒体文件

存储于 OSS：

- 图片
- 视频
- 音频
- 文档附件
- 生成结果文件

#### 过渡型本地存储

在少量场景下仍存在：

- `.runtime/local-oss`
- mock fallback
- 运行时临时文件

这说明系统已经建立了正式存储方向，但尚未完全去除过渡态。

## 10. 数据库设计分析

数据库整体采用：

- Prisma schema 定义模型
- PostgreSQL 持久化
- 以 `User`、`Brand`、`Task` 为核心根实体
- 大量使用 `Json` 字段承载扩展快照与流程态数据

这是一种典型的“结构化主干 + JSON 扩展”的混合建模风格。

### 10.3 JSON 字段的角色

当前数据库中大量使用 JSON/JSONB 字段，它们主要承担以下职责：

- 扩展配置
- 结构化但不稳定的业务快照
- 多平台差异化字段
- AI 生成过程中的输入输出
- 图片任务、发布配置、标签集合等中间态数据

优点：

- 开发灵活
- 迭代快
- 适合 AI 输出结构变化频繁的阶段

风险：

- 查询约束弱
- 字段规范容易漂移
- 统计分析成本较高
- 长期演进容易积累隐性技术债

结论：

- 现阶段合理
- 长期应对高频核心结构进一步正规化建模

## 11. 数据与模块之间的关系

### 11.1 用户、品牌、任务三大根节点

当前系统中最关键的三个根节点是：

- `User`
- `Brand`
- `Task`

原因：

- `User` 定义了身份与账号归属。
- `Brand` 定义了业务上下文与资料边界。
- `Task` 定义了 AI 执行过程与可观测性边界。

### 11.2 典型业务数据流

#### 以小红书原创笔记为例

1. 用户登录并选择品牌。
2. 品牌资料、竞品资料、营销日历、采集素材从数据库读取。
3. `Reports` 输出策略或规划。
4. `Works` 生成笔记文案、图片提示词、媒体资产。
5. `Task` 记录过程状态。
6. `MediaAsset` 保存结果元数据，文件存入 OSS。
7. `Publishing` 或草稿桥接完成平台交付。

#### 以公众号工作流为例

1. 用户在品牌上下文中保存公众号配置。
2. `WechatWorkflowSession` 保存创作过程态。
3. `Task` 分阶段记录文章生成、生图、HTML 生成、发布动作。
4. `WechatArticleDraft` 保存稿件与图片结果。
5. `WechatPublishHistory` 记录发布历史。

### 11.3 当前数据关系的优点

- 多数业务已围绕品牌聚合，边界比纯用户维度更合理。
- AI 长链路开始任务化，便于诊断、重试与回溯。
- 技能与提示词开始落数据库，利于统一治理。
- 公众号已经有专属数据表，说明系统开始从“功能集合”走向“领域建模”。

### 11.4 当前数据关系的不足

- 仍存在 mock fallback 和本地过渡路径。
- 部分工作台依然通过超级 service 管理多种异构对象。
- 某些历史模块仍以用户维度为主，而不是完全以品牌域为主。
- JSON 字段过多，后期容易出现语义漂移。

## 12. 对当前架构健壮性的判断

### 12.1 优势

#### 已经形成了统一的品牌上下文

这使得系统不是零散工具集合，而是以品牌为中心的运营系统。

#### 已经形成了真实的多层架构

页面、前端服务、代理、后端模块、数据库、存储层都已经存在，不是杂糅在一起。

#### 已经开始任务化长链路

长耗时 AI 流程可以进入任务中心，系统具备可观测性基础。

#### 技能、提示词、Provider、第三方平台逐步规范化

这对未来做模块化和可插拔能力非常关键。

#### 文档体系较完善

站点地图、工程规范、变更文档、数据库存档都已建立，说明系统具备“持续治理”的基础。

### 12.2 问题与风险

#### `WorksService` 过重

这是当前最大风险之一。很多业务都挂在其中，未来新功能继续进入这里，会导致：

- 改动波及面过大
- 认知成本上升
- 测试与回归风险增大

#### `ReportsService` 也偏重

报告、策划、日历、文案类生成被放在一个大域中，后续应继续拆分。

#### 前端部分工作台壳层仍偏厚

尤其是多工作区、多弹窗、多异步动作并存的页面，维护压力会越来越大。

#### 数据层仍有过渡态

- mock fallback 仍存在
- 本地 fallback 仍存在
- 某些能力尚未完全单轨数据库化

#### 仓库资产未完全收束

主仓、平行仓、备份仓并存，不利于长期架构治理。

## 13. “像 USB 插拔一样扩展模块”应如何设计

这是本报告最重要的未来蓝图部分。

### 13.1 目标定义

所谓“像 USB 插拔一样”扩展模块，不是简单地把页面多加一个菜单，而是要做到：

- 新模块接入成本低
- 对现有模块侵入小
- 共享能力无需重复开发
- 模块既能独立运行，也能接入统一任务、权限、品牌、配置、存储体系
- 删除或下线某模块时，不影响其他模块稳定运行

### 13.2 未来应采用的模块架构原则

#### 原则 1：模块必须分成四类能力

每个新增模块都应显式声明：

1. 页面入口
2. 业务服务
3. 数据模型
4. 外部依赖

如果这四类信息不完整，就不应视为可插拔模块。

#### 原则 2：模块必须接入统一平台底座

所有模块都应通过统一平台底座接入以下能力：

- 身份认证
- 品牌上下文
- 权限体系
- 任务系统
- 媒体存储
- 技能与提示词
- Provider 选择
- 第三方平台密钥
- 审计与日志

也就是说，新增模块不应重复造一套：

- 登录体系
- 文件存储体系
- 模型路由体系
- 发布记录体系

#### 原则 3：模块必须有标准化注册信息

建议为每个模块建立统一的模块注册元数据，例如：

- `moduleKey`
- `moduleName`
- `moduleType`
- `entryRoute`
- `requiredPermissions`
- `requiredCapabilities`
- `requiredProviders`
- `requiredTables`
- `taskTypes`
- `mediaTypes`
- `featureFlags`

这样未来新增模块时，只要完成一份注册声明，就能被系统发现、加载、展示和治理。

#### 原则 4：模块必须遵守统一输出合同

不同模块虽然业务不同，但输出合同应统一，例如：

- 任务必须写入 `Task`
- 产物必须写入 `MediaAsset`
- 技能必须落到 `SkillConfig/PromptTemplate`
- 品牌级配置必须挂在 `Brand` 相关域上
- 发布记录必须有统一发布事件结构

这会大幅降低模块之间的耦合成本。

### 13.3 建议的模块分层蓝图

未来建议把系统抽象成三层模块模型。

#### 第一层：平台底座模块

这层对业务模块透明提供能力：

- `auth-core`
- `brand-core`
- `permission-core`
- `task-core`
- `media-core`
- `storage-core`
- `provider-core`
- `prompt-core`
- `third-party-platform-core`
- `audit-core`

#### 第二层：领域能力模块

这层是可复用能力域：

- `collector-domain`
- `strategy-domain`
- `copy-domain`
- `image-domain`
- `video-domain`
- `html-render-domain`
- `publish-domain`
- `knowledge-domain`

#### 第三层：业务工作台模块

这层才是用户看到的业务模块：

- `brand-growth-workbench`
- `xiaohongshu-workbench`
- `douyin-workbench`
- `wechat-workbench`
- `design-workbench`

这样做的好处是：

- 同一能力可以被多个工作台复用
- 业务模块不再直接依赖超级 service
- 新工作台只需要声明自己组合了哪些领域能力

### 13.4 当前系统要实现“USB 式插拔”，必须先补的关键点

#### 一：拆分超级 service

优先拆：

- `WorksService`
- `ReportsService`

目标是把它们拆成多个能力服务，而不是所有业务都继续挂进去。

#### 二：建立模块注册中心

建议新增一套模块注册机制，可先从代码级常量注册开始，再演进到数据库配置：

- 菜单注册
- 路由注册
- 权限注册
- 任务类型注册
- 技能绑定注册
- Provider 需求注册

#### 三：建立统一能力接口

例如为所有生成型模块约定统一接口：

- `prepareInput()`
- `validateContext()`
- `createTask()`
- `execute()`
- `persistResult()`
- `buildPreview()`
- `publish()`

这样新模块接入时，就不是自由发挥式开发。

#### 四：把页面壳层也模块化

前端新增模块时，不应每次重新堆一个超长页面，而应基于统一工作台协议：

- `workspace-shell`
- `loader-hook`
- `actions-hook`
- `panels/*`
- `modals/*`
- `services/*`

#### 五：建立领域模型设计模板

新增模块前，先回答：

- 主实体是什么
- 与 `Brand` 的关系是什么
- 是否需要独立任务类型
- 是否需要独立媒体资产类型
- 是否需要独立历史记录表
- 是否需要独立发布记录表

只有这套模板答完，才允许开工。

## 14. 对未来新增模块的推荐接入方式

假设未来新增一个“知乎工作台”或“视频剪辑工作台”，推荐按以下步骤接入：

1. 注册模块元数据。
2. 复用平台底座能力。
3. 明确该模块组合了哪些领域能力。
4. 增加独立的页面壳层与前端服务。
5. 为其定义独立任务类型。
6. 为其定义独立数据表或扩展现有域模型。
7. 让其统一进入任务中心、媒体中心、权限中心、技能中心。
8. 在文档中补站点地图、变更记录、数据库关系说明。

这样新增模块就变成“声明式接入 + 有边界扩展”，而不是“在现有大文件里继续追加逻辑”。

## 15. 推荐的近期架构治理路线

### 第一阶段：止血与收束

- 明确 `ai-omni-ops-system` 为唯一主仓
- 将平行仓和备份仓明确标记用途
- 继续清理 mock fallback
- 继续把技能与提示词完全收敛到数据库真源

### 第二阶段：拆分超级模块

- 拆 `WorksService`
- 拆 `ReportsService`
- 把设计、公众号、视频、数字人从“超级服务”中抽离成明确能力服务

### 第三阶段：建立模块注册与能力协议

- 建立 `module registry`
- 建立统一生成链路接口
- 建立统一任务、媒体、发布合同

### 第四阶段：为新增模块建立标准接入模板

- 页面模板
- 服务模板
- 数据模型模板
- 文档模板
- 测试模板

## 16. 结论

### 16.1 当前系统是否健壮

结论是：

- **整体方向是正确的**
- **系统已经具备较好的平台化基础**
- **但仍处于从“功能集合”走向“模块化平台”的过渡阶段**

### 16.2 当前系统最值得肯定的地方

- 已有品牌上下文
- 已有多层架构
- 已有任务中心
- 已有媒体资产中心
- 已有后台配置中心
- 已有技能/提示词/Provider 治理基础
- 已有较完整文档体系

### 16.3 当前系统最需要优先治理的地方

- 超级 service 过重
- 某些模块只做了页面独立，未做到后端能力独立
- 数据层仍有过渡态
- 仓库资产边界未完全收束
- 模块注册和可插拔协议尚未建立

### 16.4 最终建议

未来这套系统不应继续按“新增一个功能，就往某个大 service 里塞”的方式演进，而应转向：

> 平台底座统一、领域能力复用、业务工作台装配、模块元数据注册、任务与数据合同标准化。

只有这样，未来新增模块时才能做到真正接近“USB 插拔式”的方便、高效、低风险接入。
