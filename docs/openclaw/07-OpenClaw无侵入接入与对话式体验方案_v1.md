# OpenClaw 无侵入接入与对话式体验方案 v1

## 1. 文档定位

本文件是在前面 `04 / 05 / 06` 三份文档基础上的补充强化版，专门解决两个容易在实施时跑偏的问题：

1. **不能影响网站正常运行**
2. **用户授权后，要尽量通过对话完成权限范围内的全部功能和数据查看，而不是要求用户频繁操作、频繁填表、频繁跳页面**

这份文档不是替代前面的架构与规格文档，而是给实施阶段增加两个强约束：

- `无侵入上线约束`
- `极简对话式体验约束`

一句话结论：

> OpenClaw 的正确落地方式，不是把网站主流程改造成“围着机器人转”，而是让机器人接入一个受控、灰度、可回滚、低耦合的能力层；用户侧则尽量做到“授权一次，后续主要靠对话完成”，只有在真正高风险或必要缺参时才要求确认或补充。

---

## 2. 必须坚持的两条硬约束

## 2.1 硬约束一：绝不能影响网站正常运行

这意味着：

- OpenClaw 接入失败，网站原功能仍必须可用
- OpenClaw 服务异常，不能拖垮网站主请求
- OpenClaw 相关模型调用变慢，不能阻塞网站核心页面
- OpenClaw 发布出问题，必须能快速回滚或一键关闭
- OpenClaw 的灰度范围必须可控，不能一上来全量影响所有用户

## 2.2 硬约束二：用户使用必须足够方便

这意味着：

- 授权后，用户不应每次都选一堆参数
- 用户不应为了让机器人做事而重复学习网站菜单
- 用户不应因为机器人接入而被迫填写大量表单
- 用户不应被频繁打断去确认低风险信息
- 用户应主要通过自然语言对话完成自己权限内的操作和数据查看

---

## 3. 无侵入接入原则

## 3.1 不改主链路，不劫持主链路

OpenClaw 接入原则上不能替代现有网站主功能入口。

网站主流程仍然是：

- 用户正常登录
- 正常访问各工作台
- 正常使用现有页面功能

OpenClaw 是新增的“辅助入口”和“统一对话能力入口”，不是把主站改成“只有机器人入口”。

### 原则

1. 网站现有 API 不因 OpenClaw 而被迫整体重写
2. 原有页面提交流程不因 OpenClaw 而被强制改造成聊天流程
3. 现有功能继续保留原入口，OpenClaw 只是新增入口
4. 任何时候都可以关闭 OpenClaw，而不影响主站业务

---

## 3.2 独立网关，避免直接压主服务

建议 OpenClaw 通过独立的 `Assistant Gateway / MCP Gateway` 接入，而不是直接把所有逻辑塞到主 Web 请求里。

推荐结构：

- 用户请求进入 OpenClaw 渠道
- 请求先到 Assistant Gateway
- Gateway 做：
  - 鉴权
  - 上下文注入
  - 工具选择
  - 限流
  - 审计
  - 风险分级
- 然后再调用现有网站的领域能力层

### 目的

- 避免把模型延迟直接压到网站主页面
- 避免 OpenClaw 调用洪峰拖慢现有 API
- 方便单独限流、熔断、灰度、回滚

---

## 3.3 主站功能与助手功能解耦

建议把 OpenClaw 相关能力按三层拆开：

### 第一层：现有网站能力

这是现有真实业务逻辑：

- 报告生成
- 内容生成
- 知识库管理
- 技能覆盖管理
- 任务读取

### 第二层：稳定能力接口层

把现有能力整理为稳定的：

- Action Code
- MCP Tool
- 聚合接口

### 第三层：对话入口层

这是 OpenClaw 或网站内助手 UI。

这样即使未来：

- 页面变
- 组件变
- 路由变
- service 拆分

OpenClaw 仍然只依赖第二层，不跟着 UI 一起抖。

---

## 3.4 只做加法，不做危险替换

上线策略上，OpenClaw 第一阶段只能做“加法”，不能做“替换”。

### 可以做

- 新增授权入口
- 新增助手对话入口
- 新增只读问答
- 新增低风险工具调用

### 不应直接做

- 替换原页面主提交按钮
- 强制所有生成任务都只能通过对话发起
- 强制所有用户先学会机器人再使用系统

---

## 4. 不影响网站运行的技术方案

## 4.1 功能开关

必须为 OpenClaw 设计多层级开关：

### 全局开关

- 平台级关闭全部 OpenClaw 能力

### 品牌级开关

- 某品牌单独关闭

### 工具级开关

- 某个高风险工具单独关闭

### 渠道级开关

- 网站内助手开着
- 外部 OpenClaw 客户端先不开

这样可以：

- 快速止损
- 快速灰度
- 快速回滚

---

## 4.2 灰度发布

建议至少分四步灰度：

### 第一步：内部只读灰度

范围：

- 内部账号
- 管理员
- 只读能力

目标：

- 验证授权、品牌上下文、数据返回、审计是否稳定

### 第二步：内部低风险写灰度

范围：

- 内部账号
- 少量管理员与运营
- 低风险动作

目标：

- 验证确认流和 Task 对接

### 第三步：小范围品牌灰度

范围：

- 指定品牌
- 指定用户组

目标：

- 验证真实业务使用体验
- 验证不会影响网站性能和主流程

### 第四步：全量开放

前提：

- 性能稳定
- 审计稳定
- 回滚机制验证完成

---

## 4.3 熔断与降级

OpenClaw 必须可降级，且降级后不影响主站。

### 建议降级策略

#### 降级一：禁用写操作

只保留只读问答。

#### 降级二：禁用模型推理

只保留结构化工具查询。

#### 降级三：禁用外部 OpenClaw 客户端

仅保留网站内入口。

#### 降级四：完全关闭 OpenClaw

网站主功能不受影响。

---

## 4.4 限流与配额隔离

不能让 OpenClaw 的流量抢占主站关键资源。

### 建议隔离

- OpenClaw 请求单独限流
- OpenClaw 模型调用单独配额
- OpenClaw 高成本工具单独并发上限
- OpenClaw 任务提交单独速率限制

### 重点

OpenClaw 不能因为短时间高频对话：

- 把任务队列打满
- 把模型预算打爆
- 把数据库热点接口拖慢

---

## 4.5 Shadow Mode

在正式开放前，建议先做 `Shadow Mode`：

- 用户正常走网站原流程
- OpenClaw 同步模拟理解意图和工具选择
- 但不真正执行写操作
- 只记录建议动作和差异

### 价值

- 验证 Skill 路由准确度
- 验证工具选择是否合理
- 不影响真实业务

---

## 4.6 审计先于放量

在 OpenClaw 放量前，审计必须先上线。

至少做到：

- 每次工具调用可追踪
- 每次品牌切换可追踪
- 每次高风险确认可追踪
- 每次失败和超时可追踪

如果审计没到位，不应进入大范围灰度。

---

## 5. 对话式体验原则

## 5.1 授权一次，后续尽量少打断

用户授权完成后，系统应自动记住：

- 当前身份
- 当前品牌
- 当前常用品牌
- 当前可用能力
- 当前数据范围

这样用户后续提问时，不需要每次重复：

- “我是哪个品牌”
- “我有什么权限”
- “我能做什么”

---

## 5.2 只在真正必要时追问

机器人不应动不动就让用户补一堆信息。

### 可自动推断的，尽量自动推断

例如：

- 当前品牌
- 默认时间范围
- 当前正在看的工作台
- 当前用户最近使用的任务类型

### 只有在以下情况才追问

1. 会影响业务结果
2. 会影响权限范围
3. 会影响高风险动作执行
4. 系统确实无法合理推断

---

## 5.3 追问必须最小化

如果必须追问，也要一次只问最少的问题。

### 不好的追问方式

- 一次弹出 8 个字段
- 让用户重新填写整个表单
- 让用户去找一堆系统 ID

### 好的追问方式

- “你是想在当前品牌生成，还是切到另一个品牌？”
- “这次生成原创图文，还是视频笔记？”
- “这次是查看摘要，还是导出完整明细？”

---

## 5.4 低风险动作不应强确认

如果用户已经明确表达：

- “帮我看看最近的任务”
- “帮我看一下当前品牌知识库”
- “帮我生成一份品牌增长报告”

那么在权限允许、参数足够的情况下，应直接执行。

不要把系统做成：

- 每一步都确认
- 每一步都点按钮
- 每一步都再问一次

否则用户体验会变得比原网站还差。

---

## 5.5 高风险动作必须明确确认

为了便利不能牺牲安全。

因此以下动作仍必须确认：

- 删除知识资料
- 重置品牌技能基线
- 导出完整敏感数据
- 触发后台 CLI 作业

### 原则

- 只对高风险动作加强确认
- 不对低风险动作滥用确认

---

## 5.6 用户不应理解系统字段

用户对话时不应被迫输入：

- `slug`
- `targetId`
- `targetKey`
- 内部任务 ID
- 内部模型配置 ID

用户应使用业务语言即可：

- 品牌名
- 知识库名称
- 任务标题
- 时间范围
- 平台类型

系统负责映射到底层对象。

---

## 5.7 尽量通过对话完成，不强制跳页

理想目标是：

- 大部分只读能力直接在对话里完成
- 大部分低风险执行动作直接在对话里完成
- 只有在以下情况才跳页：
  - 需要预览复杂视觉结果
  - 需要人工精细编辑
  - 需要审批流处理
  - 需要查看超大明细表

也就是说：

> 对话应是默认入口，页面应是补充入口，而不是反过来。

---

## 6. 授权后的理想使用体验

## 6.1 用户第一次授权后

用户应得到清晰反馈：

- 已授权成功
- 当前默认品牌是什么
- 当前可用能力有哪些
- 哪些能力需要额外权限或审批

## 6.2 用户后续对话的理想状态

用户可以直接说：

- “看看我们品牌最近的任务情况”
- “帮我生成一份品牌增长报告”
- “把企业知识库里上周新传的资料列出来”
- “给我做一版小红书原创图文”
- “把公众号文章创作技能的当前品牌覆盖配置给我看一下”

系统应自动完成：

- 品牌识别
- 能力匹配
- 权限校验
- 工具执行
- 结果摘要

## 6.3 对话式工作流目标

最终用户体验应接近：

- 授权一次
- 打开就能问
- 问了就能看
- 说了就能做
- 做完就有结果
- 风险高才确认

---

## 7. 对话式交互策略

## 7.1 当前品牌默认策略

如果用户未明确说明品牌：

1. 优先使用当前网站品牌上下文
2. 如果来自外部客户端，优先使用最近一次品牌
3. 如果用户有多个品牌且无法判断，再单次追问

不应默认跨品牌汇总。

## 7.2 默认参数策略

对常见动作给默认值：

- 最近 7 天
- 当前品牌
- 当前工作台
- 最近一次同类任务配置

用户不满意再继续细化。

## 7.3 单轮完成优先

一个请求能在一轮完成，就不要拆成三轮。

例如：

- 用户说“帮我生成品牌增长报告”
- 系统在默认品牌、默认模板、默认时间范围可成立时，应直接发起任务

而不是先问：

- 你是谁
- 你在哪个品牌
- 你要什么时间范围
- 你要什么模板
- 你确认吗

---

## 7.4 结果呈现要适合对话

对话返回不是把整个页面 JSON 扔给用户。

建议：

- 先给摘要
- 再给关键指标
- 再给可继续操作建议
- 如果需要，再提供“展开详情”或“打开页面”

### 示例

不推荐：

- 直接返回 60 行结构化字段

推荐：

- “最近 7 天共有 12 个任务，8 个已完成，2 个进行中，2 个失败。是否需要我展开失败任务原因？”

---

## 8. 不影响网站运行的实现策略

## 8.1 首期只读优先

第一阶段优先上：

- 身份读取
- 品牌切换
- 品牌摘要读取
- 任务读取
- 知识库读取
- 技能中心读取

这样最不容易影响主站。

## 8.2 写操作逐步开放

第二阶段再开放：

- 新建知识库
- 上传资料
- 触发报告生成
- 触发内容生成

第三阶段再开放：

- 技能覆盖更新
- 基线重置
- 高风险导出

## 8.3 所有生成动作继续走 Task

这可以避免：

- OpenClaw 直接占住主请求
- 页面等待超时
- 用户感知混乱

OpenClaw 只要做到：

- 发起任务
- 告诉用户任务已受理
- 支持继续跟进结果

---

## 8.4 失败时优先不影响主站

如果 OpenClaw 某个能力失败：

- 返回明确失败原因
- 尽量给替代建议
- 不影响原网站入口继续使用

示例：

- “这次通过对话触发失败了，你仍然可以在品牌增长工作台继续使用原入口，我也可以帮你检查失败原因。”

---

## 9. 建议新增的体验规范

## 9.1 对话优先级规则

建议：

- `只读 > 低风险执行 > 高风险执行 > 后台治理`

优先让用户先获得结果，再逐步扩展复杂能力。

## 9.2 追问上限规则

建议：

- 单次请求最多连续追问 1 到 2 次
- 超过后要给用户可选项，而不是无限追问

## 9.3 自动补全规则

系统自动补全：

- 当前品牌
- 默认时间范围
- 最近任务类型
- 当前工作台语义

## 9.4 页面跳转规则

只有以下情况推荐跳页：

- 需要查看复杂设计结果
- 需要编辑长文内容
- 需要审批
- 需要查看大表格或大图集

---

## 10. 观测与验收指标

## 10.1 无侵入指标

- OpenClaw 开启后，主站核心页面 P95 延迟无显著劣化
- OpenClaw 模块故障时，主站核心流程可正常使用
- OpenClaw 可在 5 分钟内通过开关或回滚关闭
- OpenClaw 任务洪峰不影响主站正常任务处理

## 10.2 体验指标

- 授权后首个成功任务对话轮数尽量小于等于 2
- 常见只读查询尽量单轮完成
- 常见低风险动作尽量 1 到 2 轮完成
- 非必要追问率持续下降

## 10.3 业务指标

- 用户通过对话完成的有效任务数
- 对话触发任务成功率
- 对话转人工页面补充率
- 高风险动作确认通过率

---

## 11. 开发与上线建议

## 11.1 技术建议

- Assistant Gateway 独立部署或独立逻辑隔离
- 独立限流
- 独立审计
- 独立功能开关
- 先读后写
- 先内测后灰度

## 11.2 产品建议

- 授权页做得极简
- 对话入口显眼但不打断主流程
- 默认展示“你现在能做什么”
- 默认不要求用户理解系统术语

## 11.3 实施建议

- 先做“授权后可用的 10 个高频只读能力”
- 再做“5 个高频低风险执行能力”
- 最后再做高风险治理动作

---

## 12. 一句话结论

> OpenClaw 的最佳实施方式，是在技术上做到“与主站低耦合、可灰度、可降级、可回滚”，在产品上做到“授权一次、后续主要靠对话完成、只有真正必要时才追问或确认”；只有同时满足这两个条件，OpenClaw 才会既不伤系统稳定性，又真正让用户觉得好用。
