# OpenClaw正式安装与网站对接说明

## 当前结论

截至 2026-06-12，`OpenClaw / WorkBuddy / Cursor / Claude Desktop` 对接网站的正式安装链路已经基本成型，但**当前 MCP 还不能定义为“全部开发完成”**。

原因不是安装中心或 HTTP 网关没通，而是现在的产品目标已经升级为：

- 网站技能和提示词是唯一生产内核
- MCP 不只要“能调网站功能”，还要逐步承接“技能配置读取、提示词覆盖、执行跟踪、结果反馈、优化分析”这条闭环
- Skill 未来主要做编排、跟踪和优化建议，而不是复制网站原生功能

在这个口径下，当前最准确的阶段判断是：

- 安装链路已完成
- 核心执行类 MCP 已完成大半
- 技能配置治理类 MCP 已开始接入
- 反馈与提示词优化闭环尚未完成
- 因此现在**不建议进入正式 Skill 开发阶段**

## 这份文档现在要表达什么

这份文档不再只说明“怎么安装”，还要同步回答三个问题：

1. 当前 MCP 到底做完了多少
2. 哪些能力还没补齐，因此还不能定义为完全完工
3. 什么时候才适合开始正式开发“品牌运营助手 Skill”

## 目标

把本地联调用的 `账号 + 密码 + stdio 脚本` 方式，升级成正式环境可交付的 `网站安装中心 + 品牌级安装令牌 + MCP HTTP 网关` 方式。

正式交付时，品牌用户不需要理解 MCP、Skill、CLI 差异，也不需要暴露网站登录密码。用户只需要在网站里完成登录，进入安装中心，复制配置，粘贴到对应客户端即可。

当前正式交付口径需要明确：

- 当前真正需要安装的是网站 MCP
- 页面里的“品牌运营助手 Skill”目前仍然是官方说明和使用示例，不是正式执行包
- 后续如果要开发正式 Skill，也应该让 Skill 去调用网站 MCP，而不是自己再复制一套网站功能

## 为什么不再用本地联调方式

本地联调脚本只适合验证：

- 网站能力层是否可调用
- MCP 工具定义是否正确
- 对话调用链路是否可跑通

它不适合正式环境，原因包括：

- 会暴露网站账号密码
- 会要求用户在本机运行脚本
- 很难做品牌级权限隔离
- 不利于后续审计、吊销、续期

## 正式安装方式

正式环境改成三层结构：

1. 网站安装中心生成品牌级安装令牌
2. 客户端通过 MCP HTTP 地址连接网站
3. 网站 MCP 网关转调现有网站能力层

对应用户体验：

1. 用户登录网站
2. 切到目标品牌
3. 打开 `个人中心 -> OpenClaw 安装`
4. 点击“生成正式安装令牌”
5. 复制 `OpenClaw`、`WorkBuddy`、`Cursor` 或 `Claude Desktop` 配置片段
6. 粘贴到对应客户端
7. 直接开始用自然语言调用网站能力

## 安全原则

### 1. 不暴露网站账号密码

OpenClaw 安装只使用品牌级安装令牌，不再使用网站手机号、邮箱或密码。

### 2. 令牌绑定品牌

安装令牌绑定当前品牌，并在请求头里带上 `x-brand-id`，避免跨品牌误用。

### 3. 令牌绑定生成者权限

安装令牌的实际执行权限复用网站当前账号的品牌权限。如果生成者后续被移出品牌或失去权限，相关能力会自动失效。

### 4. 令牌可重置、可吊销、可过期

当前正式实现采用“品牌单活令牌”策略：

- 重新生成时，旧令牌自动失效
- 可以在网站里直接停用当前令牌
- 默认有效期 30 天

### 5. 支持基础审计

令牌记录当前已保存：

- 令牌预览
- 最近使用时间
- 过期时间
- 更新时间

后续仍需要扩展成完整工具调用审计。

## MCP 安装片段

OpenClaw 正式配置示例：

```json
{
  "mcp": {
    "servers": {
      "ai-omni-ops-品牌名": {
        "enabled": true,
        "url": "https://你的域名/api/openclaw/mcp",
        "transport": "streamable-http",
        "headers": {
          "Authorization": "Bearer ocp_xxx",
          "x-brand-id": "br_xxx"
        }
      }
    }
  }
}
```

WorkBuddy 正式配置示例：

```json
{
  "mcpServers": {
    "ai-omni-ops-品牌名": {
      "url": "https://你的域名/api/openclaw/mcp",
      "headers": {
        "Authorization": "Bearer ocp_xxx",
        "x-brand-id": "br_xxx"
      },
      "type": "streamableHttp",
      "timeout": 600000
    }
  }
}
```

## 当前 MCP 开发状态

### 已完成部分

截至当前代码状态，`apps/server/src/modules/openclaw/openclaw.service.ts` 已经暴露约 54 个 MCP tools，已覆盖以下主线：

- 品牌上下文与基础信息
- 平台账号与品牌产品
- 任务摘要、失败摘要、任务详情、取消与重试
- 知识库创建与资料上传
- 小红书原创 / 二创
- 抖音原创 / 二创
- 设计工作台
- 公众号草稿、排版工作流、发布检查、正式发布、发布历史
- 小红书 / 抖音发布接力创建与状态查询
- 品牌技能配置摘要、技能配置详情、技能配置更新、恢复平台基线

这说明当前 MCP 已经不只是“查数据”，而是开始覆盖：

- 执行网站任务
- 跟踪任务状态
- 读取网站技能配置
- 修改品牌级技能覆盖

### 还未完成部分

如果按你当前的新目标来定义，以下能力仍未完成，因此不能说 MCP 已全部开发完：

1. 提交生成结果反馈
2. 将反馈绑定到技能、提示词、任务、作品
3. 汇总用户反馈、失败原因、人工修改结果
4. 生成提示词优化建议
5. 形成“网站技能配置 -> 生成结果 -> 用户反馈 -> 优化建议 -> 技能升级”的闭环
6. 更完整的调用审计、效果统计和版本追踪

换句话说：

- 如果只按“能否安装并调网站能力”判断，MCP 已经基本可用
- 如果按“是否已经支撑未来 Skill 做编排、跟踪、反馈优化”判断，MCP 还没有完全完成

## Skill 与 MCP 的最新关系定义

### 当前阶段

当前阶段不建议为了复刻网站功能而去开发很多 Skill。

当前更合理的定义是：

- 网站里的技能和提示词，是唯一生产内核
- MCP 负责把这些网站能力、数据和配置暴露出来
- Skill 后续主要负责：
  - 理解用户需求
  - 补齐上下文
  - 调用 MCP
  - 跟踪网站内执行过程
  - 收集反馈和结果
  - 反向推动技能和提示词优化

### 为什么现在不进入正式 Skill 开发

因为网站相关能力还不够健全，最典型的就是：

- 还没有“提交生成结果反馈”
- 还没有“按技能 / 提示词汇总效果问题”
- 还没有“提示词优化建议”闭环

如果现在就进入正式 Skill 开发，Skill 只能做“调用工具”，但还无法承担你希望的主要职责，也就是“跟踪和优化网站技能”。

所以当前顺序应该是：

1. 先把 MCP 补到治理闭环
2. 再开发正式 Skill

### 后续正式 Skill 的定位

后续正式 Skill 应该优先做成一个总入口的“品牌运营助手 Skill”，而不是先拆成很多复刻网站功能的小 Skill。

这个总 Skill 的核心职责应当是：

- 获取网站里所有可用技能、提示词和品牌配置
- 获取网站里的任务、作品、报告、知识库等数据
- 根据用户需求决定调用哪些 MCP tools
- 跟踪网站内生成与发布过程
- 收集用户反馈与过程数据
- 为后续提示词优化提供依据

## 当前测试重点

从这一阶段开始，测试不再只看安装是否成功，还要看 MCP 是否已经接近“未来 Skill 的编排底座”。

当前测试重点应包括：

1. 网站页面是否能正常生成安装令牌
2. 页面复制出的配置是否正确
3. `POST /api/openclaw/mcp` 是否能用 Bearer 令牌完成 `initialize / tools/list / tools/call`
4. 客户端实际挂载后是否能在对话里调用网站能力
5. 技能配置相关工具是否能读取、更新、恢复平台基线
6. 后续补上反馈能力后，是否能形成优化闭环

- WorkBuddy 配置模板已纳入安装页
- 服务端已补入小红书 / 抖音发布接力与技能配置治理相关 MCP 工具
- 但“结果反馈、反馈分析、提示词优化建议”仍未落地，因此当前不建议判定为 MCP 全部开发完成

## 当前阶段结论

现在最准确的阶段结论是：

- `MCP 安装链路`：已完成
- `MCP 核心业务能力`：已完成大半，可进入持续补强
- `MCP 技能治理能力`：已开始接入
- `MCP 反馈优化闭环`：未完成
- `正式 Skill 开发`：暂缓，等网站能力更健全后再进入

## 进入 Skill 开发前的条件

建议至少满足以下条件，再进入正式 Skill 开发：

1. 已支持提交生成结果反馈
2. 已能把反馈与任务、作品、技能、提示词关联
3. 已能查看某个技能最近的反馈问题与失败模式
4. 已能为提示词生成优化建议或优化摘要
5. 已补充关键调用日志和效果统计

在这些条件满足前，优先工作应继续放在 MCP 和网站治理能力本身，而不是急着做正式 Skill。

## 上线前最小检查清单

为了把这套能力真正交付给品牌用户，建议上线前至少完成以下检查：

1. 将最新前端代码部署到正式网站，确认 `个人中心 -> OpenClaw 安装` 可访问
2. 进入安装页后验证“生成正式安装令牌 / 停用当前令牌 / 复制配置”三项操作
3. 校验安装页里的文档链接能打开：
   - `OpenClaw正式安装与网站对接说明.html`
   - `品牌运营助手Skill示例SKILL.html`
4. 使用页面生成的正式令牌，在真实 OpenClaw 或 WorkBuddy 客户端完成一次 MCP 挂载
5. 在客户端里至少验证一次：
   - 获取当前品牌上下文
   - 查看最近任务摘要
   - 查看最近品牌增长报告摘要
   - 创建知识库或生成规划类内容
   - 查看技能配置详情
6. 验证令牌重置后，旧配置立即失效，避免品牌成员继续误用旧令牌

- 增加调用日志表，记录工具名、品牌、调用耗时、结果状态
- 增加技能 / 提示词版本效果追踪
- 在 Skill 开发前，先补一份“品牌运营助手 Skill 编排原则说明”
