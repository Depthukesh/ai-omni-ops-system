关键纠偏说明

OpenClaw 渠道、Skill 与 MCP 对接说明

OpenClaw 的主入口不是网站前端，而是飞书、企微等外部沟通渠道。 Skill 负责业务理解、任务编排和输出体验，MCP 负责网站能力和历史数据的标准化接入， 网站第一阶段主要提供后端能力层、绑定鉴权和复杂结果落点页。

渠道 飞书、企微等是主要对话入口，不是网站聊天框。
Skill 负责业务语义、高频任务、工作流、追问策略和输出风格。
MCP 负责把网站能力和历史数据以标准化工具 / 资源形式暴露给 OpenClaw。
网站 第一阶段重点是后端能力层、鉴权绑定、审计和深链接页面。

正确理解 OpenClaw

它首先是什么

  • 自托管 Gateway
  • 多渠道 AI 助手
  • 通过 Feishu、Slack、Telegram 等渠道对话
  • Control UI 是辅助控制界面，不是必须主入口

对我们意味着什么

  • 用户主要不在网站里和 OpenClaw 对话
  • 网站不是第一阶段的主聊天入口
  • 网站仍然是业务能力、历史数据和权限的权威来源

Skill、MCP、CLI 分工

Skill

  • 教 agent 如何理解业务语义
  • 定义高频任务和工作流
  • 定义追问策略和输出风格
  • 不直接读数据库
  • 不承接底层权限校验

MCP

  • 承接网站能力和历史数据读取
  • 承接任务触发和结构化结果返回
  • 是受控工具接入层
  • 不是业务语言定义层

CLI

  • 主要用于 Onboarding、运维和调试
  • 可管理 MCP 定义和排障
  • 不是业务员工的主入口

我们系统里的正确关系

层级 在我们系统中的作用
渠道 飞书、企微等负责用户发消息和收结果，是主交互入口
OpenClaw Gateway 负责消息接入、会话路由、Skill 装载、MCP 调用和会话管理
Skill 定义品牌运营助手的业务理解、任务编排、追问和输出规则
MCP 把网站已有能力和历史数据包装成标准化工具 / 资源
网站后端 作为数据、权限、任务执行和审计的权威后端

推荐接入架构

渠道层

飞书机器人、企微机器人作为主要对话入口。

Gateway 层

接收渠道消息、路由到 session、调 Skill、调 MCP。

Skill 层

定义品牌运营助手的高频任务、历史数据使用规则、默认追问策略和输出结构。

MCP 层

建议拆成品牌上下文、任务与报告、知识库、技能配置、内容生成、历史分析等 MCP 能力集。

请求如何跑通

例子一：总结失败任务原因

  • 用户在飞书里提问
  • Gateway 识别用户、品牌和权限
  • Skill 判断为“失败任务总结”
  • MCP 读取失败历史、错误摘要、重试记录
  • OpenClaw 返回结构化结论

例子二：做一版小红书原创图文

  • 用户在企微里发起需求
  • Skill 判断是否需要最少追问
  • MCP 触发网站现有内容生成任务
  • Task 在网站原有链路执行
  • 结果摘要和链接回传到企微

第一阶段需要什么

重点要做

  • 飞书、企微渠道接入
  • 账号绑定和品牌权限识别
  • 品牌运营助手 Skill
  • 网站 MCP 能力层
  • 审计与风控

第一阶段不应重点做

  • 网站内聊天前端
  • 复杂站内对话交互
  • 把 OpenClaw 当成第二套网站 UI
对我们这套系统来说，正确接法不是“在网站里再做一个聊天框”，而是“让飞书、企微成为对话入口，让 Skill 成为任务理解和编排层，让 MCP 成为网站能力与历史数据接入层”。
