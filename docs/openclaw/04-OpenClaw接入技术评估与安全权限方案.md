# OpenClaw 接入技术评估与安全权限方案

## 1. 文档目的

这份文档是在既有 `OpenClaw 对接网站方案` 基础上的增强版技术评估稿，重点回答四个问题：

1. 面向当前这套网站系统，对接 OpenClaw 类智能体时，`Skill`、`MCP`、`CLI` 三种方式分别有什么优劣势。
2. 对于“让员工在权限内自由使用网站全部能力和读取全部可见数据”这一目标，技术上应如何落地。
3. 网站在接入智能体后会面临哪些新增安全威胁，分别应如何防护。
4. 最终推荐采用什么组合架构，以及应该按什么顺序实施。

一句话结论：

> 对员工开放的网站级智能体接入，推荐采用“`Skill 负责认知与路由` + `MCP 负责受控能力调用` + `CLI 仅限内部运维与受限后台自动化`”的组合方案，而不建议把 CLI 作为面向员工的网站主接入层。

---

## 2. 你的核心诉求转译

结合现有方案和你这次补充的要求，技术目标可以明确为：

### 2.1 业务目标

- 员工可以在网站内像使用一个“超级助手”一样自然使用系统功能。
- 员工在自己的权限范围内，尽量不用记菜单路径，也能调用网站现有能力。
- 员工在自己的权限范围内，可以读取所有允许查看的数据，而不是只能用少量预置问答。
- 系统支持多品牌、多角色、多成员协作，且不串数据。
- 高风险动作可确认、可审计、可追责、可回滚。

### 2.2 技术目标

- 智能体不能直连数据库。
- 智能体每次调用都必须带上真实用户身份。
- 所有请求都必须带上品牌上下文、角色上下文、资源范围和操作范围。
- 前台员工可以“自由使用”，但自由是建立在强约束的授权、审计和风险分级之上。
- 接入层要具备长期产品化能力，而不是只能做一次性脚本对接。

### 2.3 安全目标

- 不越权。
- 不串品牌数据。
- 不泄露敏感字段和密钥。
- 不让提示词注入、恶意网页、恶意文件等内容带着智能体越权执行。
- 不让“自由使用”演变成“自由破坏”。

---

## 3. 三种接入方式的定义

为了避免讨论时混淆，先统一三个概念：

### 3.1 Skill

这里的 `Skill` 指面向智能体的认知规则层，包括：

- 系统定位说明
- 数据字典
- 实体关系
- 工具选择规则
- 输出约束
- 风险边界
- 写操作确认规则

它更像“智能体的大脑说明书”和“业务操作手册”，不直接承载真正的数据权限执行。

### 3.2 MCP

这里的 `MCP` 指面向模型的受控工具协议层，包括：

- 标准化工具定义
- 参数 Schema
- 调用上下文
- 工具权限控制
- 结果结构化返回
- 统一审计和限流

它更像“智能体和网站之间的标准化工具网关”。

### 3.3 CLI

这里的 `CLI` 指命令行工具层，包括：

- 网站或后台封装的命令行入口
- 管理脚本
- 内部自动化命令
- 定时任务与运维脚本

它更像“给开发者、运维或内部自动化使用的强控制台”，不是天然适合直接暴露给普通员工的网站级交互方式。

---

## 4. 三种方式的技术评估

## 4.1 总体结论

如果你的目标是：

- 员工直接在网站或消息渠道中使用智能体
- 在权限内自由读取和操作网站能力
- 未来可持续扩展到更多模块、更多角色和更多品牌

那么推荐顺序是：

1. `MCP` 作为主执行层
2. `Skill` 作为智能认知与编排层
3. `CLI` 作为内部受限补充层

也就是：

> `Skill + MCP` 是主方案，`CLI` 是补方案，不是主方案。

---

## 4.2 Skill 的优劣势

### 优势

- 开发成本低，起步快。
- 特别适合把你这套系统的品牌模型、权限边界、业务规则讲清楚。
- 适合定义“什么时候需要先确认品牌”“什么时候必须先确认写操作”。
- 适合做工具路由，把用户自然语言映射到正确能力。
- 对多轮对话体验提升明显。

### 劣势

- Skill 本身不是权限系统。
- Skill 本身不负责强制执行权限，只能“告诉模型应该怎么做”。
- 如果没有受控工具层支撑，Skill 很容易变成“只会解释、不会安全执行”。
- Skill 规则越多，越需要版本管理和回归测试，否则行为容易漂移。

### 适合承担的角色

- 智能体系统认知层
- 业务术语解释层
- 品牌上下文选择规则
- 工具选择与流程编排
- 风险提示与输出约束

### 不适合单独承担的角色

- 最终权限裁决
- 高风险写操作执行
- 敏感数据过滤的最后一道防线

### 结论

`Skill` 必须有，但不能单打独斗。

---

## 4.3 MCP 的优劣势

### 优势

- 工具定义标准化，参数和返回结构清晰。
- 很适合把网站能力做成“可被模型安全调用”的工具。
- 便于统一注入用户身份、品牌上下文、角色、授权范围。
- 便于做工具级权限校验、调用日志、审计、限流、熔断和灰度。
- 比“随意拼 API”更容易长期维护。
- 更适合多步复杂调用，例如“先查品牌，再查任务，再触发生成，再回读结果”。
- 更适合未来扩展到多个智能体客户端，而不是只服务一个 OpenClaw。

### 劣势

- 比单纯 Skill 成本高，需要做工具 Schema、鉴权、错误码、可观测性。
- 首次接入时会增加一层系统抽象。
- 如果工具颗粒度设计得太细，会导致调用链过长；设计得太粗，又会失去复用性。

### 适合承担的角色

- 网站智能体能力网关
- 统一工具注册中心
- 权限与品牌上下文强制执行层
- 工具调用审计层
- 智能体标准接入层

### 不适合直接承担的角色

- 复杂自然语言理解
- 业务语义讲解
- 大量领域规则描述

### 结论

如果你要做“员工真正可用、长期可扩展、能控风险”的网站智能体，`MCP` 最适合作为主执行层。

---

## 4.4 CLI 的优劣势

### 优势

- 对内部工具、管理任务、批量操作、脚本自动化非常高效。
- 封装复杂后台操作时，研发与运维使用门槛低。
- 适合跑定时任务、批量修复、内部诊断、只在受控环境运行的自动化能力。
- 一些已有能力如果已经是脚本或命令，短期改造成本可能最低。

### 劣势

- 对普通员工不友好，不适合作为网站主交互层。
- 安全风险更高，尤其是命令注入、环境变量泄露、主机权限扩大化。
- 天然依赖运行环境，难以在多租户、多品牌、多角色场景下精细授权。
- 不利于前端体验、权限审计和结构化返回。
- 一旦把 CLI 暴露给智能体，若隔离不严，破坏面可能远高于 API/MCP。

### 适合承担的角色

- 内部运维自动化
- 只在后台受控环境执行的批处理
- 诊断、同步、修复、导出等内部工具
- 被 MCP 服务端包装调用的受限执行器

### 不适合直接承担的角色

- 员工网站智能体的主能力层
- 前台高频业务查询和写操作
- 面向多角色、强权限边界的统一网站接口层

### 结论

`CLI` 可以保留，但应该在 `MCP` 或后台服务之后，作为一个被严格包裹、严格白名单化的内部执行器，而不是直接面向员工开放。

---

## 4.5 三种方式对比

| 维度 | Skill | MCP | CLI |
| --- | --- | --- | --- |
| 上手速度 | 快 | 中 | 快 |
| 长期可维护性 | 中 | 高 | 中低 |
| 权限强约束 | 低 | 高 | 低到中 |
| 结构化调用 | 中 | 高 | 低 |
| 多品牌隔离 | 依赖外层 | 强 | 容易出问题 |
| 对员工友好度 | 高 | 高 | 低 |
| 对运维友好度 | 中 | 中 | 高 |
| 审计能力 | 依赖外层 | 高 | 中 |
| 风险控制 | 低 | 高 | 低到中 |
| 适合作为网站主接入层 | 否 | 是 | 否 |

## 5. 推荐总体架构

## 5.1 推荐架构结论

建议采用五层架构：

1. `网站前端 / 消息渠道 / OpenClaw 客户端`
2. `Skill 层`
3. `Assistant Gateway / MCP Server`
4. `领域服务层 / 聚合 API 层`
5. `数据库 / 对象存储 / 任务系统 / 现有业务服务`

### 核心原则

- 员工看到的是统一助手。
- 模型理解靠 Skill。
- 真正执行靠 MCP。
- 所有数据访问最终都落到网站自己的领域服务和权限体系。
- CLI 只能在后台受控使用，不进入员工直接能力面。

---

## 5.2 推荐调用链

建议流程如下：

1. 员工在网站或 OpenClaw 中发起请求。
2. 系统识别当前用户、当前品牌、当前组织、当前角色。
3. Skill 判断问题类型、确认是否需要切品牌、是否需要写操作确认。
4. MCP 工具层接收调用。
5. MCP 工具层从会话中自动注入：
   - `userId`
   - `brandId`
   - `orgId`
   - `role`
   - `allowedScopes`
   - `dataVisibilityPolicy`
6. 领域服务层执行实际查询或操作。
7. 返回结果前执行字段级脱敏、结果裁剪、来源标注和审计记录。
8. Skill 再把结构化结果组织成自然语言回复。

---

## 5.3 为什么不建议“直接 Skill + API”作为最终形态

虽然第一版可以先这么做，但它有几个长期缺点：

- API 规范容易分散在多个模块里，不利于统一治理。
- 权限、限流、审计、工具注册会逐渐分散。
- 后续接更多智能体客户端时会重复接入。
- 复杂调用链缺少统一工具编排层。

因此更推荐：

- MVP 允许 `Skill + 聚合 API`
- 正式版升级为 `Skill + MCP + 领域服务`

---

## 6. 权限目标如何落地为技术方案

你提出的重点是：

> 我希望不同权限的员工，他们可以非常自由地在权限内使用网站里面的所有功能和读取所有数据。

这句话的关键不是“所有人都能做所有事”，而是：

> 任何一个员工，在自己的授权范围内，都应该尽量完整地使用可用能力，而不需要因为 AI 接入方式受额外限制。

这要求权限设计不能只做页面菜单权限，而要做四层权限。

## 6.1 四层权限模型

### 第一层：身份层

判断“你是谁”：

- 用户 ID
- 员工身份
- 所属组织
- 登录方式
- 会话状态
- 设备与风险状态

### 第二层：品牌成员层

判断“你属于哪个品牌、在品牌里是什么角色”：

- 是否属于该品牌
- 是否是 OWNER / ADMIN / EDITOR / OPERATOR / VIEWER
- 是否是外部协作者

### 第三层：能力层

判断“你能调用哪些能力”：

- 是否可读取品牌档案
- 是否可读取品牌资产
- 是否可读取知识库
- 是否可读取任务
- 是否可触发生成
- 是否可修改技能中心
- 是否可导出数据
- 是否可恢复平台基线

### 第四层：数据范围层

判断“你能看到这些能力下的哪些数据”：

- 是否可看本品牌全部数据
- 是否仅可看自己创建的数据
- 是否可看某些敏感字段
- 是否可看某些部门范围内的数据
- 是否可导出明细还是只能看摘要

---

## 6.2 从 RBAC 升级到“RBAC + Scope + Policy”

如果只做传统角色权限，后面会不够用。

推荐采用：

- `RBAC`：定义基础角色，如 OWNER、ADMIN、EDITOR、OPERATOR、VIEWER
- `Scope`：定义动作范围，如 `brand.asset.read`、`brand.task.run`
- `Policy`：定义额外限制，如“只能看自己部门”“只能看脱敏手机号”“只能导出摘要”

### 示例

#### VIEWER

- 可以读品牌档案
- 可以读品牌资产摘要
- 可以读任务结果
- 不可发起高成本生成
- 不可修改技能配置
- 不可导出完整敏感数据

#### OPERATOR

- 可以读大部分品牌数据
- 可以触发常规工作台生成
- 可以查看任务详情
- 不可改平台级或品牌级核心配置
- 不可做高风险批量导出

#### EDITOR

- 可以读写内容、素材、知识库、部分任务
- 可以触发生成
- 可以更新部分提示词或业务配置
- 不可恢复平台基线

#### ADMIN

- 可以管理品牌内绝大多数配置
- 可以恢复品牌技能到平台基线
- 可以导出品牌级完整数据
- 可以配置 OpenClaw 授权与可用能力集

#### OWNER

- 拥有品牌最高权限
- 可授权、撤权、审计和做高风险批准

---

## 6.3 自由使用但不越权的关键实现

要实现“自由”，必须做三件事：

### 1. 能力发现

员工进入助手时，系统自动返回：

- 当前品牌
- 当前角色
- 当前可用能力列表
- 当前不可用能力及原因

这样员工不会因为“AI 不知道我能干什么”而受限。

### 2. 自动上下文注入

员工不需要每次手工说明权限和品牌，系统自动给每次工具调用附带：

- 当前用户
- 当前品牌
- 当前角色
- 当前组织
- 当前范围策略

这样员工可以自然表达需求，系统自动边界收口。

### 3. 风险分级执行

不同操作按风险级别处理：

- `L1 只读`：直接执行
- `L2 低风险写操作`：执行前简短确认
- `L3 高风险写操作`：二次确认 + 审计 + 可回滚
- `L4 敏感操作`：管理员批准或双人确认

这样员工体验仍然自由，但系统不会让危险动作静默发生。

## 7. 推荐的工具能力建模方式

## 7.1 不要按“页面按钮”建模

不要让智能体能力直接等于网站页面按钮，否则扩展性会很差。

## 7.2 要按“业务动作”建模

建议把能力定义成标准动作：

- `brand.read.summary`
- `brand.read.archive`
- `asset.read.list`
- `asset.read.detail`
- `task.read.list`
- `task.read.detail`
- `task.run.content_generation`
- `knowledge.read.list`
- `knowledge.write.upload`
- `skill.read.profile`
- `skill.write.prompt`
- `skill.reset.baseline`
- `report.export.summary`
- `report.export.full`

然后：

- 前端页面权限
- MCP 工具权限
- 审计日志
- 风险等级

都围绕同一套动作编码来做。

- `list_brand_assets`

### B. 分析类工具

- `summarize_brand_archive`

### C. 执行类工具

- `run_hot_topic_generation`

### D. 管理类工具

### E. 内部受限工具

- `run_internal_cli_job`

这类工具不能直接给普通员工，只能在后台受控使用。

## 8. 网站安全威胁清单与应对方案

接入智能体后，安全威胁不再只有传统 Web 风险，还会叠加模型调用风险、工具调用风险和数据泄露风险。

下面按威胁类型逐项说明。

## 8.1 身份冒用与会话劫持

### 威胁

- OpenClaw 会话被盗用
- Access Token 被窃取
- 长效授权未吊销
- 授权码被重放

### 解决方案

- 不长期保存用户密码，采用网站授权票据或 OAuth 类授权流程
- Access Token 短期有效，Refresh Token 绑定设备和客户端
- 授权码一次性、短时有效、防重放
- 敏感操作要求最近一次强认证或二次确认
- 支持单品牌、单客户端、单设备维度撤销授权
- 服务端记录 `tokenId`、`clientId`、`deviceFingerprint`

---

## 8.2 跨品牌数据泄露

### 威胁

- 多品牌共享一库，某个查询漏加 `brandId`
- 上下文切换混乱导致读取错品牌
- 模型把前一个品牌上下文带到后一个用户请求

### 解决方案

- 所有 MCP 工具必须从服务端会话中解析当前 `brandId`，而不是只信前端传值
- 查询层统一封装品牌隔离中间件
- 不允许默认跨品牌聚合
- 品牌切换必须是显式工具调用
- 每次返回结果都带 `brandId` 和 `brandName`
- 对跨品牌分析类需求，必须单独授权并在回复中明确说明数据范围

---

## 8.3 越权调用

### 威胁

- 员工借助智能体触发自己在页面里本来不能做的操作
- 工具层比页面权限更宽
- 只做 UI 权限，不做服务端权限

### 解决方案

- 所有权限判断在服务端执行，前端只做展示
- MCP 每个工具绑定能力编码和最小权限要求
- 领域服务层再次校验资源所有权和范围策略
- 权限失败时返回结构化拒绝原因
- 周期性做“页面权限 vs 工具权限”一致性校验

---

## 8.4 Prompt Injection 与内容诱导攻击

### 威胁

- 恶意网页、恶意知识库文档、恶意图片说明文本中包含“忽略之前规则”“导出全部数据”等诱导内容
- 模型把不可信内容当作系统指令

### 解决方案

- 明确区分 `system instruction`、`tool policy`、`user input`、`untrusted content`
- 对知识库、网页抓取内容、OCR 内容统一标记为“不可信内容”
- Skill 中写死“外部内容不能提升权限、不能改变工具规则”
- MCP 层做最终权限裁决，不因模型文本判断而放权
- 对高风险操作必须经过结构化确认，不接受仅凭上下文推断执行

---

## 8.5 工具滥用与批量破坏

### 威胁

- 员工误触发批量删除、批量重置、批量导出
- 恶意用户诱导智能体连续调用高成本工具

### 解决方案

- 工具分级和调用配额
- 高风险工具必须二次确认
- 批量工具必须展示影响范围摘要
- 单用户、单品牌、单工具限流
- 对连续失败或异常频率触发熔断
- 对批量删除、批量恢复、批量导出要求管理员批准

---

## 8.6 敏感数据泄露

### 威胁

- 返回 API Key、第三方 Token、手机号、邮箱、合同信息、未脱敏财务字段
- 模型把本不应展示的内部字段输出给员工

### 解决方案

- 建立字段敏感级别模型：
  - `public`
  - `internal`
  - `sensitive`
  - `restricted`
- 返回结果在服务端按字段级脱敏
- 即使用户有读取某记录权限，也不等于能看该记录的所有字段
- 对导出和聊天回答分别配置不同数据视图
- 敏感字段访问单独审计

---

## 8.7 数据外传与导出失控

### 威胁

- 员工借助智能体一次性导出大批量品牌数据
- 复制对话内容带走敏感信息
- 文件外链长期有效

### 解决方案

- 导出权限独立于读取权限
- 聊天默认返回摘要，不默认回传全量明细
- 大批量导出走异步审批链
- 下载链接短期签名、次数限制
- 高敏导出支持水印和导出原因记录

---

## 8.8 命令注入与 CLI 扩权

### 威胁

- 如果智能体可直接调用 CLI，可能出现命令拼接、参数注入、系统命令扩权

### 解决方案

- 不允许模型直接拼接 Shell 命令
- CLI 只允许执行白名单命令模板
- 禁止把自由文本直接拼进命令行
- CLI 运行在隔离环境或作业容器中
- 运行身份使用最小权限账户
- 命令执行全量审计

---

## 8.9 RAG / 知识库投毒

### 威胁

- 员工上传恶意文档，让智能体在回答时偏向错误结论或诱导执行风险动作

### 解决方案

- 知识库分品牌隔离、分数据源隔离
- 文档入库前做基础安全扫描
- 把“知识内容”和“执行权限”严格分离
- 知识库只影响回答内容，不直接提升工具权限
- 对引用来源做可追溯展示

---

## 8.10 审计缺失导致无法追责

### 威胁

- 出现错操作后，不知道是谁在什么品牌、通过什么工具做的

### 解决方案

- 统一记录：
  - `requestId`
  - `userId`
  - `brandId`
  - `toolName`
  - `actionCode`
  - `riskLevel`
  - `inputSummary`
  - `resultSummary`
  - `approvalId`
  - `traceId`
- 写操作日志不可被普通员工篡改
- 支持按用户、品牌、工具、时间回放链路

---

## 8.11 成本失控与资源滥用

### 威胁

- 高频调用大模型、批量触发生成任务、恶意消耗积分或算力

### 解决方案

- 按用户、品牌、角色设置额度
- 按工具设置调用频率和并发上限
- 高成本工具返回预计消耗并要求确认
- 对异常用量报警
- 对预算超限自动降级到只读模式

---

## 8.12 供应链与第三方依赖风险

### 威胁

- OpenClaw、模型服务、第三方抓取或外部 API 异常导致结果污染或系统暴露

### 解决方案

- 第三方访问全部走服务端代理或受控出网
- 第三方错误不透传内部堆栈和密钥
- 外部响应做大小、类型、内容校验
- 外部依赖按品牌或工具隔离配置

---

## 9. 推荐的安全控制体系

## 9.1 身份与授权

- 网站统一身份源
- OpenClaw 使用网站授权票据换会话
- 会话与品牌上下文绑定
- 敏感操作支持二次确认与短期再认证

## 9.2 工具治理

- 所有能力通过 MCP 暴露
- 工具有唯一 ID、版本号、风险等级、最小权限要求
- 工具返回统一错误码和拒绝原因

## 9.3 数据治理

- 字段分级
- 结果脱敏
- 默认最小返回
- 摘要与明细分离

## 9.4 执行治理

- 限流
- 配额
- 幂等控制
- 高风险确认
- 批量操作审批

## 9.5 审计治理

- 读敏感数据记审计
- 写操作必审计
- 审计日志可检索、可追踪、可告警

---

## 10. 推荐实施路线

## 10.1 阶段一：形成统一权限与能力模型

先完成：

- 角色定义
- Scope 定义
- 数据可见性策略
- 风险等级定义
- 审计字段定义

这是后面一切能力开放的基础。

## 10.2 阶段二：MVP 版 Skill + 聚合 API

先跑通：

- 授权登录
- 品牌切换
- 只读问答
- 少量低风险操作

目的是快速验证员工使用体验。

## 10.3 阶段三：升级为 MCP 主执行层

把高频能力全部纳入 MCP：

- 查询类
- 分析类
- 执行类
- 管理类

并统一接入审计、限流、风险分级。

## 10.4 阶段四：引入受限 CLI 执行器

只给内部后台使用：

- 批量同步
- 索引重建
- 修复脚本
- 诊断命令

由 MCP 服务端按白名单触发，不直接暴露给员工。

## 10.5 阶段五：产品化前端与审批流

补齐：

- OpenClaw 授权管理页
- 可用能力展示
- 风险操作确认页
- 审计日志页
- 导出审批页

---

## 11. 最终推荐方案

## 11.1 推荐架构

- `Skill`：负责系统认知、品牌上下文规则、工具路由、回答策略、风险提示
- `MCP`：负责受控工具调用、权限校验、上下文注入、审计、限流、结构化返回
- `CLI`：仅作为后台受限执行器，不直接对员工开放

## 11.2 推荐权限模型

- `RBAC + Scope + Policy`
- 角色定义基础边界
- Scope 定义可执行动作
- Policy 定义数据可见范围和额外限制

## 11.3 推荐安全策略

- 不直连数据库
- 不直出敏感字段
- 不允许无品牌上下文操作
- 不允许模型文本绕过权限
- 高风险操作必须确认、审计、可追踪

## 11.4 推荐产品目标

让员工感觉：

- “我可以很自由地问、查、看、做”

同时让系统保证：

- “你的一切自由，都严格发生在你的身份、品牌、角色、范围和审计边界之内”

---

## 12. 一句话结论

> 如果你要的是一套真正能给员工长期使用、能接网站全部能力、又能在多品牌多角色场景下稳住安全边界的 OpenClaw 类智能体方案，最合理的路线不是只做 Skill，也不是直接开放 CLI，而是以 `MCP 为主执行层`、`Skill 为认知编排层`、`CLI 为后台受限执行器` 的组合架构来落地。
