# 公众号发布修复：容器内回读站内图片时不再误用宿主机映射端口

## 1. 背景

- 用户在公众号工作流 Step 5 点击发布时，前端与 MCP 都只收到统一的 `fetch failed`
- 进一步排查发现，失败并不在微信 `draft/add` 本身，而在发布前的图片回读阶段
- 当前发布链会先下载封面图与正文图片，再转传给微信素材接口

## 2. 真实原因

- 这条 workflow 落库的封面图与正文图片地址都是：
  - `http://127.0.0.1:13011/api/works/brands/.../assets?...`
- 这个地址对宿主机浏览器是可访问的，但在 `ai-omni-server` 容器内部并不可达
- 容器内真正可达的是服务监听端口 `3011`
- 因此 `fetch()` 在下载站内图片时直接抛出 `TypeError: fetch failed`，最终被工作流收口成统一失败

## 3. 本次修改

- 文件：`apps/server/src/modules/works/wechat-official-account-api.service.ts`
- 在下载公众号封面图 / 正文图片前，新增受控改写：
  - 仅当图片地址属于站内 `works` 生成资产接口
  - 且主机是 `127.0.0.1 / localhost / 0.0.0.0`
  - 才自动改写到容器内可达的 `127.0.0.1:${SERVER_PORT}`
- 同时补充下载失败错误文案，显式带出：
  - 源地址
  - 实际请求地址

## 4. 影响范围

- 影响模块：`works`
- 影响链路：公众号 Step 5 API 发布
- 不影响：
  - 外部公网图片下载
  - 微信 token 获取
  - 微信 `draft/add` 协议
  - 其他设计 / 作品图片生成链路

## 5. 验证

- `pnpm exec tsc --noEmit -p apps/server/tsconfig.json` 通过
- 现场复核：
  - 容器内访问 `http://127.0.0.1:13011/...` 会直接 `fetch failed`
  - 容器内访问 `http://127.0.0.1:3011/...` 可正常返回站内图片

## 6. 后续建议

- 发布链后续可继续收口成“站内资产优先走内部可达 URL / 直接文件流”，避免各模块重复处理 Docker 映射端口差异
- 如后续仍出现公众号发布失败，应优先区分：
  - 站内图片回读失败
  - 微信素材上传失败
  - 微信 `draft/add` 返回业务错误
