# 2026-06-08 视频号浏览器辅助发布最小验证方案

## 背景

- 当前已验证两条桌面发布链路可作为参考：
  - 小红书：图文笔记 -> 浏览器扩展写入草稿箱
  - 抖音：视频作品 -> 浏览器扩展辅助发布
- 用户进一步希望评估：视频号是否也能走同样的浏览器辅助发布模式。
- 当前目标不是直接开发视频号正式发布功能，而是先形成一份最小验证方案，判断这条路线是否值得继续投入。

## 已确认事实

### 1. 视频号存在官方电脑端发布入口

- 官方帮助中心已明确：
  - 电脑端浏览器登录 `https://channels.weixin.qq.com/`
  - 支持电脑端发表视频
  - 支持电脑端发表图文
- 这意味着视频号不是只能依赖手机端发布，存在浏览器辅助发布的前提条件。

### 2. 当前代码库尚未开始视频号发布开发

- 当前已有的发布链路只包括：
  - 小红书桌面/移动发布
  - 抖音桌面/移动发布
  - 公众号官方 API 发布
- 当前还没有：
  - 视频号发布会话类型
  - 视频号发布接口
  - 视频号发布弹窗
  - 视频号浏览器扩展

### 3. 现有骨架可以复用，但不能直接照搬

- 可以复用的主要是结构，不是页面脚本本身：
  - 前端发布 flow Hook
  - `services/publishing.ts` 的 API 封装风格
  - `PublishingController / PublishingService` 的会话模型
  - 浏览器扩展的 `manifest/background/content-script` 三件套
- 不能直接照搬的部分：
  - 视频号登录方式
  - 视频号发布页 DOM 结构
  - 视频号图文/视频双入口
  - 视频号上传器、编辑器和确认区交互

## 最小验证目标

本轮最小验证只回答 4 个问题：

1. 能否稳定打开 `channels.weixin.qq.com`
2. 能否在登录后的发布页稳定注入扩展
3. 能否完成视频上传并进入可编辑状态
4. 能否完成图文发布页的素材上传与文案填写

只要这 4 个问题中有 3 个能成立，就可以进入视频号第一版开发；若前两项都不稳定，则暂不继续投入。

## 验证边界

### 第一阶段只做浏览器辅助发布

- 不做官方 API 直发
- 不做手机接力
- 不做多账号复杂调度
- 不做统一插件合并

### 第二阶段只测最小素材类型

- 视频：
  - `H.264 MP4`
  - 小于 `2G`
  - `16:9` 或 `9:16`
  - `1080p`
- 图文：
  - `1-3` 张 JPG/PNG
  - 不先测超过 9 张或 18 张的边界数量

### 第三阶段只测最少浏览器矩阵

- Windows Chrome
- Mac Safari

之所以保留 Safari，是因为视频号官方说明里已经明确提到：对于 `h265` 编码视频，Chrome 电脑端存在不支持风险，Safari 更适合作为对照验证环境。

## 建议验证路线

### 路线 A：视频链路最小验证

目标：
- 证明视频号视频发布页可被浏览器扩展接管

步骤：
1. 手动登录 `https://channels.weixin.qq.com/`
2. 打开视频发布页
3. 检查 content script 是否注入成功
4. 检查扩展是否能识别上传控件
5. 检查扩展是否能写入本地视频文件
6. 检查页面是否进入“上传中 / 可编辑”状态
7. 检查标题、简介、话题等字段是否可自动填写

通过标准：
- 能找到上传控件
- 文件能被页面接受
- 至少标题和正文区可自动填写

失败标准：
- 上传控件无法定位
- 登录后页面禁止脚本写入文件
- 页面进入上传态后始终无法编辑文案

### 路线 B：图文链路最小验证

目标：
- 证明视频号图文页也可被浏览器扩展接管

步骤：
1. 登录后进入“内容管理 > 图文 > 发表图文”
2. 检查是否存在稳定的图片上传控件
3. 上传 1-3 张图片
4. 自动填写标题和正文
5. 观察页面是否允许草稿或发表前人工确认

通过标准：
- 图片上传成功
- 标题/正文可自动填写
- 页面存在明确的下一步或发表按钮

失败标准：
- 图文页入口难以稳定命中
- 上传控件无法写入
- 编辑器不接受脚本输入

## 风险清单

### 1. 登录态风险

- 视频号网页端依赖微信扫码登录与手机确认
- 登录态可能比抖音更容易受浏览器环境、设备信任和时间窗口影响

### 2. DOM 脆弱性风险

- 视频号视频页与图文页是两条入口
- 即使都在 `channels.weixin.qq.com`，也不能假设使用同一套选择器

### 3. 编码兼容风险

- 官方已明确指出 `h265` 视频在 Chrome 电脑端存在兼容问题
- 所以第一版验证必须把素材编码限定为 `H.264`

### 4. 风控与限制风险

- 可能出现手机确认、权限弹窗、上传异常、内容审核拦截等额外流程
- 这类问题决定视频号更适合做“辅助发布”，不适合一开始就追求无人值守直发

## 实施建议

### 建议 1：独立插件 PoC

- 先建立 `wechat-channel-publisher` 独立扩展目录
- 不要直接复用抖音脚本
- 更不要重新尝试统一插件

### 建议 2：先视频，后图文

- 先验证视频发布页
- 因为当前抖音侧已经沉淀了“视频上传 + 文案填写”的骨架，迁移思路最接近
- 图文页可以作为第二条验证路径

### 建议 3：沿用现有调试取证方式

- 继续沿用浏览器端远程调试日志采集
- 先只记录：
  - 页面是否注入成功
  - 上传控件是否定位成功
  - 文件写入是否成功
  - 标题/正文是否填写成功

## 推荐结论

当前最合理的下一步是：

1. 为视频号建立独立插件 PoC
2. 先跑通视频发布页最小验证
3. 再决定是否补图文发布页
4. 等视频号最小链路验证通过后，再讨论统一插件架构
