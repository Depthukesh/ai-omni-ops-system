# 2026-05-22 任务超时回收与模型兜底规范

## 背景

- 任务中心出现了作品任务长时间停留在 `RUNNING` 的情况。
- 现有系统对“首选模型失败后继续 fallback”已有部分实现，但对“单模型运行过长后自动切换兜底模型”缺少统一硬规范。
- 用户明确确认了一条长期规则：
  - 无论是生文、生图还是生视频，只要当前模型失败或运行时间过长，都必须由同类兜底模型继续接力完成任务。

## 本次确定的规则

### 1. 单模型最长运行时间

- 文本生成：`120s`
- 图片生成单张：`180s`
- 视频生成单阶段：`300s`

说明：
- 若 provider 配置中的 `timeoutMs / requestTimeoutMs` 小于以上基线，则允许使用更小值。
- 若 provider 配置中的超时时间大于以上基线，运行时必须向下收口到以上基线，避免单模型长时间阻塞整任务。

### 2. 模型切换策略

- 运行时必须先严格尝试后台技能中心当前配置的首选模型。
- 当首选模型失败或超时后，必须按同类型候选模型顺序继续 fallback。
- 不允许跳过首选模型直接落到兜底模型。
- 超时视为与调用失败同级的 fallback 触发条件。

### 3. 总任务超时回收

- 异步任务不能无限期停留在 `QUEUED / RUNNING`。
- 当前任务中心的总任务超时基线统一为：
  - 品牌增长报告：`15 分钟`
  - 可视化报告：`10 分钟`
  - 半年营销规划：`15 分钟`
  - 小红书营销策划方案：`60 分钟`
  - 抖音营销策划方案：`60 分钟`
  - 小红书营销日历：`10 分钟`
  - 小红书原创笔记：`20 分钟`
  - 小红书二创笔记：`20 分钟`
  - 小红书视频笔记：`30 分钟`

- 超过对应窗口后，系统必须自动把任务收口为 `FAILED`，并给出“已自动终止并标记失败，可重试或切换兜底模型”的提示。

## 落地范围

- `TasksService`：任务中心读取任务列表时，对超时仍处于 `QUEUED / RUNNING` 的任务做状态归一化，避免残留“假运行中”状态。
- `WorksService`：统一为小红书文本、图片、视频阶段模型调用增加单模型超时上限，让超时能够自动触发下一个候选模型。
- `ReportsService`：统一为报告类文本模型调用增加单模型超时上限，让超时与失败共享同一 fallback 逻辑。
- `docs/engineering-standards.md`：同步固化为长期工程规范。

## 验证建议

- 创建原创、二创、视频、报告类任务，确认首选模型被刻意限速或超时后，系统会继续尝试下一个同类候选模型。
- 在任务中心保留一个超出总时长窗口的 `RUNNING` 任务，确认刷新列表后自动转为 `FAILED`。
- 检查失败文案，确认保留：
  - 首选模型
  - 实际尝试顺序
  - 最后失败原因
  - 超时或失败是否触发了切换
