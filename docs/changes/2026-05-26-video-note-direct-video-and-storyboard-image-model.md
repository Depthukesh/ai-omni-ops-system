# 2026-05-26 视频笔记改为直接用故事板图生成视频，并补充故事板生图模型选择

## 背景

- 视频笔记原先在“故事板图片完成”后，还会再调用一次“短视频提示词”技能，把故事板提示词和故事板图片重新翻译成视频提示词。
- 这会带来两类问题：
  - 多一层 LLM 理解，容易把已经确认过的故事板再次带偏。
  - 技能中心里保留了一个前台实际不需要单独维护的“短视频提示词”叶子项，增加认知成本。
- 同时，视频笔记创建弹窗里只能选最终视频模型，无法单独指定“故事板图片”使用哪个生图模型。

## 本次调整

### 1. 视频阶段不再二次生成短视频提示词

- 后端继续生成最终视频时，不再调用 `generateShortVideoPromptFromStoryboard`。
- 改为直接使用固定提示词：
  - `按照故事板的内容生成视频`
- 如果用户在视频笔记里填写了额外要求，则拼接到固定提示词后一起传给视频模型。
- 最终视频阶段继续使用故事板图片作为图生视频输入。

### 2. 技能中心移除“视频笔记-短视频提示词”

- 从技能中心前端目录树中移除“视频笔记-短视频提示词”叶子项。
- 从后端技能注册表中移除 `prompt_xhs_video_short_prompt`。
- 从提示词源映射与 mock 提示词模板中移除这条旧提示词。
- 旧的阶段拆分文档保留，但已补记当前真实逻辑，避免后续误判。

### 3. 创建弹窗新增“故事板生图大模型”

- 视频笔记创建弹窗新增独立下拉框：
  - `故事板生图大模型`
- 该选择只影响第 2 阶段“故事板图片生成”，不影响最终视频模型。
- 前端会把该字段随创建请求一起传给后端。
- 后端会把该字段持久化到视频作品 metadata 中。
- 首次生成故事板图片和后续“修改重新生成故事板”都会优先使用这次选中的生图模型。

### 4. 单 Agent 文档口径继续收口

- 明确当前只有主 Agent 单线开发，不再存在并行开发的其他 Agent。
- 同步修正文档中容易让人误解为“还有其他 Agent 正在开发”的表述。

### 5. 故事板生图模型收紧为纯文生图可用模型

- 故事板图片生成默认是纯文生图场景，不能把必须依赖参考图的 edit 图生图接口混进候选池。
- 这次补上了图片 Provider 的能力标记：
  - 是否支持纯文生图
  - 是否支持参考图输入
  - 是否必须提供参考图
- 视频笔记创建弹窗的“故事板生图大模型”下拉现在只展示可用于纯文生图的模型。
- 后端真正执行故事板生图前，也会再按“是否有参考图”过滤一次 Provider，避免前端缓存、旧表单状态或 fallback 仍把请求落到 edit 接口。
- 这样可以避免用户明明选择了文生图模型，执行时却因为跑到 edit 接口而报 `编辑模式需要提供 image_urls 参数`。
- 同时修正了一个过度兜底问题：像 `Right Codes · 文生图/图生图` 这种同时支持文生图和图生图的 Provider，不能只因为名字里带“图生图”就被误判为必须带参考图。

### 6. 修正系统 Provider 同步误写 APIZ 查询路径

- 这会导致部分 APIZ 任务型图片 / 视频 Provider 在数据库里被错误回写为：
  - `queryPath=/openapi/v2/query`
  - `queryMethod=POST`
  - `queryBodyMode=taskId-json`
- 同时把图片 Provider 新增的能力字段也纳入系统同步，避免数据库继续保留旧的图片输入模式配置。

### 7. 对齐 APIZ 最新主机与故事板竖版尺寸策略

- 进一步核对 `速推` 文档后发现，APIZ 的最新任务接口示例主机已经写成 `https://api.xskill.ai`，而项目里早期接入时记录的是 `https://api.apiz.ai`。
- 本次改为：
  - 运行时优先使用 `https://api.xskill.ai`
  - 同时保留 `https://api.apiz.ai` 作为兼容地址
- 这样既对齐最新文档，也避免直接切 host 导致品牌平台匹配和历史配置瞬间失效。
- 同时补上故事板场景的 APIZ 图片比例：
  - 普通图文场景仍沿用 `4:3`
  - `video_storyboard` 场景改为竖版 `3:4`
- 此外，视频故事板 metadata 现在会额外记录：
  - 最终成功的图片 Provider 名称
  - 实际命中的 Provider host
  - 若是 APIZ 任务模式，还会记录最终成功的 taskId
- 这样后续如果再出现“首选 APIZ，但最终由 Right Codes 成功”的情况，系统内就能直接看出真实落地链路。

### 8. 修正 APIZ 双 host 执行副作用与前端重复提交风险

- 进一步排查发现，之前为了兼容 APIZ 新旧 host，把 `api.xskill.ai` 和 `api.apiz.ai` 同时放进了运行时 `baseUrls`。
- 这会导致同一个 APIZ Provider 在执行层被当成两个可轮询地址：
  - 如果第一个 host 已经创建了任务，但查询阶段超时
  - 后端循环可能继续尝试第二个 host，并再次创建一条新任务
- 本次已把两类地址拆开：
  - `baseUrls` 只保留实际执行 host
  - `platformBaseUrls` 用于品牌平台 host 匹配兼容
- 同时，APIZ 图片查询超时不再立刻判失败，而是在更长轮询窗口内继续等待，避免第三方仍在处理中时网页过早显示超时。
- 前端“添加视频笔记”入口也补了同步防重入，避免用户连续点击或状态尚未刷新时重复发起创建请求。
- 需要额外说明的是：
  - 这组 host 拆分与前端防重入，主要是为后续阶段的重复执行和提前超时补护栏
  - 它们并不等同于“最早那批同时双任务”的唯一根因判断

### 9. 补充故事板生图执行去重与尝试轨迹

- 继续排查后发现，单次故事板生图真正执行前，仍然存在运行时候选集合重复的风险：
  - 同一 Provider 记录重复装配
  - 同一 Provider 下 `baseUrl` / `apiKey` / `model` 重复
  - 同一 prompt 候选重复进入循环
- 为了避免同一次故事板生图因为运行时配置重复而再次创建多条第三方任务，本次在执行层补了统一去重：
  - `providers`
  - `baseUrls`
  - `apiKeys`
  - `models`
  - `promptCandidates`
- 同时，图片生成失败信息现在会带上实际尝试顺序，便于后续区分：
  - 是首选 Provider 真失败
  - 还是某个重复候选把执行链路带偏
- 这样后续再出现 APIZ 或其他图片平台异常时，排查不再只能看最后一条报错，而是能看到完整尝试轨迹。

### 10. 调整故事板图片查询窗口并补强成功结果解析

- 继续排查“APIZ 后台已生成，但网页仍长时间运行”后，发现问题不只在总轮询窗口，还包括两类具体卡点：
  - 单次图片查询请求允许卡住过久，导致前端明明已经出图，后端却还在等待当前这次查询返回
  - 查询接口已经返回成功，但图片地址不一定落在旧逻辑已识别的字段里，导致任务状态是成功却仍被当成“没拿到图片”
- 本次将故事板图片查询策略调整为：
  - `15 秒`查询一次
  - 总时长 `20 分钟`
  - 单次查询超时 `20 秒`
- 同时，把查到图片结果后的远程图片下载超时收紧到 `30 秒`，避免“任务已成功，但缓存落盘阶段继续卡住很久”。
- 图片任务成功结果解析也做了补强，新增兼容读取：
  - `results`
  - `content`
  - `task_result`
  - `download_url`
  - `url`
  - `fileUrl`
- 这样如果 APIZ 查询接口已经返回成功，只是图片地址字段位置与旧实现不同，后端也能直接接住并返回图片，不再继续空转到超时。

### 11. 修正对象结果被误当成图片地址的问题

- 继续根据线上报错排查后，确认这次并不是“APIZ 没有返回图片地址”，而是后端兜底解析过宽：
  - 某些字段返回的是对象
  - 旧实现却直接 `String(...)` 转成文本
  - 最终把 `[object Object]` 当成远程图片地址传入下载逻辑，触发 `ERR_INVALID_URL`
- 本次收紧了图片地址提取逻辑：
  - 只接受明确的 `http/https` 地址
  - 对对象和数组只做递归拆解，不再直接字符串化
  - 允许从 `images / url / image_url / download_url / fileUrl / result / content / data` 等嵌套结构中提取真实地址
- 同时，远程图片下载前新增地址合法性校验，避免脏值再次进入 `fetch`
- 这样即使第三方查询返回里混有对象包装层，也只会提取真实图片 URL；拿不到有效地址时会直接报“未返回有效图片地址”，而不会再出现 `[object Object]` 这一类误导性报错。

## 后续关注

- 如果后续还要让用户在后台默认配置“故事板生图模型”，可在现有创建字段基础上继续补品牌级默认值。
- 若未来视频阶段仍需要更细的 prompt 控制，建议直接做成“固定模板 + 可选补充规则”，不要再回到单独一条二次 LLM 提示词链路。
- 如果后续继续扩充第三方图片 Provider，新增 seed 时必须同时声明它支持哪种图片输入模式，避免“文生图/图生图能力边界”再次混淆。
- 如果后续再扩系统 Provider 自愈同步，必须先评估它会不会把某个平台的查询协议、回调路径或能力字段错误扩散到其他平台。
- 如果后续再遇到“第三方平台后台出现多条任务”，先区分是：
  - 前端重复请求
  - 运行时 host / key / model 重复候选
  - 还是真实 fallback 触发的新任务
