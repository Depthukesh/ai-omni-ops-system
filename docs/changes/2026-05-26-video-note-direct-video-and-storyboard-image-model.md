# 2026-05-26 视频笔记改为直接用故事板图生成视频，并补充故事板生图模型选择

## 背景

- 视频笔记原先在“故事板图片完成”后，还会再调用一次“短视频提示词”技能，把故事板提示词和故事板图片重新翻译成视频提示词。
- 这会带来两类问题：
  - 多一层 LLM 理解，容易把已经确认过的故事板再次带偏。
  - 技能中心里保留了一个前台实际不需要单独维护的“短视频提示词”叶子项，增加认知成本。
- 同时，视频笔记创建弹窗里只能选最终视频模型，无法单独指定“故事板图片”使用哪个生图模型。

## 本次调整

### 1. 视频阶段不再二次生成短视频提示词

- 后端继续生成最终视频时，不再调用 `generateShortVideoPromptFromStoryboard`。
- 改为直接使用固定提示词：
  - `按照故事板的内容生成视频`
- 如果用户在视频笔记里填写了额外要求，则拼接到固定提示词后一起传给视频模型。
- 最终视频阶段继续使用故事板图片作为图生视频输入。

### 2. 技能中心移除“视频笔记-短视频提示词”

- 从技能中心前端目录树中移除“视频笔记-短视频提示词”叶子项。
- 从后端技能注册表中移除 `prompt_xhs_video_short_prompt`。
- 从提示词源映射与 mock 提示词模板中移除这条旧提示词。
- 旧的阶段拆分文档保留，但已补记当前真实逻辑，避免后续误判。

### 3. 创建弹窗新增“故事板生图大模型”

- 视频笔记创建弹窗新增独立下拉框：
  - `故事板生图大模型`
- 该选择只影响第 2 阶段“故事板图片生成”，不影响最终视频模型。
- 前端会把该字段随创建请求一起传给后端。
- 后端会把该字段持久化到视频作品 metadata 中。
- 首次生成故事板图片和后续“修改重新生成故事板”都会优先使用这次选中的生图模型。

### 4. 单 Agent 文档口径继续收口

- 明确当前只有主 Agent 单线开发，不再存在并行开发的其他 Agent。
- 同步修正文档中容易让人误解为“还有其他 Agent 正在开发”的表述。

### 5. 故事板生图模型收紧为纯文生图可用模型

- 故事板图片生成默认是纯文生图场景，不能把必须依赖参考图的 edit 图生图接口混进候选池。
- 这次补上了图片 Provider 的能力标记：
  - 是否支持纯文生图
  - 是否支持参考图输入
  - 是否必须提供参考图
- 视频笔记创建弹窗的“故事板生图大模型”下拉现在只展示可用于纯文生图的模型。
- 后端真正执行故事板生图前，也会再按“是否有参考图”过滤一次 Provider，避免前端缓存、旧表单状态或 fallback 仍把请求落到 edit 接口。
- 这样可以避免用户明明选择了文生图模型，执行时却因为跑到 edit 接口而报 `编辑模式需要提供 image_urls 参数`。
- 同时修正了一个过度兜底问题：像 `Right Codes · 文生图/图生图` 这种同时支持文生图和图生图的 Provider，不能只因为名字里带“图生图”就被误判为必须带参考图。

### 6. 修正系统 Provider 同步误写 APIZ 查询路径

- 后续排查发现，系统 Provider 同步逻辑里曾把 `RunningHub` 的查询配置误当成所有系统 Provider 的默认值。
- 这会导致部分 APIZ 任务型图片 / 视频 Provider 在数据库里被错误回写为：
  - `queryPath=/openapi/v2/query`
  - `queryMethod=POST`
  - `queryBodyMode=taskId-json`
- 结果就是任务创建成功后，查询阶段错误打到 RunningHub 的查询接口，并返回 `404 Not Found`。
- 本次已把系统 Provider 同步改回“默认按各自 seed 的查询配置回写，只有 RunningHub 才强制覆写为 RunningHub 查询接口”。
- 同时把图片 Provider 新增的能力字段也纳入系统同步，避免数据库继续保留旧的图片输入模式配置。

## 后续关注

- 如果后续还要让用户在后台默认配置“故事板生图模型”，可在现有创建字段基础上继续补品牌级默认值。
- 若未来视频阶段仍需要更细的 prompt 控制，建议直接做成“固定模板 + 可选补充规则”，不要再回到单独一条二次 LLM 提示词链路。
- 如果后续继续扩充第三方图片 Provider，新增 seed 时必须同时声明它支持哪种图片输入模式，避免“文生图/图生图能力边界”再次混淆。
- 如果后续再扩系统 Provider 自愈同步，必须先评估它会不会把某个平台的查询协议、回调路径或能力字段错误扩散到其他平台。
