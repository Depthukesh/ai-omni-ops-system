# 2026-08-19 OpenClaw 生图已成功扣费后不应因本地缓存失败而整体报错

## 背景

用户反馈存在更严重的问题：

- 多元探索平台侧已经成功扣费
- OpenClaw 端却仍提示 `502`
- 且不是个别，而是大面积出现

这类问题与“上游 403 / 额度不足”不是同一类故障。

## 第一性原理判断

对于同步生图链路，真实成功标准应该先分层：

1. **上游 provider 是否已经成功生成结果**
2. **本站是否又成功把结果下载、归一化并落盘**

如果第 1 步已经成功，就不能因为第 2 步退化，再把整次任务重新定义为失败。

否则会出现：

- provider 已扣费
- provider 也已经给出结果 URL
- 但本站因为后处理失败把接口整体打成失败
- 外部平台误以为“这次生图没成功”

这会直接放大为重复提交、重复扣费和错误归因混乱。

## 代码结论

旧逻辑在 `apps/server/src/modules/works/works.service.ts` 中：

- provider 成功返回 `asset.url` 后
- 会继续调用 `cacheRemoteGeneratedImage()`
- 如果远程二次下载、内容归一化或本地写入失败
- 只有在少数条件下才回退使用原始远程 URL

这意味着：

- 某些已经拿到上游图片地址的成功结果
- 仍可能因为站内缓存动作失败而抛错

## 本次修复

修改文件：

- `apps/server/src/modules/works/works.service.ts`

调整逻辑：

- 只要上游已经返回合法的 `asset.url`
- 无论本地缓存 / 归一化 / 落盘是否失败
- 都优先回退为直接使用原始远程 URL 作为返回结果

也就是：

- **上游成功 = 优先返回成功**
- **本站缓存失败 = 降级，不再把整个同步接口打成失败**

## 影响

这能直接压住一类“已扣费但 OpenClaw 仍报 502”的场景：

- provider 已经成功
- 只是本站后处理失败

这类场景以后会降级成：

- 先把远程结果回给调用方
- 不再把已成功的付费调用重新归类为失败

## 说明

截至当前已核实的 `2026-08-19 11:44 ~ 12:10` 那一波重复失败，主因仍是：

- **上游成功后，不允许再因本站缓存失败把任务整体打回失败**
