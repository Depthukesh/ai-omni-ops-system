AI 全域智能体系统架构分析报告

本报告用于系统性梳理当前网站的真实架构、模块边界、数据存储设计、数据库结构，以及未来如何把模块能力改造成类似 USB 插拔一样可扩展、可复用、可维护的体系。

1. 分析范围与方法

本次分析以主仓 ai-omni-ops-system 为核心对象，因为它已经承接了当前网站的主业务链路，包括前端工作台、后台管理台、品牌增长、小红书、抖音、公众号、设计工作台、个人中心、任务中心和第三方平台配置。

目录中的 ai-omni-ops-xhs-agent 与 ai-omni-ops-system-code-backup-20260525-205255 分别更像平行开发仓和备份快照，不作为主结论的核心依据，只在资产治理层面做说明。

方法说明： 本报告综合参考了前后端代码结构、Prisma schema、迁移脚本、工程规范、站点地图、数据库存档和近期变更文档。

2. 系统总体架构

当前系统不是单一页面应用，而是一个以品牌为上下文、以多平台内容生产为核心的复合型业务系统。它同时具备 SaaS 化账号体系、多品牌工作区、内容采集、策略生成、作品生产、发布交付、模型配置与第三方平台配置等能力。

系统主轴：以品牌为统一上下文，以采集数据和品牌资料为原料，通过报告与作品模块驱动多平台内容生产，再通过发布模块输出到平台，整个过程由任务、媒体、技能、供应商和提示词系统共同支撑。

六层结构

  • 表现层：apps/web/src/app
  • 前端服务层：apps/web/src/services
  • API 代理层：Next 同域代理
  • 后端业务模块层：apps/server/src/modules
  • 基础设施层：Prisma、Storage、Common、Config
  • 数据层：PostgreSQL、OSS、本地 fallback

典型调用链

  1. 前端页面触发动作
  2. 调用前端服务层
  3. 经 Next API 代理转发
  4. 后端控制器进入对应模块
  5. Service 调用数据库、OSS、外部模型或平台
  6. 结果回写任务、资产和业务表

3. 仓库与目录结构

主仓采用 workspace monorepo 结构，核心目录包括 apps/web、apps/server、packages/shared、packages/prompt-runtime、packages/ui、docs 和 prisma。

这说明项目已经具备一定的平台化雏形，但根目录中仍有平行仓、备份仓、方案文档、素材和运维资料并存，后续需要收束资产边界，明确唯一生产主仓。

4. 独立模块清单

认证与账号模块

负责登录、注册、验证码、刷新 token、用户资料与品牌切换，是全站统一入口和身份来源。

品牌与团队协作模块

负责品牌主档案、成员、邀请、角色权限和品牌级第三方配置，是全站业务主数据中心。

后台管理模块

负责技能中心、提示词模板、Provider、第三方平台、计费规则、用户管理、知识库与统计，是平台控制面。

任务中心模块

负责长耗时链路的状态观测、失败诊断、重试与取消，是系统可运行性的关键横切面。

媒体资产模块

负责图片、视频、音频、上传媒体和 OSS 资产，是生成能力与最终交付之间的桥梁。

第三方平台配置模块

负责品牌级和用户级第三方平台密钥、平台能力目录和模型目录，是平台连接层。

6. 非独立模块与共享基础设施

当前最大风险： WorksService 与 ReportsService 已经演化为跨多个平台与多个能力域的超级服务，未来如果继续往里堆功能，会持续拉高认知成本和回归风险。
  • Works 模块： 当前最重要的生产执行中心，承接小红书、抖音、公众号、设计等多种执行链路。
  • Reports 模块： 策略与文案生成中心，承接报告、规划、日历、选题和文案。
  • Publishing 模块： 交付出口层，负责把内部作品推向外部平台。
  • Collectors 模块： 数据采集与素材输入层，为报告和作品模块提供原料。
  • Prompt / Skill / Provider 体系： 横跨所有业务模块的 AI 配置底座，是标准化和可替换的关键枢纽。

7. 数据存储与数据库设计

当前正式持久化主链路是 PostgreSQL + OSS，另有少量本地 fallback 和 mock 过渡路径。数据库整体采用 结构化主干 + JSON 扩展 的混合建模方式，以 User、Brand、Task 为三大根节点。

  • 用户与认证域
  • 品牌与协作域
  • 经营资料域
  • 任务与资产域
  • 技能与提示词域
  • 供应商与第三方配置域
  • 公众号专属域

JSON 字段的作用

  • 多平台差异字段
  • 流程状态与中间态数据

8. 数据与模块之间的关系

当前系统中最关键的三个根节点是 User、Brand 和 Task。身份从用户进入，业务在品牌上下文中展开，执行过程和诊断落在任务中心，产物再进入媒体资产和各业务域表。

  1. 用户登录并进入某个品牌上下文。
  2. 品牌资料、采集数据和营销策略从数据库读取。
  3. Reports 输出规划、日历、文案或报告。
  4. Works 生成图文、视频、HTML 或设计结果。
  5. Task 记录过程状态，MediaAsset 记录产物元数据。
  6. Publishing 把内容推向平台，业务域表再保存历史记录。

9. 对当前架构健壮性的判断

优势： 已形成统一品牌上下文、多层架构、任务化长链路、媒体资产中心、后台配置中心，以及技能/提示词/Provider 治理基础，文档体系也较完整。
风险： 超级 service 过重、前端部分壳层偏厚、数据层仍有过渡态、仓库资产未完全收束、模块注册和可插拔协议尚未建立。

10. 如何做到像 USB 插拔一样扩展模块

所谓“像 USB 插拔一样”，不是多加一个菜单，而是新增模块接入成本低、对现有系统侵入小、共享能力无需重复开发、模块既能独立运行，又能统一接入身份、品牌、权限、任务、存储和配置体系。

建议的未来三层模块模型

平台底座模块

  • auth-core
  • brand-core
  • permission-core
  • task-core
  • media-core
  • provider-core
  • prompt-core

领域能力模块

  • collector-domain
  • strategy-domain
  • copy-domain
  • image-domain
  • video-domain
  • html-render-domain
  • publish-domain

业务工作台模块

如 brand-growth-workbench、xiaohongshu-workbench、douyin-workbench、wechat-workbench、design-workbench。这些工作台不再直接依赖超级 service，而是声明自己装配了哪些领域能力。

必须补的关键点

  • 拆分 WorksService 与 ReportsService
  • 建立模块注册中心
  • 建立统一生成链路接口
  • 让页面壳层标准化
  • 建立领域模型设计模板

建议的模块注册元数据

  • moduleKey、moduleName、moduleType
  • entryRoute、requiredPermissions
  • requiredCapabilities、requiredProviders
  • requiredTables、taskTypes、mediaTypes
  • featureFlags

11. 推荐治理路线图

  1. 第一阶段： 明确唯一主仓，继续清理 mock fallback，继续收敛技能与提示词数据库真源。
  2. 第二阶段： 拆分 WorksService 与 ReportsService，把设计、公众号、视频、数字人等能力从超级服务中抽离。
  3. 第三阶段： 建立模块注册中心、统一任务/媒体/发布合同和生成链路接口。
  4. 第四阶段： 为未来新增模块提供标准接入模板，包括页面、服务、数据模型、文档和测试模板。

12. 最终结论

当前系统整体方向是正确的，已经具备较好的平台化基础，但仍处于从“功能集合”走向“模块化平台”的过渡阶段。

未来这套系统不应继续按“新增一个功能，就往某个大 service 里塞”的方式演进，而应转向：平台底座统一、领域能力复用、业务工作台装配、模块元数据注册、任务与数据合同标准化。

只有这样，未来新增模块时才能真正接近“USB 插拔式”的方便、高效、低风险接入。
