# JJYB_AI智剪 混剪模式对接开发说明

本文档面向另一套系统的软件开发人员，目标是说明如何把本项目已有的“混剪模式”接入到外部系统中，而不是重新实现一套混剪引擎。

本文仅描述当前仓库里已经存在并可调用的能力，不描述未来规划。

## 1. 对接目标

当前混剪模式包含两条真实可运行的能力链路：

1. `普通混剪`
   - 多素材智能分镜
   - 高光筛选
   - 生成覆盖目标时长的时间线
   - 渲染成片

2. `音乐卡点混剪`
   - 多素材智能分镜
   - BGM 节拍分析
   - 卡点时间线生成
   - 渲染成片并叠加 BGM

另外还提供：

1. 可轮询的智能镜头分割任务
2. 混剪任务进度查询
3. 剪映草稿导出
4. 项目/素材/任务落库

## 2. 推荐接入方式

推荐优先级如下：

### 方式 A：HTTP 服务接入，推荐

适合：

- 另一套系统不是 Python 项目
- 希望低耦合接入
- 希望把混剪作为独立能力服务

做法：

- 部署本项目服务
- 外部系统通过 HTTP 调用 `/api/upload/*`、`/api/remix/*`
- 外部系统只负责上传素材、提交任务、轮询进度、回收成片

优点：

- 改造成本最低
- 不需要理解内部服务编排
- 后续升级本仓库时，对接系统改动最少

### 方式 B：Python 源码嵌入

适合：

- 另一套系统本身也是 Python
- 希望复用 `RemixService`、`TaskService`
- 能接受对数据库、任务、文件系统的耦合

做法：

- 在对方系统中引入本仓库的 `backend/services/remix_service.py`
- 同时接入 `DatabaseManager`、`TaskService`、`VideoProcessor` 等依赖

缺点：

- 耦合较深
- 后续升级时需要关注内部接口变动

结论：**除非你们明确要把混剪能力内嵌到现有 Python 后端，否则建议使用 HTTP 服务接入。**

## 3. 混剪模式源码边界

混剪模式不是单文件能力，它依赖以下模块：

| 模块 | 作用 |
|---|---|
| `backend/api/remix_api.py` | HTTP 接口入口 |
| `backend/services/remix_service.py` | 混剪业务编排 |
| `backend/services/task_service.py` | 异步任务执行 |
| `backend/engine/smart_shot_segmenter.py` | 智能镜头分割 |
| `backend/engine/beat_remix_engine.py` | 音乐卡点分析与卡点匹配 |
| `backend/engine/puppet_sync_engine.py` | 时间线收口与渲染 |
| `backend/engine/video_processor.py` | FFmpeg 裁剪、合并、加音频 |
| `backend/api/upload_routes.py` | 视频/BGM 上传 |
| `backend/database/db_manager.py` | 项目、素材、任务落库 |
| `backend/utils/jianying_detector.py` | 剪映草稿检测与导出 |

如果只想“移植混剪模式”，至少要把上面这些模块视为一个整体。

## 4. 运行前提

另一套系统如果要复用本混剪能力，运行环境至少要满足：

1. Python 依赖已安装
2. `ffmpeg` 和 `ffprobe` 可执行
3. 进程对以下目录有读写权限：
   - `uploads/`
   - `output/`
   - `temp/`
   - `database/`
   - `logs/`
4. 若走音乐卡点模式，需要 `librosa` 可用
5. 若走镜头分析，需要 `opencv-python` 可用

注意：

- 混剪模式默认依赖本地文件路径，不是对象存储 URL。
- 如果你们的素材在 OSS / S3 / MinIO，需要先下载到本地工作目录，再调用混剪接口。

## 5. 推荐的最小对接流程

对于另一套系统，建议采用如下最小闭环：

### 5.1 上传视频素材

接口：

- `POST /api/upload/video`

表单字段：

- `video`: 文件本体
- `scene=remix`

返回重点字段：

- `data.path`: 相对路径，如 `uploads/remix_videos/xxx.mp4`

### 5.2 可选：上传 BGM

接口：

- `POST /api/upload/audio`

返回重点字段：

- `data.path`

### 5.3 提交混剪任务

统一入口：

- `POST /api/remix/generate`

这是推荐入口。它会自动：

1. 创建混剪项目
2. 组装计划 `plan`
3. 创建后台任务
4. 返回 `project_id` 和 `task_id`

### 5.4 轮询任务进度

接口：

- `GET /api/remix/progress/{task_id}`

任务完成后，读取：

- `data.video_url`
- `data.output_path`
- `data.timeline`
- `data.editing_mode`

### 5.5 可选：导出剪映草稿

接口：

- `POST /api/remix/export-jianying-draft`

## 6. HTTP 接口契约

下面只列外部系统最常用、最有价值的接口。

### 6.1 统一异步混剪入口

接口：

```text
POST /api/remix/generate
```

推荐请求体：

```json
{
  "name": "营销视频混剪任务",
  "video_paths": [
    "uploads/remix_videos/a.mp4",
    "uploads/remix_videos/b.mp4"
  ],
  "remix_mode": "general",
  "style": "dynamic",
  "target_duration_seconds": 60,
  "auto_highlight": true,
  "auto_transition": true,
  "auto_bgm": false,
  "transition_style": "auto",
  "template": "vlog",
  "quality": "1080p"
}
```

音乐卡点模式示例：

```json
{
  "name": "音乐卡点混剪",
  "video_paths": [
    "uploads/remix_videos/a.mp4",
    "uploads/remix_videos/b.mp4"
  ],
  "remix_mode": "music",
  "style": "exciting",
  "target_duration_seconds": 45,
  "music_path": "uploads/audios/bgm_001.mp3",
  "auto_bgm": false,
  "template": "highlight"
}
```

成功返回：

```json
{
  "code": 0,
  "msg": "混剪任务已创建",
  "data": {
    "project_id": "xxx",
    "task_id": "xxx",
    "plan": {
      "mode": "general",
      "style": "dynamic",
      "target_duration": 60,
      "video_count": 2
    }
  }
}
```

关键字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `video_paths` | 是 | 素材视频路径列表，必须是服务端能访问到的本地路径 |
| `target_duration_seconds` | 是 | 显式目标时长，必须大于 0 |
| `remix_mode` | 否 | `general` 或 `music`，默认 `general` |
| `music_path` | 音乐模式必填 | 音乐卡点模式的 BGM 路径 |
| `style` | 否 | `dynamic` / `calm` / `exciting` |
| `auto_highlight` | 否 | 普通模式默认启用；音乐模式默认关闭 |
| `template` | 否 | 前端节奏包模板，会映射成默认剪辑策略 |

### 6.2 查询混剪任务进度

接口：

```text
GET /api/remix/progress/{task_id}
```

成功返回示例：

```json
{
  "code": 0,
  "msg": "获取成功",
  "data": {
    "task_id": "xxx",
    "project_id": "xxx",
    "status": "completed",
    "progress": 100,
    "video_url": "/output/remix/xxx.mp4",
    "output_path": "D:/.../output/remix/xxx.mp4",
    "duration": 60.02,
    "target_duration_seconds": 60,
    "actual_duration_seconds": 60.02,
    "duration_delta_seconds": 0.02,
    "duration_within_tolerance": true,
    "video_count": 2,
    "mode": "general",
    "editing_mode": "highlight_clips",
    "timeline": []
  }
}
```

重点字段：

| 字段 | 说明 |
|---|---|
| `status` | `pending` / `running` / `completed` / `failed` |
| `progress` | 0-100 |
| `video_url` | 前端可直接播放的相对 URL |
| `output_path` | 成片绝对路径 |
| `editing_mode` | 真实成片方式，不是 UI 文案 |
| `timeline` | 可用于草稿导出或二次编辑的时间线 |

`editing_mode` 的常见值：

| 值 | 含义 |
|---|---|
| `highlight_clips` | 普通混剪高光裁切成功 |
| `beat_remix` | 音乐卡点混剪成功 |
| `basic_merge` | 仅基础合并 |

### 6.3 智能镜头分割

如果外部系统想先做“素材分析确认”，再决定是否启动混剪，可调用：

```text
POST /api/remix/smart-segment
GET /api/remix/smart-segment/{task_id}
```

请求示例：

```json
{
  "video_paths": [
    "uploads/remix_videos/a.mp4",
    "uploads/remix_videos/b.mp4"
  ],
  "threshold": 0.5,
  "use_transnetv2": true,
  "export_keyframes": true
}
```

返回结果中最重要的数据：

- `all_shots`
- `per_video`
- `processed_video_count`
- `total_shots`

这些镜头结果可直接回填到 `/api/remix/generate` 的 `segment_data` 字段里，避免主任务重复分析。

### 6.4 直接同步执行普通混剪

接口：

```text
POST /api/remix/general-mode
```

适合：

- 外部系统自己管理任务队列
- 不需要项目落库
- 只需要拿时间线和成片结果

示例：

```json
{
  "video_paths": [
    "uploads/remix_videos/a.mp4",
    "uploads/remix_videos/b.mp4"
  ],
  "target_duration_seconds": 30,
  "style": "dynamic",
  "render": true
}
```

### 6.5 直接同步执行音乐卡点混剪

接口：

```text
POST /api/remix/music-beat
```

示例：

```json
{
  "video_paths": [
    "uploads/remix_videos/a.mp4",
    "uploads/remix_videos/b.mp4"
  ],
  "music_path": "uploads/audios/bgm_001.mp3",
  "target_duration_seconds": 30,
  "beat_density": "dense",
  "slow_motion_at_climax": true,
  "render": true
}
```

### 6.6 导出剪映草稿

接口：

```text
POST /api/remix/export-jianying-draft
```

请求示例：

```json
{
  "project_id": "xxx",
  "timeline": [],
  "final_video_path": "D:/.../output/remix/xxx.mp4",
  "audio_paths": [],
  "bgm_path": "uploads/audios/bgm_001.mp3",
  "subtitle_text": "",
  "draft_dir": "",
  "export_basis": "remix_timeline"
}
```

## 7. 对接时必须遵守的业务约束

这些不是建议，而是当前实现里的真实规则：

### 7.1 必须显式传入目标时长

`target_duration_seconds` 是硬要求。

如果没有传，或者值小于等于 0，接口会直接报错。

### 7.2 音乐卡点模式不会伪装成普通混剪

如果是 `music` 模式，但：

- 没有 `music_path`
- 节拍不足
- 卡点片段裁切失败

系统会直接失败，不会偷偷回退成普通混剪。

### 7.3 自动高光失败不会静默回退

如果你请求了 `auto_highlight=true`，但没有分析出足够高光片段，系统会返回失败，不会假装做成“智能混剪”。

### 7.4 时长必须达标

当前混剪对目标时长是严格约束。

默认容差：

- `0.35s`

如果最终成片时长超出容差，会判定失败。

### 7.5 输入路径必须是服务端本地路径

当前实现大量依赖本地文件系统：

- 裁剪
- 合并
- 加 BGM
- 导出草稿

所以外部系统如果管理的是远程地址，需要先落地到本地路径。

## 8. 面向另一套系统的推荐封装方式

如果你们要在另一套系统里做“业务集成”，建议只暴露下面这组内部服务接口：

### 8.1 你们自己的上层接口建议

建议另一套系统只再封装成 4 个接口：

1. `uploadRemixSource()`
2. `startRemixJob()`
3. `queryRemixJob()`
4. `exportRemixDraft()`

不要把本项目前端里的几十个可调参数全部暴露给终端用户，否则你们自己的产品也会变复杂。

### 8.2 推荐透出的最小参数

对你们自己的产品 UI，建议只保留：

1. 素材列表
2. 模式：普通 / 卡点
3. 目标时长
4. 风格
5. BGM
6. 是否自动高光

其它高级参数如：

- `beat_sensitivity`
- `fast_keyframe`
- `feature_fusion`
- `remixModelOpt`

建议先不要暴露，除非你们确实要做专业版参数面板。

## 9. Python 内嵌接入方式

如果对方系统就是 Python 服务，可直接嵌入服务层。

最小依赖关系：

```python
from backend.database.db_manager import DatabaseManager
from backend.services.task_service import TaskService
from backend.services.remix_service import RemixService
```

典型初始化思路：

```python
db_manager = DatabaseManager()
task_service = TaskService(db_manager=db_manager, socketio=None)
remix_service = RemixService(
    db_manager=db_manager,
    socketio=None,
    task_service=task_service,
)
```

普通异步混剪：

```python
project = remix_service.create_remix_project({
    "name": "外部系统混剪任务",
    "video_paths": [
        "uploads/remix_videos/a.mp4",
        "uploads/remix_videos/b.mp4",
    ],
    "style": "dynamic",
    "target_duration_seconds": 60,
})

task_id = remix_service.process_remix(project["project_id"], {
    "video_paths": [
        "uploads/remix_videos/a.mp4",
        "uploads/remix_videos/b.mp4",
    ],
    "mode": "general",
    "target_duration_seconds": 60,
    "style": "dynamic",
    "auto_highlight": True,
})
```

直接同步普通混剪：

```python
result = remix_service.general_mode_remix(
    video_paths=[
        "uploads/remix_videos/a.mp4",
        "uploads/remix_videos/b.mp4",
    ],
    target_duration=30,
    style="dynamic",
    render=True,
)
```

直接同步音乐卡点混剪：

```python
result = remix_service.music_beat_remix(
    video_paths=[
        "uploads/remix_videos/a.mp4",
        "uploads/remix_videos/b.mp4",
    ],
    music_path="uploads/audios/bgm_001.mp3",
    target_duration=30,
    beat_density="dense",
    render=True,
)
```

## 10. 如果要从本项目中拆成“独立混剪服务”

如果你们不想整套引入，只想拆成单独服务，建议以如下边界拆分：

### 10.1 必须保留

1. `backend/api/remix_api.py`
2. `backend/services/remix_service.py`
3. `backend/services/task_service.py`
4. `backend/engine/video_processor.py`
5. `backend/engine/smart_shot_segmenter.py`
6. `backend/engine/beat_remix_engine.py`
7. `backend/engine/puppet_sync_engine.py`
8. `backend/database/db_manager.py`
9. `backend/api/upload_routes.py`
10. `backend/utils/jianying_detector.py`

### 10.2 建议替换的点

为了更适配另一套系统，建议你们做二次抽象：

1. 把本地路径改成统一的“媒体资产适配层”
2. 把 SQLite 改成你们自己的数据库
3. 把线程任务改成你们自己的任务队列
4. 把 SocketIO 事件改成你们已有的事件总线

也就是说，最适合替换的其实是：

- `db_manager`
- `task_service`
- 文件上传/存储适配

而不建议轻易重写的是：

- `RemixService`
- `BeatRemixEngine`
- `SmartShotSegmenter`
- `PuppetSyncEngine`

## 11. 已知问题与接入风险

对接前需要让另一套系统开发人员知道这几点：

### 11.1 现在是“本地文件系统优先”架构

这套混剪模式天然适合：

- 本地部署
- Windows 工作站
- Docker 容器挂载目录

不适合直接拿远程 URL 做无状态纯云函数式调用。

### 11.2 当前服务层和任务/数据库耦合较深

如果你们要深度内嵌，不能只复制 `remix_service.py` 一个文件。

### 11.3 音乐卡点模式依赖更多第三方能力

尤其是：

- `librosa`
- `opencv`
- `ffmpeg`

所以音乐卡点模式比普通混剪更容易受环境影响。

### 11.4 不是所有高级 UI 参数都已经形成稳定对外契约

前端页面里有很多专业调参项，但对接另一套系统时，不建议把这些字段直接当稳定公开 API。

建议只使用本文档列出的主干字段。

## 12. 建议的对接验收清单

在另一套系统完成接入后，建议至少做以下验收：

1. 上传 2 个视频素材，普通混剪 30 秒成功
2. 上传 2 个视频素材 + 1 个 BGM，卡点混剪 30 秒成功
3. 故意不给 `target_duration_seconds`，验证接口报错符合预期
4. 卡点模式故意不给 `music_path`，验证接口报错
5. 轮询 `progress` 能拿到 `output_path`、`video_url`、`timeline`
6. 导出剪映草稿成功
7. 素材路径改成远程 URL，验证系统按预期拒绝或先落地再处理

## 13. 最终建议

如果目标只是把“混剪模式”集成到另一套系统，最稳的方案是：

1. 保留本项目作为独立混剪服务
2. 另一套系统通过 HTTP 调它
3. 另一套系统只做：
   - 用户权限
   - 任务单管理
   - 素材管理
   - 结果展示

不要一开始就尝试把混剪引擎拆散重组。

这样成本最低，风险最小，也最符合当前仓库真实结构。
